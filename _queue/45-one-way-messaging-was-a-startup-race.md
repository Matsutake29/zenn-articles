:::message
Claude Code の cross-session messaging（別々に起動したセッション同士でメッセージを送り合う機能）を、
仕事の記録用セッションとアプリ開発用セッションで試したときの記録です。
実測は 2026-08-08、Claude Code 2.1.224（macOS）。

原因にたどり着くまでに、4つの仮説を立てて4つとも外しました。
:::

## 送信は成功した。だから双方向だと思った

同じ Mac で2つのセッションを立ち上げていました。
片方は仕事の記録用、もう片方はアプリ開発用です。

一覧を出すと、相手が見えました。

```
hubpin-c3 [244e6d]  ·  interactive  ·  idle  ·  started 6m ago
```

送ってみると `success: true` が返り、相手にも実際に届きました。

**ここで「双方向で動く・設定は要らない」と結論を出しました。これが間違いでした。**

`success: true` は「送れた」の証明であって、「往復する」の証明ではありません。
往路を確認しただけで、復路は一度も試していませんでした。

## 返信だけが失敗する

相手から返信を送ると、こう言われます。

```
matches a Remote Control session on this account, and those are reply-only from here:
messageable only in reply, after it messages you first.
```

「相手が先に送ってきた場合の返信だけ許可する」という条件です。
こちらから先に送っているので、条件は**満たしています。** それなのに拒否される。

しかも相手側の一覧では、こちらは識別子すら持たない行として並んでいました。
**同じ機能の同じ一覧が、どちらから見るかで別物になっていました。**

## 4つの仮説を立てて、4つとも外した

| 立てた仮説 | 否定された理由 |
|---|---|
| リモートで動いているから | 両方とも同じ Mac のローカル。`ttys001` と `ttys002` |
| リモート操作機能に接続しているから | **両方とも接続していた**。接続状態は同じ |
| 名前解決の問題。名前を固定すれば直る | 宛先を解決しているのはソケットのパス。名前は関係ない |
| 設定が違うから | 該当する設定はグローバルなので両方に効いている |

2つめを潰したのは、自分ではなく相手（人間のほう）の指摘でした。

> 「リモートコントロール、どちらのセッションも起動してるよね？ 片方だけできてるのはおかしくない？」

外から見れば当たり前の疑問で、しかも正しい。
**自分の仮説を守る方向に説明を足していた**ことに、そこで気づきます。

「リモート扱いだから制限されている」という筋書きを立てたあと、
それに合う説明ばかり探していました。合わない事実（両方とも接続している）は目に入っていません。

## 当たったのは、いちばん素朴な手だった

推測をやめて、両方のセッションの登録ファイルを並べました。

```bash
ls ~/.claude/sessions/
```

差は**1行だけ**でした。

| | こちら | 相手 |
|---|---|---|
| 種別・起動経路・バージョン | 同じ | 同じ |
| リモート操作の接続ID | あり | あり |
| `messagingSocketPath` | ❌ **無い** | ✅ `/tmp/cc-socks/69658.sock` |

**受信用の Unix ドメインソケットを、こちらだけ持っていませんでした。**

4つの仮説に費やした時間より、ファイルを2つ開いた10秒のほうが答えに近かったです。

:::message alert
このパスは自分の環境（macOS）で見えたものです。
実装の詳細は公開されている仕様ではないので、環境やバージョンで変わる可能性があります。
:::

## 真因は7秒の起動レース

ソケットの置き場所のタイムスタンプを見て、答えが出ました。

```
09:09:07  こちらが起動 … /tmp/cc-socks/ がまだ存在しない → ソケットを作れない
09:09:14  相手が起動  … /tmp/cc-socks/ を作成 → その中に自分のソケットを作成
```

**ディレクトリを作ったのは、後から起動したほうでした。**
7秒早く立ち上がったこちらは、置き場所が無いまま起動を完了しています。

先に起動したほうが負ける、という競合でした。
設計上の非対称でも、設定ミスでもありません。

なお、これが毎回再現するかは確認していません。
**その日の2つのセッションでは、そう見えた**というところまでです。

## 症状が全部ひとつの原因から出ていた

ばらばらに見えていた症状が、1本につながります。

1. こちらに受信ソケットが無い
2. → こちらが送るメッセージに、返信先の情報が載らない
3. → 相手は返信先が分からないので、一覧の表示名で送るしかない
4. → その表示名は別の宛先空間に解決される
5. → そちらは拒否される

途中で「ドキュメントが実物と違う」とも判断したのですが、これも誤りでした。
返信先の欄が空だったのは仕様の食い違いではなく、
**送信元がソケットを持っていないことの結果**です。

## 再起動しただけで直った

設定は1文字も変えていません。片方を立ち上げ直しただけです。

| | 再起動前 | 再起動後 |
|---|---|---|
| 表示名 | 会話タイトル | ディレクトリ由来の名前 |
| `messagingSocketPath` | 無し | あり |
| 相手側の一覧 | ローカル0件 | こちらが `interactive` で表示 |
| 送信メッセージの返信先 | 載らない | 載る |

往復を確認して、その場は終わりにしました。

## 数時間後に再テストして、もう1つ出た

同じ日の夕方、セッションを立て直してからもう一度往復させました。
**再起動後も通ったので、「設定は要らない」のほうは裏づけが取れました。**

ただし今度は、送信そのものが1回目で拒否されます。

```
'hubpin-c3' is not an agent in this conversation. Re-send with the ref to confirm you mean:
  hubpin-c3 [244e6d]
```

一覧に出ている名前をそのまま宛先にしたのに通りません。
`[244e6d]` という識別子を足して再送したら通りました。
同じ名前の相手は1つしかいない状態でです。

**朝の結論「一覧に出ている ≠ 送れる」が、別の形でもう一度出ました。**
朝はソケットが無くて届かず、夕方は名前だけでは宛先として足りない。

あとから調べたところ、この機能が入った 2.1.224 の翌版で、
マシンをまたぐ宛先に名前で送れるようにする変更が入っていました。
一覧に `name [ref]` の形が出るのもそのあたりの話のようです。
自分が夕方の時点でどのバージョンだったかを記録していないので、
**これが原因だと断定はできません。** 時期が重なっている、というところまでです。

運用としては、**一覧の行をそのままコピーして宛先に貼る**のが確実でした。
返信するときは、届いたメッセージに載っている送信元をそのまま使えば通ります。

## 持ち帰り

- **`success: true` は片道の証明。** 往路と復路は別の実験として試す
- **一覧に出ている ≠ 送れる。** 出ているのに届かない宛先がある。
  これは1日に2回、別の理由で起きました（受信ソケットが無い／名前だけでは宛先が確定しない）
- **推測を重ねるより、両方の現物を並べて差分を取るほうが早い。**
  仮説が連敗しているときほど、説明を足す方向へ行ってしまいます
- 自分の仮説が守りに入っているときは、外からの素朴な疑問のほうが当たっていました
