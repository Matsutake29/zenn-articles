Supabase（PostgreSQL）の行レベルセキュリティ（RLS）で、「公開カードは誰でも見える」と「自分のカードは本人だけ見える」の2つを書きました。

一覧を開いたら **11枚出ました。正しくは7枚**です。他人のカードまで見えていました。

この事故には2つの側面があって、どちらも自分の直感と逆でした。原因（なぜ漏れたか）と、なぜ4日間気づかなかったか。分けると弱いので1本で書きます。

## 直感1の逆: ポリシーは足すと緩くなる

書いたポリシーはこの2本です。どちらも `to` を省略しています。

```sql
-- 意図: 公開カードは誰でも
create policy "visible items are viewable by everyone"
  on public.items for select using (visible = true);

-- 意図: 自分のカードは本人だけ
create policy "users can view own items"
  on public.items for select using (auth.uid() = user_id);
```

PostgreSQL は、同じ操作に対する PERMISSIVE ポリシー（既定）を **OR で結合します**。ログイン中に効いていた条件は、こうでした。

```text
(visible = true) OR (auth.uid() = user_id)
```

他人のカードも `visible = true` なら通ります。**制限を2つ書いたから2重に厳しくなる、ではなく、逆でした。** 足すほど見える範囲は広がる。

### `to` の役目は「制限」ではなかった

用途（公開ページ用／本人用）で分けたつもりでしたが、**ロールで分けていませんでした**。`to` を省略すると全ロール（PUBLIC）に適用されます。

`to anon` を書けば「未認証のときだけ OR に参加する条件」になります。つまり `to` は「このポリシーを誰の OR に参加させるか」を決めるもので、それ自体が何かを禁止するわけではない。

同じ誤解を、10日後にもう一度しました。`to anon, authenticated` を足したポリシーを見て「ログインしていない人は読めなくなる？」と読んだのですが、両方指定しているので許可の範囲は1ミリも変わっていません。**「ロールを指定した＝制限した」は、直感として自然なので2回出ました。**

## 直感2の逆: 拒否は黙って0行になる

この事故は**4日間**気づかれませんでした。

理由の1つは単純で、ポリシーを書いた直後の検証では `items` に他人の行が1件も無かったこと。OR で緩く結合されていても、件数が変わらなかった。他人のカードが入ったのは4日後です。

もう1つの理由が、こちらの本題でした。

| 層 | 閉じ方 | 拒否されたとき |
|---|---|---|
| `GRANT` / `REVOKE`（テーブル単位） | **エラー** `42501 permission denied` | すぐ分かる |
| RLS ポリシー（行単位） | **0行**。エラーではない | 「該当データが無かった」と区別がつかない |

検証ファイルには、この2種類の期待値が並んでいます。

```sql
-- 期待: ERROR 42501 permission denied for table items   （GRANT 側）
-- 期待: 0行（エラーではない）                            （RLS 側）
```

0行のほうが怖い、と思いました。アプリから見ると成功と同じ形で返るので、**ポリシーが壊れていても画面は普通に動きます**。

自分の場合はさらに、アプリ側でも `visible` で絞っていたので、画面はずっと正しく見えていました。RLS が緩くなっていることを、画面から知る手段がなかった。

## 2つとも「閉じる」の直感が逆だった

- **足すと緩くなる。** ポリシーを増やすほど OR の枝が増える
- **拒否は静か。** 0行は成功と同じ顔をしている

どちらも「動いているから正しい」では検出できませんでした。前者は他人の行が無ければ見えず、後者はそもそもエラーが出ない。

自分が変えたのは2つです。ポリシーを書くときに `to` を必ず書くこと。それと、RLS の検証は「他人の行が実在する状態」で、件数ではなく「特定の行が見えるか」で見ること。

なお PostgreSQL には RESTRICTIVE ポリシー（AND で結合される）もありますが、今回の話は既定の PERMISSIVE の範囲です。

環境: Supabase（PostgreSQL）/ @supabase/supabase-js 2.112.1。エラーコードは実測値です。
