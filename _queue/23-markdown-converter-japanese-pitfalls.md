ブログの投稿をスクリプトから流し込むために、Markdown → HTML の変換を自作しています。
ライブラリを入れるほどの規模ではなかったので、必要な記法だけ自前で処理する方針でした。

その変換に、**日本語ブログ特有のバグが2つ**ありました。どちらも既に公開済みの記事に実害が出ていました。

## 1. 段落内の改行が消えて、半角スペースが入る

段落の中の複数行を、こう連結していました。

```python
html = " ".join(lines)
```

英語なら正しい処理です。単語の途中で改行しても、スペースで繋げば元の文になります。

日本語だとこうなります。

```
入力:
  です。
  もともと〜

出力:
  <p>です。 もともと〜</p>
```

**改行が消えたうえに、「。」の後に半角スペースが入ります。**

自分は読みやすさのために句点で改行して書く癖があります（1行が長いと読まれないので）。
その改行が全部潰れて、しかも不自然な空きが残っていました。

### 直したときに一度踏んだこと

`"<br>".join()` に変えれば済む、と思ったのですが、そのままだと `&lt;br&gt;` が本文に出ました。

原因は処理の順序です。

```python
# ダメ
html = inline_format("<br>".join(lines))   # <br> ごとエスケープされる

# 正しい
html = "<br>".join(inline_format(line) for line in lines)
```

インライン記法の処理（`**強調**` など）がHTMLエスケープを含んでいます。
そのため**先に `<br>` で繋ぐと、その `<br>` までエスケープされます。**

行ごとに整形してから連結する。順序が逆だと、タグが文字として表示されます。

## 2. リンク記法が未対応で、生のまま公開されていた

変換していたのは `**強調**` と `` `コード` `` だけでした。

`[text](url)` は処理していませんでした。
**そのため記事にそのまま `[テキスト](https://...)` と表示されていました。**

公開済みの記事1本で実際に出ていました。

対応するときに考えたのが以下です。

```python
def convert_link(m):
    text, url = m.group(1), m.group(2)
    if not url.startswith(("http://", "https://")):
        return m.group(0)          # javascript: などを弾く
    if '"' in url:
        return m.group(0)          # href属性の破壊を防ぐ
    return f'<a href="{url}">{text}</a>'
```

- **`http` / `https` のみ変換する**（`javascript:` を弾く）
- **URLから `"` を除外する**（属性値の破壊を防ぐ）
- `&` はエスケープ後 `&amp;` になるが、属性値の中ではそれが正しい

自分しか使わないスクリプトでも、`javascript:` を弾く判定は入れました。
将来的に他人の書いたMarkdownを流す可能性がゼロではないので。

## 3. 影響範囲は、全記事を走査して確定させた

修正した後にやったことです。

REST API で公開中の52記事を取得して、機械的に数えました。

- 生のリンク記法（`[...](...)` が本文に残っているもの）
- 「。 」（句点＋半角スペース）の混入

これが今回いちばんの学びでした。

**1本の記事を見て「無事だった」と判断したのは早計でした。**

記事ごとに、元のMarkdownの書き方が違うからです。
1段落を1行で書いた記事なら、`" ".join()` しても連結する行がないので影響ゼロ。句点で改行していた記事だけが壊れます。

**同じバグでも、入力の書き方によって影響が出たり出なかったりする。** サンプル1件では判定できませんでした。

```python
# 走査の骨子
for post in fetch_all_posts():
    body = post["content"]["rendered"]
    if re.search(r"\[[^\]]+\]\(https?://", body):
        print(f"生リンク: {post['id']} {post['link']}")
    if "。 " in body:
        print(f"句点+空白: {post['id']} {post['link']}")
```

### 走査したのに、1ページだけ直っていなかった

後日談があります。

全件走査して直したはずなのに、**固定ページが1つだけ古いまま**残っていました。

原因は走査対象の定義です。WordPressでは「投稿」と「固定ページ」が別の post_type で、
`wp post list` も REST API の `/wp/v2/posts` も、**既定では投稿しか返しません。**

```bash
# これだと固定ページが入らない
wp post list --format=ids

# post_type を明示する
wp post list --post_type=post,page --format=ids
```

「全記事を走査した」と思っていたものが、正確には「全**投稿**を走査した」でした。

**走査で安心するときは、走査対象の定義まで確認しないと意味がない**というのが追加の学びです。
件数が出ると数えた気になりますが、母集団が間違っていれば漏れは検出されません。

## 教訓

英語前提の実装が日本語で崩れる、というのは普遍的なテーマだと思います。
今回の `" ".join()` は、まさに「単語がスペースで区切られる言語」の前提でした。

自作の変換を使うなら、**日本語特有の入力パターンでテストする**必要があります。

- 句点で改行した段落
- 1段落1行で書いた段落
- 記法が入れ子になっているもの

そして修正したら、**過去の出力を全部走査する。** 変換スクリプトのバグは、直した時点より前に出したものに残り続けるので。

## まとめ

- 段落内の改行を `" ".join()` すると、日本語では**改行が消えて半角スペースが入る**
- `<br>` で繋ぐときは、**行ごとに整形してから連結する**（先に繋ぐとタグごとエスケープされる）
- リンク記法の追加時は `http/https` のみ許可し、URLから `"` を除外する
- **1本見て無事でも判定できない**。入力の書き方によって影響が変わる
- 変換スクリプトのバグは過去の出力に残る。**全件走査で影響範囲を確定させる**
