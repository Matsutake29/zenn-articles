macOS で書いたシェルスクリプトを Linux で動かしたら、`File: unbound variable` で落ちました。

スクリプトのどこにも `File` という変数はありません。原因は1行で、その1行には `2>/dev/null` が付いていました。

## 落ちた場所

ファイルの最終更新日を epoch 秒で返すだけの関数です。

```bash
file_epoch() {
  local f="$1"
  # ファイル名から日付が取れなければ最終更新日を使う
  stat -f %m "$f" 2>/dev/null
}

ep=$(file_epoch "$f")
[ -z "$ep" ] && continue
days=$(( (NOW - ep) / 86400 ))   # ← ここで落ちる
```

macOS では動いていました。落ちたのは Linux（GNU coreutils）に持っていったときです。

## `stat -f` の意味が BSD と GNU で違う

| | `-f` の意味 | `stat -f %m FILE` の結果 |
|---|---|---|
| **BSD（macOS）** | 出力フォーマットの指定 | mtime が epoch 秒で出る（意図どおり） |
| **GNU（Linux）** | **ファイルシステム情報を表示** | `%m` をファイル名と解釈してエラー。**そのうえで FILE の FS 情報を stdout に出す** |

GNU 側の実際の出力はこうでした。

```text
stat: cannot read file system information for '%m': No such file or directory   ← stderr
  File: ".company/.secretary/notes/2026-06-08-....md"                            ← stdout
    ID: 0        Namelen: 255     Type: ext2/ext3
```

1行目が stderr、2行目以降が stdout です。

## `2>/dev/null` が消したのは1行目だけ

ここからが本題でした。

- `2>/dev/null` が消したのは stderr の1行目だけ。**2行目以降は stdout なので生き残ります**
- 関数の最終行の stdout がそのまま返り値になるので、`ep` に `File: ".company/..."` が入る
- `[ -z "$ep" ]` は**素通り**します。空ではないので、ガードとして機能していません
- `$(( (NOW - ep) / 86400 ))` の算術評価で `ep` の中身が展開され、`File` が変数として評価される
- `set -u` が効いているので `File: unbound variable` で全体が停止

エラーメッセージには `stat` も `-f` も出てきません。**原因と無関係な場所を指していました。**

## 「失敗を無視する」ではなく「失敗の説明を消す」

`2>/dev/null` を書いたとき、自分は「失敗したら握りつぶす」つもりでいました。実際に消えたのは**失敗の説明**だけで、失敗そのものは残っています。

コマンドが失敗しつつ stdout に何かを出す場合、無視したつもりの失敗が**有効な値の顔をして下流に流れます**。今回はそれが偶然「変数っぽい文字列」だったので、算術式の中で名前解決されて落ちました。もっと悪いのは落ちないケースで、数字に見える文字列が出ていたら、間違った日数がそのまま計算されていたはずです。

このケースでは3つが同時に抜けていました。

- exit code を見ていない（`stat` は 1 で終わっているのに、その出力を使った）
- stdout の中身を検査していない（空かどうかしか見ていない）
- 消したのが stderr だけだと意識していない

## 直し方

値が期待した形かどうかを、**使う前に**確かめるだけです。

```bash
# -c は GNU・-f は BSD
out=$(stat -c %Y "$f" 2>/dev/null) \
  || out=$(stat -f %m "$f" 2>/dev/null) \
  || out=""
[[ "$out" =~ ^[0-9]+$ ]] && printf '%s' "$out"
```

`||` で繋いでいるので、GNU で `-c` が通ればそこで終わり、BSD なら `-c` が失敗して `-f` に落ちます。どちらでも最後の正規表現で「数字だけか」を見るので、`File: ...` のような文字列は返り値になりません。

`2>/dev/null` は残しています。説明を消すこと自体は問題ではなく、**消したあとに残るものを検査していなかった**のが問題だったので。

## 書いたのに漏れていた

「エラー処理を書かなかった」なら、書けばいい話です。今回は**書いたのに漏れていた**ので、自分にとってはそちらのほうが引っかかりました。

`2>/dev/null` は見た目にはエラー処理をしているように見えます。書いた本人も、そう思っています。それが「失敗の説明を消す」だけの処理だと分かっていれば、stdout の検査を別に置く判断ができたはずでした。
