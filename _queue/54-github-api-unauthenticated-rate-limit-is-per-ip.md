GitHub のリポジトリ一覧を、認証なしで1時間に1回取りに行く設計にしていました。「未認証は 60 回/時だから、1回なら余裕」という見積もりです。

成り立ちませんでした。

## 実測した値

```text
GET https://api.github.com/users/{user}/repos?per_page=1
```

| | 値 |
|---|---|
| HTTP | 200 |
| レスポンスサイズ | **6.0KB（1件）**。フィールドを絞れないので1件でも大きい |
| `x-ratelimit-limit` | **60**（未認証・1時間あたり） |

60 は想定どおり。問題は**何を60回と数えているか**のほうです。

## 未認証の制限は、送信元 IP ごとに数えられる

GitHub の未認証リクエストは、**送信元の IP アドレスに紐づけて**レート制限されます。自分のアプリが1時間に1回しか叩かなくても、**同じ IP から出た他のリクエストと合算されます**。

サーバーレス環境（Vercel の Functions など）は共有 IP から出ていきます。つまり同じ IP を使っている他のアプリが GitHub を叩いていれば、その分も自分の60回に入る。

**自分の呼び出し頻度と無関係に 429 が返りうる。** 「1時間に1回だから引っかからない」は、自分のリクエストだけを数えた見積もりでした。数える単位が違った。

## 対応の選択肢

| 案 | 上限 | 判断 |
|---|---|---|
| **失敗を許容する** | 60/h | ✅ 前回取得したデータを残し、失敗しても画面を壊さない設計にする |
| Personal Access Token を使う | 5,000/h | 環境変数の管理が増える。Cron の秘密鍵とまとめて扱う段階で入れる |

前者にしました。取得に失敗したら**前回の結果をそのまま残し、上書きしない**。それだけです。

## 失敗しても壊れない形

```text
1. 取得（失敗したらここで終わり。以降を実行しない）
2. 正規化して max 件に切る
3. 同一トランザクションで delete → insert
4. last_fetched_at / last_status を更新
```

3 を別々に実行しない。ここが要点でした。削除だけ成功して挿入が失敗すると、**表示が空になります**。

もう1つ踏みやすいのが「**200 が返ったが0件**」のケースです。これを成功として扱うと、既存のデータを0件で上書きして全部消えます。0件は失敗と同じ扱いにする必要がありました。

## 見積もりの単位を確認していなかった

- 未認証の 60/h は「**自分が60回叩ける**」ではなく「**その IP から60回**」
- サーバーレスの共有 IP では、自分の設計と無関係に上限に達しうる
- だから「叩く回数を減らす」より先に、**失敗しても壊れない形**を用意するほうが効く

レート制限の数字は見ていたのに、その数字が何を数えているかは見ていませんでした。「60」だけ見て「1回なら余裕」と判断した形です。単位を確認せずに見積もると、こういう外し方をするのだと思いました。

環境: Next.js 16.3.0 / Vercel。実測は 2026-09-01 時点。実際に 429 を踏んだかは、運用を続けてから追記するつもりです。
