転職activity用にGitHubを整えようと思って、自分の「草」を測ってみました。
そうしたら、**3ヶ月ぶんのコミットが1つも記録されていない**ことに気づきました。

原因は自分の設定ミスです。しかも**その対策は3ヶ月前に自分で決めていて、実行されないまま止まっていた**、
というのが今回のいちばん痛かったところでした。

同じ踏み方をしている人がいそうなので、記録として残します。

## 起きていたこと

作業ログ用のリポジトリで、7月にどれだけコミットしたかを数えました。

```bash
git log --since=2026-07-01 --pretty=%ad --date=short | sort | uniq -c
```

**16日ぶん、155コミット。** ほぼ毎日触っています。

一方、GitHubのプロフィールに出ていた草は **7日ぶん** でした。半分以上が消えています。

## 原因：草は default branch のコミットしか数えない

GitHubのcontribution graphには、カウントの条件があります。公式ドキュメントに書かれていますが、
そのうちのひとつが**「コミットが default branch（または `gh-pages`）にあること」**です。

自分のリポジトリはこうなっていました。

| | |
|---|---|
| default branch | `main` |
| 実際の作業ブランチ | `develop` |
| `main` の最終コミット | **3ヶ月前** |

`develop` に直接コミットする運用にしていて、`main` は放置されていました。
つまり**それ以降のコミットは、1件も草になっていなかった**わけです。

## 対策を決めていたのに、止まっていた

ここが本題です。

この仕様自体は、3ヶ月前の時点で把握していました。記録も残っていました。

> - デフォルトブランチは `main` のまま維持（GitHub標準運用に揃える）
> - **毎週金曜の作業終わりに** develop → main をマージする（週次統合）
> - 草は default branch のみカウントされるので、main マージしないと反映されない

**知らなかったのではなく、決めた運用が続かなかった。**

初回の統合はやりました。その次の週から、やらなくなりました。
「毎週金曜に手でやる」というルールは、忙しい週に一度飛ばすと、そのまま戻ってこないのだと思います。

## どう直したか

週次マージを続ける努力をやめて、**default branch のほうを `develop` に変えました**。

```bash
gh api repos/OWNER/REPO -X PATCH -f default_branch=develop
```

GitHubのWeb UIなら Settings → Branches からも変更できます。

変更すると、**過去ぶんも含めて再計算されます**。手元では1〜2時間ほどで反映されました。

| | 変更前 | 変更後 |
|---|---|---|
| 年間コントリビューション | 332 | **528** |
| 7月のコミット | 48件 / 4リポジトリ | **209件 / 5リポジトリ** |

「Contributed to」の筆頭も、外部案件のリポジトリから自分のメインリポジトリに変わりました。

## つまずいたこと：APIとWebで数字が違う

反映を確認しようとして、コマンドで測ったら**変わっていませんでした**。

```bash
gh api graphql -f query='{ viewer { contributionsCollection {
  contributionCalendar { totalContributions } } } }'
# → 332 のまま
```

一方、ブラウザでプロフィールを開くと **528** と出ています。

GraphQL側にキャッシュがあるようで、しばらく古い値を返し続けました。
**採用担当者が見るのはWebのほう**なので実務上は問題ありませんが、
「反映されていない」と誤解しかけました。**確認はWebで**したほうが確実です。

## 他にもカウントされない条件がある

今回は default branch でしたが、草がつかない条件は他にもあります。自分が確認したのは以下です。

- コミットの **author email が GitHubアカウントに紐づいていない**
- **push していない**（ローカルでコミットしただけでは乗らない）
- fork したリポジトリへのコミット
- private リポジトリの場合、プロフィール設定で
  **「Include private contributions on my profile」がオフ**になっている

private の設定は自分の場合すでにオンになっていて、
実際 528 のうち **258件が private 由来**でした。リポジトリ名や内容は公開されず、マスの濃さだけが出ます。

## 学んだこと

技術的には「default branch を見ろ」で終わる話です。
ただ自分にとっては、**そこより後半のほうが学びでした。**

対策は3ヶ月前に立てていました。仕組みも理解していました。
それでも、**手動の定期作業に依存する対策は続かなかった**。

今回は設定を1つ変えるだけで、以後は勝手に記録されます。
「毎週やる」と決めるより、**やらなくても成立する形にする**ほうが確実でした。

自分の中では、こう置き直しています。

> 設定で解決できることを、運用の努力で解決しようとしない。

もし転職やポートフォリオでGitHubを見せる予定があるなら、
**一度プロフィールを開いて、実際の作業量と合っているか**を確かめてみてください。
自分は3ヶ月ぶん損していました。
