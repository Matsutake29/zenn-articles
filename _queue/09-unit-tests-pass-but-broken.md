以前、[テストはどこまで書けばいいのか、個人開発で見つけた3つの線引き](https://zenn.dev/matsutake_prgrm/articles/test-how-much-to-write)という記事を書きました。
エラーケースは理論上いくらでも増やせるので、どこで止めるかを決めた話です。

その線引きで書いたテストが**21本すべて通っている状態で、機能が壊れていました。**

線引きの問題ではなく、**単体テストという道具では見えない種類のバグ**でした。その構造が面白かったので書きます。

## 症状

バーベルのプレート計算アプリで、目標重量を増減する ± ボタンがあります。

在庫設定（どのプレートを持っているか）によって、挙動が3種類に分かれていました。

| 刻み | ＋を1回押す | −を1回押す | 判定 |
|---|---|---|---|
| 1kg | **3kg** 増える | 2kg 減る | 非対称 |
| 5kg | 5kg 増える | **0kg**（動かない） | −だけ効かない |
| 10kg | **0kg** | **0kg** | 両方効かない |

自分が最初に気づいたのは「10kg刻みだと ± が反応しない」でした。ここから調べていったら、刻みごとに別の症状が出てくる状態でした。

そして繰り返しますが、**テストは21本すべて通っています。**

## 原因: どちらの関数にもバグがない

コードは2つに分かれていました。

- `WeightInput` … ボタンが押されたら、常に **+2.5kg** した値を親に要求する
- `App` … 受け取った値を、**最寄りの刻みへ丸める**

単体で見ると、どちらも正しく動きます。

- 「+2.5kgを要求する」は仕様どおり
- 「最寄りの刻みに丸める」も仕様どおり

問題は組み合わせでした。

要求値が刻みのちょうど中間に落ちると、`Math.round` は常に切り上げます。**正の方向にしか働きません。**

具体的に追うと、こうなります。

```
刻み5kg・現在100kgのとき

＋: 100 + 2.5 = 102.5 → 丸め → 105  （5kg進む）
−: 100 - 2.5 =  97.5 → 丸め → 100  （元に戻る＝動かない）
```

＋は先へ進み、−は元の位置へ戻される。刻みが10kgになると、＋の2.5kgも丸めで吸収されて、両方動かなくなります。

## 本質: 責任がどこにも置かれていなかった

原因を追ったあとで、設計として何がまずかったのかを言語化しました。

> **「ボタンが何kg動くべきか」を決める責任が、どのファイルにも置かれていなかった**

丸め処理は「不正な入力を正す」ための仕組みです。「ボタンの移動量を決める」仕組みではありません。

なのに、実質そこに委ねていました。`WeightInput` は2.5kgという固定値を投げるだけで、実際にいくつ動くかは丸めの結果次第。
誰も決めていないので、誰のバグでもない。

**どちらにもバグがないのに、機能が壊れる。** この構造が、今回いちばんの学びでした。

## 直し方

増減幅を「**刻み1つ分**」にしました。

```ts
const step = getWeightStep(availablePlates)
onChange(value + step)   // ＋
onChange(value - step)   // −
```

刻みの整数倍で動かせば、丸めが手を出す余地がありません。押した分だけ確実に動いて、± が対称になります。

責任の置き場所も明確になりました。「1回押すといくつ動くか」は `WeightInput` が決める。
丸めは、手入力された半端な値を正すためだけに残る。

## テストも書き換えた

ここが今回の本題かもしれません。

元のテストは「関数が正しいか」を見ていました。

```ts
it('2.5kg単位で丸める', () => {
  expect(roundToStep(102.3, 2.5)).toBe(102.5)
})
```

これは通ります。関数は正しいので。

書き換えたのは、**性質が保たれるか**を見るテストです。

```ts
// 全在庫パターンでループして、性質を固定する
inventoryPatterns.forEach((plates) => {
  it(`${plates} で ± が対称に動く`, () => {
    const step = getWeightStep(plates)
    const start = 100

    expect(increment(start, step)).toBe(start + step)  // 押せば必ず動く
    expect(decrement(start, step)).toBe(start - step)
    expect(decrement(increment(start, step), step)).toBe(start)  // 往復で戻る
  })
})
```

見ているのは個々の値ではなく、

- **押せば必ず動く**
- **± が対称**
- **往復すると元に戻る**

という性質です。これを全在庫パターンでループさせました。

このテストがあれば、今回のバグは最初のパターンで落ちます。「10kg刻みで＋を押しても動かない」は「押せば必ず動く」に反するので。

## 学び

単体テストは「**部品が正しいか**」しか見ていません。

今回のような、**2つの正しい部品の組み合わせで壊れる**類のバグは、単体テストの視野の外にあります。落ちようがない。

捕まえる方法は2つだと思っています。

1. **性質ベースのテスト**（入力を変えても保たれるべき関係を書く）
2. **実機で操作する**

今回バグを見つけたのは2のほうでした。ブラウザで在庫設定を切り替えて触っていて、「あれ、動かないな」と気づいた。
テストを増やしても見つからなかったはずです。

テストをどこまで書くかの線引きは前の記事で決めました。
ただ**線引きの前に「そのテストは何を見ているのか」を分かっていないと、
通っていることが安心の根拠にならない**というのが、今回の実感です。
21本通っているのに壊れていたので。

## まとめ

- 単体で正しい2つの関数が、組み合わさって機能を壊すことがある
- 原因は「**その判断は誰の責任か**」が決まっていないこと
- 丸めは「不正な入力を正す」仕組みで、「移動量を決める」仕組みではない
- 「関数が正しいか」ではなく「**性質が保たれるか**」でテストを書くと捕まえられる
- 通っているテストの本数は、安心の根拠にならない
