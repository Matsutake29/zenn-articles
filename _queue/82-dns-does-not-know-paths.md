デプロイ先を決めるときに、自分でこう聞きました。

**「Aレコードを向けるのは `example.com/hubpin` じゃないの？」**

間違っています。
**DNS はパスを扱いません。**

当たり前だと言われそうですが、ここを勘違いしていると、移行の影響範囲の見積もりが丸ごとずれます。
実際、自分の最初の計画は危ないものでした。

## ブラウザは、名前しか聞いていない

`example.com/hubpin/` を開いたとき、何が起きているかを分解します。

1. ブラウザは **`example.com` だけ**を DNS に聞く。**パスは聞かない**
2. IP アドレスが返る
3. その IP のサーバーに TCP で繋ぐ（HTTPS なら TLS の握手で、どのホスト名に用があるかを伝える）
4. `GET /hubpin/` を送る。**パスを見るのはここが最初**

DNS が返すのは「その名前のサーバーはどこにあるか」だけです。
建物の住所は分かっても、**何号室に行くかは建物に入ってから決まります**。

だから DNS の設定画面に、パスを書く欄はありません。
自分は「Aレコードにパスを書くのだろう」と思って探していました。

## サブドメインは別の行で、サブディレクトリは中身

ここが分かると、移行で何が巻き込まれるかが決まります。

```text
DNS（住所録）
example.com          → 旧サーバー   ← この行を書き換える
blog.example.com     → 旧サーバー   ← 別の行なので影響なし
portfolio.example.com → 旧サーバー  ← 別の行なので影響なし
```

- **サブドメイン**（`blog.` `portfolio.`）は、住所録の**別の行**です。ルートの A レコードを変えても無傷
- **サブディレクトリ**（`/hubpin/`）は、そのホストの**中身**です。ホストごと引っ越すので道連れになる

当初の計画は「ルートの A レコードを新しいホスティングへ向ける」でした。
そうすると、同じドメインに置いてある `/plate-calculator/` と `/assets/` も一緒に移動先を向きます。
**移す気がなかったものが、全部 404 になる**計画でした。

`dig` で調べたら、ルートも `www` も `blog` も `portfolio` も、全部同じ IP を指していました。
**同じサーバーに同居しているが、DNS 上は別の行**です。
同居していることと、同じ行であることは違いました。

## パスで振り分けたいなら、それは別のレイヤーの仕事

「`/hubpin/` だけ別のサーバーへ送りたい」は、DNS ではできません。
やるとしたらリバースプロキシか rewrite です。

Vercel の `rewrites` は `destination` に外部の URL を書けるので、こちらで受けて別のところへ流すことはできます。
ただ、今回は逆方向（既存サーバーが手前）だったので使っていません。

## 調べたら、切り替える必要そのものが消えた

最終的に採った構成はこれです。

- **サブドメインを1つ追加する**（`hub.mt-tk.com`）
- **トップだけ `.htaccess` で 301 を返す**
- **A レコードは1本も触らない**

`dig` で現状を全部書き出したら、想像よりずっと軽い作業でした。
ネームサーバーも移していません。レンタルサーバーの DNS パネルに1行足しただけです。

`.htaccess` の書き方には気をつける必要がありました。

```apache
# トップだけを飛ばす
RewriteRule ^$ https://hub.example.com/ [R=301,L]
```

`^$` は空文字にマッチするので、ドキュメントルートだけが対象になります。
ここを `^` や `.*` にすると、**下層ページまで全部飛びます**。
サイトの全ページが1箇所へリダイレクトされる状態になるので、実際に外から `curl` を打って、トップだけが 301 で、下層は 200 のままであることを確認してから置きました。

ちなみに調べる過程で、既存の `.htaccess` にすでに `RewriteRule` が1本入っていることも分かりました。
数年前に自分で書いたもので、忘れていました。
**触る前に全部読む**のは、こういうものを見つけるためにも要ります。

## 戻すときの速さが、まるで違う

この構成にしたもう1つの理由は、ロールバックでした。

| 方法 | 戻し方 | 反映まで |
|---|---|---|
| A レコードを切り替える | 元の IP に戻す | **各リゾルバのキャッシュが TTL で切れるまで待つ** |
| `.htaccess` で 301 | 1行消す | サーバー側は即時 |

よく「DNS の浸透を待つ」と言いますが、正確ではありません。
**権威サーバーの値は書き換えた瞬間に変わっています。**
待っているのは、世界中のリゾルバが持っている古いキャッシュが、TTL のカウントダウンを終えるまでの時間です。

だから TTL を事前に下げておけば待ち時間は短くできます。
逆に言うと、TTL を下げずに切り替えると、その TTL のぶんだけ戻せません。

`.htaccess` の 301 なら、1行消せばサーバーはすぐ元の応答に戻ります。
ただしブラウザ側は 301 を強くキャッシュするので、**すでに踏んだ人の手元には残ります**。
サーバーが戻っていることと、全員が戻っていることは別でした。

## 一番の発見は、メールだった

調べていて一番ひやりとしたのは、**このドメインで仕事のメールが動いていた**ことです。

MX レコードが5本立っていて、Google のメールサーバーを指していました。
サブドメイン側にも MX があって、合計8本ありました。

今回の構成では、この MX に一度も触っていません。
MX が指しているのは Google 側のホスト名なので、**自分のサイトの A レコードを変えても、メールの経路には関係しない**からです。

ただ、これは「調べたから分かった」ことでした。
最初の計画どおり A レコードを触り始めていたら、DNS パネルの同じ画面で MX も並んでいます。
**作業中の画面に、壊してはいけないものが一緒に表示されている**状態でした。

「A レコード以外は触らない」を作業の鉄則にしたのは、このときからです。

## 怖さは、書き出すと手順になった

振り返ると、この作業で時間を使ったのは調べるところでした。
実際の変更は、DNS に1行足して、`.htaccess` に1行書いただけです。

**「DNS 切り替え」という言葉が重かった**だけで、中身は軽い作業でした。
`dig` で今の状態を全部書き出して、どれが何を指しているかを並べたら、触る行と触らない行がはっきりしました。

そして書き出した結果、**切り替える必要そのものが無くなりました**。
調べる前は「どう切り替えるか」の問題だと思っていたのが、調べたら「切り替えなくていい」が答えでした。
