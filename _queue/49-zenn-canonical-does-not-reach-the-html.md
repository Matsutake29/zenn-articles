:::message
自分のブログと Zenn の使い分けを決めるときに調べた話です。
**結論だけ先に書くと、Zenn 側から canonical を外部のURLに向けることはできませんでした。**
確認したのは 2026年8月時点の挙動です。
:::

## 同じ記事を両方に出したかった

書いた記事を、自分のブログと Zenn の両方に置きたいと考えていました。

読む人がどちらに来るかは選べません。
Zenn を見ている人もいれば、ブログの側から流れてくる人もいる。
だったら両方に出しておくのが親切だろう、と思ったわけです。

引っかかったのは検索エンジンの扱いでした。
同じ本文が2つのURLにあると、どちらを評価するかは検索エンジン側が決めることになります。
これを避けるための仕組みが `rel="canonical"` で、「正本はこちらです」と宣言できます。

やりたかったのはこの形です。

- 正本 → 自分のブログ
- Zenn → ミラー。canonical でブログを指す

## dev.to の感覚で設計していた

この形が成立するサービスを先に知っていました。dev.to です。

dev.to のエディタガイドには、front matter のキーとしてこう書かれています。

> **canonical_url:** link for the canonical version of the content

自分で書いた記事を dev.to にも流し、正本は自分のサイトに置く。
クロスポストの標準的なやり方として紹介されているのを何度か見ていたので、
**Zenn も同じだろうと思い込んでいました。**

## Zenn の frontmatter に canonical は無い

調べてみると、そもそも設定する場所がありませんでした。

Zenn CLI のガイドが挙げている frontmatter のキーは、この6つです。

| キー | 内容 |
|---|---|
| `title` | 記事のタイトル |
| `emoji` | アイキャッチ絵文字 |
| `type` | `tech` か `idea` |
| `topics` | タグの配列 |
| `published` | 公開するかどうか |
| `published_at` | 公開日時の指定 |

canonical に相当するキーは入っていません。

YAML なので書くこと自体は止められませんが、**知らないキーは読まれずに終わります。**
「書けるけど反映されない」ではなく、**受け取る口が用意されていない**、という状態でした。

### 文字列があっても、それが根拠とは限らなかった

ここで一度、自分で自分を引っかけています。

ローカルの `zenn-cli`（0.4.7）を `canonical_url` で検索したら、1件ヒットしました。
ビルド済みのバンドルの中です。**内部的にはサポートされているのかと思いました。**

前後を出してみたら、こういう並びの中にありました。

```
additional_checkout_buttons|address|all_country_option_tags|all_products|
articles??|block|blogs??|canonical_url|cart|checkout|collections??|...
```

Shopify Liquid のシンタックスハイライト用の変数リストでした。
コードブロックに色を付けるための文法定義が同梱されているだけで、
**Zenn の frontmatter とは何の関係もありません。**

grep のヒット数だけ見て「ある」と判断していたら、逆の結論を書くところでした。

## 公開されたHTMLを見に行った

仕様に無いことは分かりましたが、実際に出力されるHTMLも確認しておきます。
自分の公開済み記事を2本、そのまま取ってきました。

```bash
curl -s https://zenn.dev/matsutake_prgrm/articles/unit-tests-pass-but-broken \
  | grep -o '<link[^>]*rel="canonical"[^>]*>'
```

返ってきたのはこれです。

```html
<link rel="canonical" href="https://zenn.dev/matsutake_prgrm/articles/unit-tests-pass-but-broken"/>
```

もう1本も同じで、**canonical は Zenn 自身のURLで固定されていました。**

つまり Zenn の記事は、常に「この記事の正本は Zenn にある」と宣言している状態です。
ここを外部に向ける手段は、少なくとも記事側からは見つかりませんでした。

## 制約が1つ決まると、決めることが1つ減る

分かったのは「1記事につき媒体は1つしか選べない」ということでした。

両方に出せば重複コンテンツになり、どちらが拾われるかは検索エンジン任せになります。
片方に決めれば、その心配は最初から発生しません。

最初は選択肢が減ったと感じたのですが、実際には楽になりました。
**「どちらに出すか」を毎回決めればよくなった**からです。
転載の設計を考える必要が消えて、振り分けの基準を作るほうに時間を使えるようになりました。

自分の場合はこう分けています。

| 記事の性質 | 出す先 |
|---|---|
| 単独で完結する技術メモ。検索から来る人向け | Zenn |
| 前後の記事を続けて読むと価値が増すもの | 自分のブログ |

後者をブログに置いているのは、品質で分けているからではありません。
**Zenn は投稿のペースに制限があるので、続きものが日をまたいで分断されます。**
5回に分けた記事の3回目だけを読んだ人は、たぶん前後まで追ってくれません。

自分のブログなら固定ページから古い順に並べて、まとめて読ませられます。
記事の中身ではなく、**器の向き不向きで決めた**という感覚に近いです。

## 仕様としては妥当だと思う

書きながら「不便だ」と何度か思ったのですが、立場を変えると理解できます。

投稿する側が canonical を自由に指定できるとしたら、
他人の記事を転載して正本を自分のサイトに向ける、といったことが成立してしまいます。
ユーザーが記事を投稿する形のサービスで、その口を開けておく理由はあまりなさそうです。

自分が想定していた使い方が、たまたま少数派だっただけでした。

## 持ち帰り

- Zenn の frontmatter に canonical に相当するキーは無い。公開HTMLの canonical は Zenn 自身を指す（2026年8月時点）
- dev.to は `canonical_url` を公式にサポートしている。**同じつもりで設計すると外す**
- grep のヒット数は根拠にならなかった。同梱されている別の文法定義を拾っていた
- 制約が確定すると、その先で迷わなくなる。転載の設計を捨てたぶん、振り分けの基準を作れた
