日時から9時間引いた値を作りたくて、GNU date にこう書きました。

```bash
g=$(date -d "$d -9 hours" '+%Y-%m-%d %H:%M:%S')
```

1本を手で計算して動作確認したときは正しかったのですが、同じ処理をループにして14件に流したら、**引かれるどころか19時間足されていました**。

## 起きたこと

やりたかったのは、`2026-08-13 20:00:00`（JST）から9時間引いて `2026-08-13 11:00:00`（UTC）を得ることです。

```text
入力: 2026-08-13 20:00:00
出力: 2026-08-14 15:00:00    ← 19時間「増えて」いる
```

エラーは出ません。もっともらしい日時が返ってきます。

## `-9` がタイムゾーンとして読まれていた

GNU date の日時文字列では、**符号付きの数値がタイムゾーン（UTC オフセット）として解釈されます**。`-9` は UTC−09:00 です。

つまり date はこう読んでいました。

1. `2026-08-13 20:00:00 -9` → 「UTC−9 での 20:00」＝ UTC では `2026-08-14 05:00:00`
2. 出力はローカル時刻（JST）なので `2026-08-14 14:00:00`（ここで +18時間）
3. 残った `hours` は数値の付かない相対指定で、**`hours` 単体は「+1 hour」**
4. 合計 +19時間 → `2026-08-14 15:00:00`

3 が自分には意外でした。`-9` をタイムゾーンに取られたあと、余った `hours` が独立した「1時間足す」になっています。

## 再現

GNU coreutils 8.22 で、要素を1つずつ変えて確かめました。

```text
入力（TZ=Asia/Tokyo）                    出力
"2026-08-13 20:00:00 -9 hours"     → 2026-08-14 15:00:00   （+19h）
"2026-08-13 20:00:00 -9"           → 2026-08-14 14:00:00   （+18h。-9 だけでタイムゾーン）
"2026-08-13 20:00:00 hours"        → 2026-08-13 21:00:00   （+1h。裸の hours）
"2026-08-13 20:00:00 -9 2 hours"   → 2026-08-14 16:00:00   （+18h +2h）
"2026-08-13 20:00:00 9 hours ago"  → 2026-08-13 11:00:00   （意図どおり）
```

`-9` 単体と `-9 hours` の差がちょうど1時間で、裸の `hours` 単体も +1時間。3行目まで並べて、やっと自分の中で辻褄が合いました。

## 正しい書き方

```bash
# 1. ago を使う（符号を使わない）
date -d "$d 9 hours ago" '+%Y-%m-%d %H:%M:%S'

# 2. タイムゾーン変換として明示する
TZ=UTC date -d "$d JST" '+%Y-%m-%d %H:%M:%S'

# 3. そもそも計算しない（値を直接渡す）
```

自分は最終的に **3番** で処理しました。14件しかなく、一度壊したあとで「計算するコード」をもう一度信用する判断ができなかったためです。

## 1本で検証した手順が、ループに移した瞬間に別物になっていた

これが自分にとっての本題でした。

最初の1本は、**手で計算した値を直接渡して**動作確認していました。そこで確認できたのは「両方の引数を渡せば直る」ことだけで、**「9時間をどう計算するか」は検証の範囲に入っていませんでした**。

- 検証したのは手順の一部で、一括実行するコードは初回実行だった
- 差分は `date` の1行だけ。動いた部分が9割あると、残り1割も動く気になる
- しかも `date` はエラーを返さない。もっともらしい日時を返してくる

何のデータを壊したかは別の記事に書いていますが、背景だけ言うと WordPress の予約投稿の GMT 値でした。壊れた14件は値を直接書いて直しています。

日付計算は、**エラーにならずに間違う**のがいちばん厄介でした。仕様であってバグではないので、GNU date が悪いという話ではありません。ただ、「動いた1本」と「流す14件」の間にある差分を、自分は数えていなかった。
