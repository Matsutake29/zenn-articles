デザインカンプが1920px幅で来る受託案件で、PCの中間幅（1280〜1919px）の可変対応をどうするかという話です。

これまでは中間幅用のブレイクポイントを足して個別に調整していました。
今回は**全プロパティを同じ式に統一する**方針で組んだら、SCSSの見通しがかなり良くなったので書き残します。

## 使った式

これひとつです。

```scss
// VAL = カンプ上の値、MIN = 縮小時の下限
property: clamp(MIN, calc(VAL / 1920 * 100vw), VAL);
```

カンプの基準幅（1920px）を分母に置いて、ビューポート幅に対する比率で縮めます。上限はカンプの値、下限は自分で決めた最小値。

実際に書くとこうなります。

```scss
.p-hero {
  padding-top: clamp(120px, calc(408 / 1920 * 100vw), 408px);
  gap: clamp(60px, calc(280 / 1920 * 100vw), 280px);

  &__title {
    font-size: clamp(40px, calc(80 / 1920 * 100vw), 80px);
  }

  &__subtitle {
    font-size: clamp(15px, calc(24 / 1920 * 100vw), 24px);
  }
}
```

**式の形が全部同じ**なので、読むときに考えなくて済みます。数字だけ見れば「カンプで80px、下限40px」と分かる。

## なぜブレイクポイントを足さなかったか

中間幅用に `@media (max-width: 1600px)` を足して個別調整する方法もあります。実際、これまではそうしていました。

比例スケールにした理由は3つです。

1. **書く量が少ない**。ブレイクポイントを足すと、そこで調整したい全プロパティを書き直すことになる
2. **中間の全幅で成立する**。ブレイクポイントは境界で段差ができるので、1500pxで見たときの見え方は「調整していない状態」になりがち
3. **他案件に転用できる**。式が同じなので、次の案件でカンプ幅だけ変えれば動く

3つ目が地味に大きくて、この案件で作ったパターンをそのまま次に持っていけました。

## clamp と min() の使い分け

実装中にいちばん迷ったのがこれです。同じ「可変」でも、下限を守りたいのか上限だけ抑えたいのかで関数が変わります。

| 何をしたいか | 使う関数 | 例 |
|---|---|---|
| **下限を確保したい** | `clamp()` | `font-size`。小さくなりすぎると読めない |
| **上限だけ制約したい** | `min()` | grid の列幅。vw比率で自然に縮小させたい |

```scss
// 文字は下限を守る
font-size: clamp(15px, calc(24 / 1920 * 100vw), 24px);

// 列幅は上限だけ決めて、あとは比率に任せる
grid-template-columns:
  min(830px, calc(830 / 1920 * 100vw))
  min(923px, calc(923 / 1920 * 100vw));
```

毎回どちらか迷っていたのですが、こう整理したら迷わなくなりました。
**「読めなくなると困るもの」は `clamp`、「小さくなる分には困らないもの」は `min()`。**

ちなみに列幅で `clamp` を使いたい場面もあります。
写真の列が中間幅で潰れすぎたときの話です。
`clamp(220px, calc(630 / 1920 * 100vw), 630px)` にしました。
**下限が要るかどうか**だけが判断基準です。

## 上下マージンは固定のままにした

全部を可変にはしませんでした。**セクションの上下padding（縦方向）は固定**です。

理由は2つあります。

- 縦方向はカンプとのズレが目立ちにくい代わりに、**比例させると意図と違う結果になりやすい**
- 縦の余白は**コンテンツ量に依存する**。文章が3行か10行かで見え方が変わるので、幅に比例させる根拠が弱い

横方向とフォントサイズだけを可変にして、縦は固定。「全部可変にすればいい」わけではない、というのが今回の判断でした。

## 既存サイトの問題に scope 限定で対処する

もうひとつ、判断が必要だった場面があります。

担当範囲の外に、既知の横スクロール問題がありました。サイト共通のフッターのレイアウトがビューポートを超える、というものです。
既存サイト全体の問題で、自分の担当ページ以外でも起きています。

**根治しない、担当スコープ内だけで封じる**という判断をしました。

```scss
body.is-{scope} .{該当クラス} {
  flex-wrap: wrap;
}
```

理由はこうです。

- 全体を直すと、**他ページ全部の検証工数**が発生する。納期に影響する
- `body` のスコープクラスで限定すれば、他ページへの影響はゼロ
- 引き継ぎ時に「ここだけ対処した」と説明できる

実装としては `overflow-x: clip` も検討しましたが、`flex-wrap: wrap` にしました。
**中身が見えなくなるのではなく、折り返して見える**ほうが正攻法だからです。clipは症状を隠すだけで、内容が切れます。

制作会社経由の案件で「どこまで直すか」は毎回悩むところです。
**直せることと直すべきことは別**で、スコープ外に手を出すと、その責任も一緒に引き取ることになります。
今回は「見えている問題を、自分の範囲で無害化する」に留めました。

## やってみて思ったこと

比例スケールは万能ではありません。

- **カンプに基準幅がある前提**です。デザイナーが複数幅でカンプを作っている場合は、素直にそちらに合わせるべきです
- 極端に縮めると、要素同士の関係（余白と文字の比率）が崩れる場面はあります。下限の設定でカバーしていますが、下限を決めるのは結局目視です

それでも、**式の形が統一されていること自体の価値**が思ったより大きかったです。
コードを読む負荷が下がると、後から触るときの心理的なハードルが下がるので。

## まとめ

- `clamp(MIN, calc(VAL / 基準幅 * 100vw), VAL)` の形に統一すると、読む負荷が下がる
- 中間幅専用のブレイクポイントより、**コード量が少なく保守しやすい**
- **下限を守りたいものは `clamp`、上限だけ抑えたいものは `min()`**
- **縦方向は固定でいい**。コンテンツ量に依存するので比例させる根拠が弱い
- スコープ外の既存問題は、`body` のスコープクラスで**無害化に留める**
