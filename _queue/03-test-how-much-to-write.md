Vitestで基本のテストを4パターン書き終えたとき、ふと手が止まりました。

「エラーケースって、理論上いくらでも増やせるよな」と。

入力値を変えれば無限にパターンは作れます。でも全部書くわけにはいかない。
じゃあどこで止めればいいのか。
個人開発でアプリを作りながら考えたことをまとめます。

:::message
パワーリフティング向けのプレート計算アプリを作っています。
目標の重量に対して、バーの片側に何kgのプレートを何枚つければいいかを計算するWebアプリです。

公式大会では装着する構成が自動で表示されるのですが、これが普段の練習でもスマホで見られたら便利だなと思って作りはじめました。

- リポジトリ: https://github.com/Matsutake29/plate-calculator
- Vite + React + TypeScript + Tailwind CSS

## テストを自分で書く方式に切り替えた

前提として、このプロジェクトではAIとペアを組んでいます。

計算ロジックの実装はAIと組んで進めたのですが、書き上がったコードを見て「やりたいことは理解できる。
でも自分ひとりではここまで書けない」という状態になりました。読めば分かるが、書けない。

その葛藤をそのままAIに話したところ、返ってきたのが「読む(触れる)のではなく、書く(自分で生産する)ことが本当の処方箋」という指摘でした。

それで次の工程であるテスト実装は、**自分で書いてAIにレビューしてもらう**方式に切り替えました。
AIはテストケースのたたき台を出す役と、レビュー役に徹してもらう形です。

このとき判断基準も置き換えました。
「TypeScriptの文法を完全に知っているか」ではなく、**「面接でこのコードを説明・弁護できるか」**を基準にすると。
知識の網羅ではなく、説明責任を持てるかどうか。

## 書いてみて初めて身についたこと

読んでいたときは分かった気になっていて、書いたら詰まったものが3つありました。

### `it` と `test` の違い

結論から言うと**同じもの**です。エイリアスなので、どちらを使っても動きます。

読んでいるときは「使い分けのルールがあるんだろうな」と勝手に思っていました。
自分で書くときに調べて、初めてスッキリしました。

### `toBe` と `toEqual` の使い分け

- `toBe` … 参照・値の厳密一致(`Object.is`相当)
- `toEqual` … 中身の再帰的な比較

オブジェクトや配列を比べるときに `toBe` を使うと、中身が同じでも参照が違うので落ちます。
これも「読む」だけでは素通りしていた部分でした。

### 判別可能Unionの絞り込みが1段階では足りない

いちばん詰まったのがこれです。

計算結果の型を判別可能Union(Discriminated Union)で定義していました。
`ok: true` と `ok: false` があり、さらに `ok: false` の中に `reason` の違いで2パターンある、という構造です。

```ts
type Result =
  | { ok: true; breakdown: Plate[]; shortfall: number }
  | { ok: false; reason: "targetBelowMinimum"; minimum: number }
  | { ok: false; reason: "invalidInput" }
```

`if (result.ok === false)` で絞り込んだつもりでも、その中ではまだ2パターンが残っています。
`minimum` にアクセスしようとすると型エラーになる。
入れ子のif文で `reason` まで見て、ようやく絞り込みが完了する。

型エラーのメッセージを読みながら自力で解決したのですが、**これは自分で書かなければ絶対に出会えなかったエラー**でした。
AIが書いたコードを読んでいるだけなら、最初から正しく絞り込まれた完成形しか見ていないので。

型の定義とテストの実物はこちらです。

- 型定義: [src/lib/calculatePlates.ts](https://github.com/Matsutake29/plate-calculator/blob/main/src/lib/calculatePlates.ts)
- テスト: [src/lib/calculatePlates.test.ts](https://github.com/Matsutake29/plate-calculator/blob/main/src/lib/calculatePlates.test.ts)

## どこまで書くか、3つの線引き

冒頭の「無限に増やせる問題」に戻ります。
整理して、この3点に落ち着きました。

### 1. 型(Union型)のパターンを最低1回ずつ通す

判別可能Unionで4パターンを定義したなら、4パターンすべてを最低1回は通す。
型で表現した状態は、実際に到達できることを確認しておく。

### 2. 境界値を押さえる

最小値・最大値・その前後。プレート計算なら「バーだけの重量(最低重量)」「それを下回る入力」あたりです。

### 3. 実装上の罠を狙い撃ちする

今回で言うと、浮動小数点の誤差対策と、貪欲法(greedy)の限界です。

プレートの組み合わせを貪欲法で計算していると、大きいプレートから順に取っていった結果、端数が埋まらないケースが出ます。
アルゴリズムの性質上そうなると分かっている場所は、意図的に狙って書く。

### つまり、テストの目的は網羅ではない

3つを整理して言語化できたのは、**「テストの目的は入力パターンを全部試すことではなく、実装の正しさに自信を持てる最低限の根拠を揃えること」**でした。

そしてこの「最低限」の基準は、領域によって全く違います。
医療・金融のようなミッションクリティカルな領域と、個人開発・ポートフォリオでは、要求されるラインがそもそも別物です。
「テストはどこまで書くべきか」に唯一の正解がないのは、たぶんここが理由です。

## AIのたたき台をそのまま受け取らない

発展的なテストケースは、AIにたたき台を出してもらいました。
ただ、レビューする段で2箇所、一歩踏み込んで直しています。

### ベタ書き配列を実装側の定数に置き換えた

たたき台では、テスト内で `availablePlates` の配列がベタ書きされていました。
実装側には `PLATE_WEIGHTS` という定数がすでにエクスポートされていたので、そちらを参照する形に置き換えました。

プレートのラインナップが将来変わったとき、テスト側を直さなくて済みます。

### 「起きないこと」の確認を「起きた結果どうなるか」まで伸ばした

「小さいプレートをオフにしたときの確認」というケースが、当初は**breakdownに小プレートが出てこないこと**だけを見る内容でした。

これを、目標重量を143kgに調整して、**0.25kg単位の端数を埋める手段がなくなり、shortfall(不足分)に正しく反映されるところまで**確認する内容に発展させました。

ここで言語化できたのが、**「起きないこと」の確認だけでなく「起きた結果どうなるか」まで見ると、保証が一段強くなる**ということです。

小プレートが出てこないのは当たり前として、その結果として計算が破綻せず、不足分として正しく表現されるか。
そこまで見て初めて、この機能を信頼できる状態になります。

## まとめ

- テストを自分で書くと、読んでいるだけでは出会えないエラーに当たれる
- 判断基準は「文法を知っているか」ではなく「説明・弁護できるか」
- どこまで書くかの線引きは、型パターン・境界値・実装上の罠の3点
- 目的は網羅ではなく、自信を持てる最低限の根拠を揃えること
- AIのたたき台は受け取って終わりにせず、一歩踏み込む余地がある

まだテストを書き始めたばかりなので、この線引き自体も今後変わっていくと思います。現時点での自分なりの整理として。

同じプロジェクトで「テストは自分で書き、UIはAIに任せた」という体制の使い分けについても別途書いています。あわせてどうぞ。
