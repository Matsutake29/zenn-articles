:::message
2作目のポートフォリオとして「Hubpin」（分散した発信を1か所に集めるハブサイト）を作りながら書いています。

- リポジトリ: https://github.com/Matsutake29/hubpin
- Next.js（App Router） + Supabase + Tailwind CSS

外部サービスの投稿を取得して一覧に出す機能を考えていたとき、最初に出た懸念がこれでした。

**「面談当日にエラーで見れませんとかなったら困る」**

転職用のポートフォリオなので、人に見せている最中に落ちるのが一番困ります。
外部 API は仕様が変わるし、有料化もするし、止まることもある。
自分では直せません。

ただ、この懸念は設計で消せる種類のものでした。

## 取得と表示を切り離す

やったことは1つだけです。
**ページを開いたときに外部を叩くのをやめました。**

```text
❌ ページを開く → その場で外部APIを叩く → 表示
   （外部が落ちたらページが壊れる）

⭕️ 日次のCron → 外部APIを叩く → DBに保存
   ページを開く → DBから読む
   （外部が落ちても、前回取れたデータが出続ける）
```

外部が落ちている間に表示されるのは古いデータですが、**何も出ないよりは古いほうがいい**という判断です。
ページが壊れないことのほうが優先でした。

ここで気づいたのは、キャッシュと保存が別物だということでした。
キャッシュは切れたら取り直しに行きます。
取り直しに失敗すれば、そこで壊れる。
**取り直しに行かない置き場が要る**ので、DB のテーブルに入れています。

## 「取れなかった」を「0件だった」に変換しない

設計で一番効いたのがここでした。

外部から取得する関数が**空の配列を返すと、保存側は「成功して0件だった」と読みます**。
そして既存のデータを全部消します。
外部が落ちた瞬間に、手元のデータまで消える。

この変換が起きる場所が3つありました。
3つとも塞いでいます。

**1つ目。未対応の媒体が来たとき、空配列を返さない。**

```ts
// src/lib/feed/index.ts
switch (source.provider) {
  case 'wordpress': return fetchWordPress(...)
  case 'zenn':      return fetchZenn(...)
  case 'github':    return fetchGitHub(...)

  // 🚨 空配列を返さない。保存側が「0件で成功」と解釈して、既存のエントリーを全部消す。
  default:
    throw new Error(`未実装、または不明な provider: ${source.provider}`)
}
```

`default` で空配列を返すのは、書いている最中は自然に見えます。
後から media を足すときに、一時的にそうしたくなる場所でもあります。

**2つ目。フォールバック先のレスポンスで `ok` を見る。**

```ts
// 🚨 ok を見ないと、404 の HTML をパースして空配列になる。
if (!fallbackRes.ok) {
  throw new Error(`フォールバックも失敗: ${fallbackRes.status}`)
}
```

404 のページも中身は HTML なので、RSS のパーサーに食わせると**エラーにならずに0件で返ってきます**。
ここが一番気づきにくい経路でした。

**3つ目。保存の直前でもう一度見る。**

```ts
// src/app/api/feeds/refresh/route.ts
// 🚨 0件で replace すると既存のエントリーが全部消える。
//    「取れなかった」を「0件だった」に変換しない。
if (entries.length === 0) {
  throw new Error('取得は成功したが0件だった')
}
```

同じことを3回書いているように見えますが、**通る経路が違います**。
1つ目は分岐漏れ、2つ目は他所のサーバーの応答、3つ目は最後の砦です。

失敗したときは、既存のデータに触らず `last_status` だけを `failure` に更新します。
データはそのまま、状態だけが変わる形です。

## REST が塞がれていたら RSS に降りる

WordPress の取得だけ、経路を2本持っています。
REST API が使えなければ RSS を読みます。

これは実務から来た判断でした。
**他人が管理している WordPress は、セキュリティプラグインで `/wp-json/` を塞いでいることがあります。** 受託で何度か見ています。
閉じているサイトのほうが少数派ですが、閉じていたら REST 側は何も返しません。

一方 RSS は、WordPress なら標準で出ています。
塞ぐ理由もあまりありません。
だから**取れる確率の高い経路を2本目に置く**構成にしました。

ただし、フォールバック先が無い媒体もあります。
GitHub には RSS がありません。

```ts
// 🚨 フォールバック先が無い媒体もある（GitHub には RSS が無い）。
//    null は「設定漏れ」ではなく「そういう媒体」。取得失敗として投げる。
if (!fallback) {
  throw new Error(`WP REST が ${res.status} で、フォールバック先も無い`)
}
```

`null` を「まだ設定していない」と読むと、埋めようとしてしまいます。
**そこに入れるものが存在しない**という意味なので、コメントに書いておきました。

## 媒体ごとの形を、1つの型に寄せる

取ってくる形が媒体ごとに違います。
WordPress は REST の JSON、Zenn は RSS の XML、GitHub は REST の別スキーマ。
そのまま扱うと、画面側が3種類の形を知ることになります。

間に1つ型を置きました。

```ts
export type NormalizedEntry = {
  title: string
  url: string
  published_at: string | null
  thumbnail_url: string | null
}
```

4つだけです。
媒体を足すときに書くのは、その媒体の応答をこの形に直す関数1つになります。

並べ替えと件数の絞り込みは、アダプター側に書いていません。

```ts
// 🚨 並べ替えと件数の保証はここ1箇所だけ。アダプター側には書かない。
//    ⚠️ 媒体ごとに書くと、書き忘れても型は通る。しかも Zenn は新しい順で返るので
//       画面を見ても気づけない（壊れるのは WP のフォールバック経路だけ）。
export function sortAndTake(entries: NormalizedEntry[], max: number) { ... }
```

書き忘れても型が通る処理は、**書く場所を1つに決めておかないと検出できません**。
しかも今回は、たまたま正しい順で返ってくる媒体があるので、画面を見ても分かりません。

## 最終取得日時を出す

画面に「最終取得: 9月11日 18:59」を出しています。

外部が落ちている間も表示は残る設計なので、**その表示がいつのものか分からないと不誠実**だと思ったからです。
数日前の日付が出ていれば、見る人は「今は取れていないんだな」と分かります。

落ちていることを隠すより、落ちても表示が残って、いつのものか書いてあるほうがいい。
そういう置き方にしました。

## 壊れたときにどうなるかを決めてから作った

書き終えて思ったのは、やったのは**難しい実装ではなく、置き場所を決めただけ**だということでした。

取得と表示を切り離す。
落ちたら古いデータを残す。
取れなかったを0件に変換しない。
どれも実装量としては数行です。
決めていなかったら、全部逆の挙動になっていました。

外部に依存する機能で怖いのは、落ちること自体より**落ちたときの挙動を決めていないこと**でした。
決めないと、フレームワークとライブラリの既定の挙動がそのまま出ます。
今回の場合、それは「全部消える」でした。
