Supabase で RLS（行レベルセキュリティ）を使っていて、ポリシーが効いているかを確かめる SQL を1つのファイルにまとめて運用しています。公開したあとにセキュリティ修正を入れたので、壊していないかをそのファイルで確認しました。

そのとき、確かめたかった結果が画面に出ていないことに気づきました。ツールは正しく動いています。ただ、検証という文脈を知らないだけでした。

## 前提: 「エラーになること」が期待値の検証がある

RLS の確認は、通ることを見るだけでは足りません。通らないことを見る検証が要ります。

```sql
-- 未認証ロールが insert できないことの確認
set local role anon;
insert into public.items (...) values (...);
-- 期待: ERROR 42501
```

このファイルには、そういう「エラーが正解」の項目がいくつか入っています。ここが最後の対策に効いてきます。

## SQL Editor は最後の SELECT しか表示しない

未認証から非公開カードが見えないことを確かめる項目で、こう書いていました。

```sql
begin;
  update public.items set visible = false where title = 'Zenn';

  set local role anon;
  select count(*) from public.items;   -- 主目的

  set local role authenticated;
  set local "request.jwt.claims" = '…';
  select count(*) from public.items;   -- 対照実験
rollback;
```

1ブロックに SELECT が2つあります。**画面に出たのは1つだけでした**（2026-08-17 に実行したときの挙動です。ドキュメントで裏を取ったわけではなく、手元で観測した範囲の話として書いています）。

しかも出たのは**後ろの対照実験のほう**で、主目的である「未認証から見えないこと」の値は表示されていません。分割して実行して、初めて出ました。

- 本人ロール（画面に出たほう）: **7**
- 未認証ロール（出なかったほう）: **10**（全11件のうち、非公開にした1枚が隠れている）

エラーは出ません。表示された 7 も正しい値です。ただ、確かめたかった側が画面に無い。「1つ足りない」ことに気づく手がかりがどこにもありませんでした。

なお、この検証は数週間前に書いたもので、期待値も2つ並べて書いてあります。**当時それが実際に画面に出ていたのかは分かりません**（分割して実行していた可能性もあります）。言えるのは、原本のまま流したら出なかった、ということだけです。

### 直し方は2つあった

1つ目は、1ブロックに「見たい結果」を2つ入れないこと。対照実験は隣のブロックへ分けました。

2つ目は、1回の表示で壊れ方を区別できるようにすること。これは分割とは別の話です。

```sql
select
  count(*)                               as 見える総数,
  count(*) filter (where title = 'Zenn') as 対象が見える数
from public.items;
```

分割しただけだと、未認証の件数が減ったとき「非公開が効いた」のか「そもそも読めなくなった」のかを1つの数字で区別できません。2列にすると、`見える総数` が 0 なら読めていない、`対象が見える数` が 1 なら非公開が効いていない、と切り分けられます。

件数を直接の期待値にしていないので、データが増えても書き換えずに済みます。

## 「エラーが正解」の項目では、HINT が逆を向く

同じ日に流した「未認証ロールが `insert` できないこと」の項目では、期待どおり `ERROR 42501` で弾かれ、HINT に `GRANT INSERT ON public.items TO anon;` が出ました。画面には「Debug with Assistant」ボタンも並びます。

この HINT に従うと「未ログインの誰でも書き込めるサイト」になる話は、[以前ブログに書きました](https://blog.mt-tk.com/grant-comes-before-rls/)。検証ファイルの中では、弾かれるのが正解なので、HINT はいつも逆を向いています。

## ツールは間違っていなかった

最後の SELECT だけ返すのは、SQL Editor の正常な動作です。HINT も、権限が足りないという事実に対しては正確です。

どちらも**ツールは間違っていません**。見る場所も間違えていませんでした。それでも、画面から受け取った次の一手が誤る形になっています。

「実物を見る」「出どころを確かめる」で防げるタイプではなかった、というのが今回いちばん残ったところです。

## 検証ファイル自身に書いた

対策としては、検証ファイルの冒頭にコメントを置きました。

```sql
-- 🚨 「ERROR が期待値」の検証がある。エラーは成功の合図。
--    SQL Editor は 42501 に対して GRANT を足す HINT を出し、
--    「Debug with Assistant」も並ぶが、どちらにも従わないこと。
--    HINT は権限が足りない事実から生成されるだけで、
--    その拒否が意図されたものかを知らない。
```

検証ファイルは何度も流します。1回読んで分かっても、**次に流すときの自分は初見**なので、ファイル側に書いておくのが確実でした。

分割のほうにも同じことをしています。

```sql
-- 🚨 1本にまとめないこと。SQL Editor は最後の SELECT しか表示しない
```

こう書いておかないと、次に整理するときに「同じトランザクションなんだから1つにまとめよう」と考えて、静かに元へ戻ってしまいそうだったからです。
