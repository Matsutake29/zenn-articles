DB 側（RLS）で「非公開カードは未認証から見えない」と絞っているところに、アプリ側でももう一度絞りました。

```ts:src/app/[username]/page.tsx
    .eq('user_id', profile.id)
    // RLS（to anon using (visible = true)）でも絞られるが、ここでも絞る。
    // 以前 PERMISSIVE の OR 結合で非公開カードが漏れた場所で、
    // ポリシーを1本触るだけで再発する。
    .eq('visible', true)
```

多層防御です。1行足しただけで、判断としては順当だと思っていました。

足した瞬間に、**RLS が壊れても症状が出なくなった**、というのが今回の話です。

## 「非公開カードが出ていない」は証拠にならない

足す前は、公開ページに非公開カードが出ていなければ、RLS が効いている証拠でした。

足した後は違います。**アプリ側のフィルタが効いているだけかもしれない。** 公開ページを見ても、どちらが効いているのかを区別できません。

| 見る場所 | RLS が効いているか分かるか |
|---|---|
| 公開ページ | **分からない** |
| RLS を直接叩く検証 SQL | **これだけ** |

自分は RLS の動作確認を SQL ファイルにまとめていて、その中に「未認証ロールから `visible = false` が見えないこと」を直接測る項目があります。この1本の位置づけが、**「動作確認」から「唯一の測定経路」に変わりました**。

## 「足す前に1枚目を確認しよう」では足りなかった

多層防御でよく言われるのは、2枚目を足す前に1枚目が効いていることを確かめよう、という順序の話です。

実際そうしました。RLS が効いていることを測った直後に `.eq` を足しています。順番は正しかった。

それでも足りませんでした。

| | 言えること |
|---|---|
| 1回の確認 | **足す瞬間に効いていたこと**しか言えない |
| 継続的な測定経路 | **足した後も、いつでも1枚目を単独で見られる** |

1回確認して足す、では「足した瞬間」の保証にしかなりません。その後にポリシーを1本触って壊れたとき、2枚目が隠すので誰も気づかない。**「1枚目を測ってから2枚目を足す」だけでは足りず、「1枚目を測り続けられる経路を残してから2枚目を足す」**が必要でした。

今回はたまたま検証 SQL が先にあったから、足せました。無ければ、測定経路ごと失っていたことになります。

## 層を足すと、その下の層の故障が観測不能になる

一般化するとこうなりました。**多層防御の代償は「冗長なコード」ではなく「観測性」**。

2枚とも効いていれば安全ですが、「2枚ある」ことと「2枚とも効いている」ことは別です。そして2枚目がある限り、1枚目が効いているかを表から見る手段はありません。

## 検証ファイル自身に書いた

対策は、検証 SQL の該当項目にコメントを置くことでした。

```sql
-- 🚨 これは「動作確認」ではなく「RLS を直接測る唯一の経路」。
--    アプリ側にも同じ絞り込みがあるため、画面を見ても区別できない。
--    ここを消すと、RLS が壊れても症状が出ないまま気づけなくなる。
```

「消すと何が起きるか」を書いたのは、**次に触る人にはこれが単なる重複チェックに見える**からです。アプリ側でも絞っているなら、こちらは要らないのでは、と整理したくなる。その判断を止めるには、ファイル側に理由が要りました。

## 全部に二重で置いたわけではない

もう1つ、判断として書いておきます。二重に絞ったのは**公開ページだけ**です。

管理画面側には置いていません。本人しか見ないので、RLS に任せています。公開ページだけ例外にしたのは、失敗したときの被害が「非公開データの公開」だからでした。置く場所は「失敗したときの被害」で決めました。全部に二重で置く形は取っていません。

二重にするかどうかの是非は、ここでは扱っていません。自分が持ち帰ったのは、**足した後に何が見えなくなるか**のほうでした。

環境: Supabase（PostgreSQL）/ Next.js 16.3.0 / @supabase/supabase-js 2.112.1。
