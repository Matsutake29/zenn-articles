ダッシュボードに「最終取得: 9月11日 18:59」という表示を足しました。

`npm run dev` で確認したら 18:59 でした。
**合っています。ここで終われます。**

終わらせていたら、本番で9時間ずれていました。

## `timeZone` を省くと、実行環境のタイムゾーンになる

日時の整形に `toLocaleString` を使っています。

```ts
new Date(value).toLocaleString('ja-JP', {
  timeZone: 'Asia/Tokyo',   // ← これを省くと、実行環境のタイムゾーンで整形される
  month: 'numeric',
  day: 'numeric',
  hour: '2-digit',
  minute: '2-digit',
})
```

`'ja-JP'` は**言語と表記の指定**であって、タイムゾーンの指定ではありません。
`timeZone` を省くと、そのコードを実行している環境のタイムゾーンが使われます。

- 開発機は JST なので、**正しく見える**
- Vercel のサーバーは UTC なので、**9時間ずれる**

厄介なのは、手元では絶対に再現しないことです。
**ローカルでの確認が、構造的に通用しない箇所**でした。

## 本番の条件をローカルに作る

Node はプロセスのタイムゾーンを `TZ` 環境変数で決めます。
本番と同じ条件を手元に作れます。

```bash
TZ=UTC npm run dev
```

これで開いたら、表示は **18:59 のまま**でした。
`timeZone: 'Asia/Tokyo'` が効いているので、実行環境が UTC でも JST で整形されています。

ここで終わりにできそうでした。

## ここで止めると、確かめたことにならない

「18:59 のままだった」が根拠になるのは、**`TZ=UTC` が実際に効いているとき**だけです。

効いていなかったら何が起きるか。
実行環境は JST のままなので、`timeZone` の指定が無くても 18:59 が出ます。
**同じ結果**です。

つまり「18:59 のまま」という観測だけでは、次の2つを区別できません。

| | 実行環境 | `timeZone` 指定 | 表示 |
|---|---|---|---|
| 確かめたかった状態 | UTC | 効いている | 18:59 |
| 🚨 `TZ` が効いていない状態 | JST | 効いているかどうか不明 | 18:59 |

期待どおりの結果が出たのに、何も確定していません。

## 反対側を見たら、両方が同時に確定した

やったのは、**`timeZone` の行を一時的にコメントアウトして、もう一度開く**ことでした。

```text
timeZone あり  → 18:59
timeZone なし  →  9:59   ← 9時間ずれた
```

9:59 が出たということは、

- **実行環境が UTC になっている**（＝ `TZ=UTC` が効いている）
- **`timeZone` 指定が整形に効いている**（＝ 外すと結果が変わる）

この2つが同時に確定します。
片方だけでは決まらなかったものが、**反対側を1回見ることで両方決まりました**。

条件を作って確かめたつもりでも、**その条件が効いているかは別の確認**でした。
`TZ=UTC` を信じた時点では、まだ何も確かめていません。

## Vercel 側で TZ を変える、という手は使えない

調べていて知ったのですが、**Vercel では `TZ` を環境変数として設定できません**。
予約された変数なので、ダッシュボードから JST を入れることはできない仕様です。

つまり「本番のタイムゾーンを日本時間に合わせる」という解き方は、この環境では取れません。
**コード側で毎回 `timeZone` を指定する**のが唯一の道になります。

これは後から知ったので、もし先に「環境変数で揃えればいい」と考えていたら、しばらく回り道していたと思います。

## 同じ罠が、別の形でもう1箇所あった

念のため `toLocale` で始まるメソッドの使用箇所を全部見ました。
1箇所だけで、しかもその日に足したものでした。

ただ、**同じ原因の罠は別の形で残っていました**。
日時を**読む**ほうです。

```ts
// 危ない
published_at: toIsoOrNull(post.date_gmt)

// 直した
published_at: toIsoOrNull(post.date_gmt ? `${post.date_gmt}Z` : undefined)
```

WordPress の REST API が返す `date_gmt` は、名前のとおり UTC の値ですが、**末尾に `Z` が付いていません**。
`new Date('2026-08-27T12:00:00')` のようにタイムゾーンの情報がない文字列は、**実行環境のタイムゾーンで解釈されます**。

出力と入力で、関数もメソッド名も違います。
でも起きることは同じで、**ローカルでは正しく、本番でだけずれる**。

`toLocale*` を検索して1箇所しかなかったとき、「片付いた」と思っていました。
探していたのはメソッドの名前で、**探すべきだったのは「タイムゾーンを省略している箇所」**でした。

なお、並べ替えにしか使っていない日時は無害です。
ISO 8601 の文字列は桁とタイムゾーン指定が揃っていれば辞書順が時系列順になるので、比較にタイムゾーンが入り込みません。
人間に見せるために整形した瞬間から、この問題が始まります。

## ローカルが反証にならない場所がある

この件で持ち帰ったのは2つでした。

1つは、**「ローカルで正しく見える」が根拠にならない箇所がある**ということ。
環境差そのものがバグの原因のとき、手元の環境は反証になりません。

もう1つは、**条件を作ったら、その条件が効いているかも確かめる**ということでした。
`TZ=UTC` と打った時点で、本番を再現したつもりになっていました。
反対側を1回見るのに、かかった時間は10秒ほどです。
