サブドメインを1つ増やすため、CNAME を1行だけ追加しました。保存して1〜2分後、反映を確認しようと `dig` を打ちました。

**この確認が、待ち時間を作っていました。**

## 起きたこと

```text
04:56  管理画面で CNAME を保存
04:58  dig を打つ → NXDOMAIN（まだ載っていない権威サーバーに当たった）
       → 8.8.8.8 / 1.1.1.1 / 9.9.9.9 の3つが「無い」をキャッシュ
05:01  権威サーバー3台すべてに反映完了
05:04  パブリックDNS のキャッシュが切れ、ようやく引けた
```

レコード自体は 05:01 に正しく載っています。それでも引けなかったのは、**3分前に自分が打った `dig` が「存在しない」をキャッシュさせたから**でした。

## ネガティブキャッシュ

DNS は「レコードが無い」という答えもキャッシュします。これがネガティブキャッシュで、RFC 2308 で定められています。

| | |
|---|---|
| 何をキャッシュするか | 「そのレコードは存在しない」という応答 |
| TTL の出どころ | **SOA レコードの最後のフィールド**（MINIMUM。今回は `3600`） |
| つまり | **正しく入れたレコードが、最大1時間確認できなくなる** |

キャッシュの話でよく聞くのは「古い値を読んでしまう」ほうだと思います。今回のは向きが逆で、**「無い」を作ってしまう**ほうでした。同じキャッシュでも、読む側と書く側で踏み方が違います。

### 実測は8分だった

「最大1時間」は上限で、実際には8分（05:01 → 05:04）で消えました。

パブリックDNS はエニーキャストで、ノードごとにキャッシュが別です。次にどのノードに当たるかで変わるので、**8分という数字も自分の環境の1回の観測**でしかありません。上限だけ見て1時間待つ必要も、8分で消えると期待する根拠もない、という状態です。

## もう1つ踏んだ: 権威サーバーを1台しか見なかった

このドメインの権威サーバーは3台（`ns-a1` / `ns-a2` / `ns-a3`）あります。**`ns-a1` だけを見て「反映されていない」と判断しました。**

実際は `ns-a2` と `ns-a3` は既に持っていて、`ns-a1` が数分遅れていただけでした。

さらに `ns-a1` の SOA シリアルが26日前の日付だったので、「このサーバーは止まっているのでは」とまで考えました。これも誤りで、**26日間そのゾーンに変更が無かっただけ**です。`ns-a1` は DMARC も DKIM も正しく持っていました。

サポートへ連絡が必要かもしれない、というところまで一歩踏み込んでいたので、確かめておいてよかったところです。

## 正しい順序

```bash
# 1. 保存したら数分待つ（ここを飛ばさない）

# 2. 権威サーバーを全部引く
dig @ns-a1.example.com sub.example.com CNAME +short
dig @ns-a2.example.com sub.example.com CNAME +short
dig @ns-a3.example.com sub.example.com CNAME +short

# 3. 全部揃ってから、初めてパブリックDNSを引く
dig @8.8.8.8 sub.example.com CNAME +short
```

権威サーバーを `@` で名指しすれば、パブリックDNS のキャッシュを経由しません。つまり**ネガティブキャッシュを作らずに確認できます**。

3番を最初にやってしまうと、まだ載っていない状態を引きに行って、自分でキャッシュを作ることになります。

## 確認のコストを数えていなかった

この日は同じ形の間違いを2回しています。「権威3台のうち1台だけを見た」のと、前日に「複数あるレコードのうち CNAME だけを見た」の2つで、**どちらも一部を見て全体を判断していました**。

それとは別に、今回のネガティブキャッシュは少し性質が違いました。判断を間違えたのではなく、**確認という行為そのものに副作用があった**という話です。

`dig` は読み取り専用のコマンドに見えます。実際、権威サーバーには何も起きていません。ただ、間にいるキャッシュサーバーには状態が残ります。ここを数えていませんでした。
