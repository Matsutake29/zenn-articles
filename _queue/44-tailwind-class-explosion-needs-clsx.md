## Tailwind の記事に、なぜか毎回 clsx が出てくる

Tailwind を使い始めたころ、紹介記事を読んでいると
`clsx`（や `classnames`）が当たり前のようにセットで出てきました。

「Tailwind を使うなら clsx も入れましょう」という書かれ方をしていることが多くて、
**何かの依存関係なのだと思っていました。**
Tailwind の機能を使うのに必要なライブラリなのだろう、と。

実際には関係ありません。
Tailwind は clsx を知らないし、clsx も Tailwind を知りません。
別々のライブラリです。
それでもセットで語られるのは、**Tailwind が生む書き方と相性がいいから**でした。

その理由が腑に落ちたのは、自分で書き方を移してからです。

## FLOCSS で書いていた頃は、この問題が起きなかった

案件では FLOCSS でクラスを設計していました。
1つの要素に付くクラスは、だいたいこのくらいです。

```html
<button class="c-button c-button--primary is-active">送信</button>
```

これを React に持ってきても、条件分岐は三項演算子1つで足ります。

```jsx
className={`c-button c-button--primary ${isActive ? 'is-active' : ''}`}
```

見た目の切り替えは**クラス名の側で完結している**からです。
「primary である」という状態に対応する見た目は、CSS の中に1箇所だけ書いてあります。
JSX 側が知っているのは、そのクラスを付けるかどうかだけでした。

## Tailwind に移すと、1要素のクラスが膨らむ

同じボタンを Tailwind で書くと、見た目の指定が全部 JSX に出てきます。

```jsx
className="rounded-full px-4 py-2 text-sm font-bold text-white bg-blue-600"
```

これ自体は困りません。
CSS ファイルを開かずに済むので、むしろ読みやすいと感じました。

問題は条件が絡んだときです。

```jsx
className={`rounded-full px-2 ${isPaid ? 'bg-green-500' : 'bg-gray-100'} ${isLarge ? 'text-lg' : 'text-sm'} ${disabled ? 'opacity-50' : ''}`}
```

読めません。
条件が3つ入っただけで、もう追えなくなります。
バッククォートの中に `${}` が3つあって、どこまでが条件でどこからが固定値なのかが読み取れない。
改行を入れても、テンプレートリテラルの中なので**空白の扱いに気を使う**ことになります。

clsx はこれを引数の並びに変えます。

```jsx
className={clsx(
  'rounded-full px-2',
  isPaid    ? 'bg-green-500' : 'bg-gray-100',
  isLarge   ? 'text-lg'      : 'text-sm',
  disabled  && 'opacity-50',
)}
```

やっていることは文字列の連結です。
それでも**1行1条件で並ぶ**ので目で追えます。
`false` や `undefined` は落ちるので、`: ''` を書く必要もなくなります。

## 道具が先にあったのではなかった

ここが自分にとっての発見でした。

clsx が必要になったのは、Tailwind を入れたからではありません。
**見た目の指定を CSS 側から JSX 側へ移したから**です。

- FLOCSS期: 見た目は CSS にある。JSX が扱うのは**状態を表すクラス1つ**
- Tailwind期: 見た目は JSX にある。JSX が扱うのは**見た目そのものの集合**

扱う対象が「状態」から「見た目の集合」に変わりました。
条件分岐の対象も1個から数個に増えます。
文字列連結では足りません。
そこに道具が要ります。

**設計を変えたから道具が必要になった**、という順序です。
「Tailwind を使うなら clsx」と紹介されると、Tailwind の付属品に見えてしまいますが、
実際には「クラスを大量に並べる設計」の付属品でした。

## 自分はまだ入れていない

正直に書くと、いま作っているアプリにはまだ clsx を入れていません。

条件が1つで済んでいるからです。

```tsx
<li className={`flex flex-col ${isOpen ? "col-span-full" : ""}`}>
```

```tsx
<button className={`pin-card grow text-left ${isOpen ? "rounded-b-none" : ""}`}>
```

この程度ならテンプレートリテラルで読めます。
まだ困っていません。
入れる基準は「条件が3つ目に入ったとき」くらいかな、と今のところ考えています。

入れないことにしたというより、**入れる理由がまだ来ていない**、という状態です。
理由が分かる前に入れていたら、たぶん「みんな入れているから」で終わっていました。

## 持ち帰り

- clsx は Tailwind の依存ではない。**クラスを大量に並べる設計と相性がいい**だけ
- FLOCSS のようにクラス名側へ見た目を寄せていると、そもそもこの問題が起きない
- 条件が3つ入るとテンプレートリテラルは読めなくなる。clsx は**1行1条件**に並べ替える道具
- 道具が先にあったのではなく、**設計を変えたから道具が要った**。この順序で理解すると、
  入れる/入れないを自分で判断できるようになりました
