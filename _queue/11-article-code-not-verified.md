書いた記事を公開する前に、載せているコードを実装ファイルと突き合わせるチェックをやりました。

**そのままではCSSが解決されない書き方**が見つかりました。他人が読んでコピペしたら動きません。

自分では動作を確認して書いているつもりだったので、なぜこうなったのかを整理しておきます。

## 記事に書いていたコード

配色とデザイントークンについての記事で、こう書いていました。

```css
:root {
  --color-bg: #f8f9fa;
}

@theme {
  --color-bg: var(--color-bg);   /* ← 自己参照 */
}
```

実装（`src/index.css`）は、こうなっていました。

```css
:root {
  --bg: #f7f7f5;
}

@theme {
  --color-bg: var(--bg);   /* ← 定義元は別名 */
}
```

Tailwind v4 の `@theme` は、最終的に `:root` へ変数を出力します。
だから**両方を同じ名前にすると、変数が自分自身を参照する**ことになって値が解決できません。

実装では定義元を `--bg`、Tailwind側を `--color-bg` と**別名にしてある**ので、正しく動きます。

## なぜこうなったか

原因ははっきりしています。

**記事用にコードを書き起こしたから**です。実装からコピーせずに、説明しやすいように名前を揃えました。

「`--bg` と `--color-bg` が混在していると読者が混乱しそうだから、名前を揃えて出そう」という判断です。
読みやすさのために変えた。そこで壊れました。

厄介なのは、**書いている側は動作を確認済み**という点です。実装は動いている。だから記事のコードも動くと思い込む。
読者がコピペして初めて分かる類のバグでした。

## 同じ検証で、もうひとつ誤りが見つかった

ついでに事実関係も突き合わせたら、別の誤りが出てきました。

記事に「プレートの色は競技規格で9色すべて決まっている」と書いていたのですが、規定があるのは**3色だけ**でした。

IPFのルールブック（一次情報）を読みに行ったら、こうなっていました。

> 10 kg and under - any color, 15 kg - yellow, 20 kg - blue, 25 kg - red

規定されているのは 15 / 20 / 25kg の3つで、10kg以下は **any color**（任意）です。

自分は「競技用プレートは色が決まっているもの」という粗い理解を持っていて、それをそのまま書いていました。
実際には、規定・慣習・識別性のために自分で選んだ色、の3種類が混ざっていた。

**記事は「自分が理解していること」を書くので、理解の粒度が粗い箇所がそのまま残ります。** 誰も指摘してくれないまま公開されます。

## 決めたこと

この2件を踏まえて、公開前のチェックに入れたのが以下です。

### 1. サンプルコードは実装ファイルからコピーする

書き起こさない。読みやすさのために名前を変えたくなったら、**変えたうえで実際に動かして確認する**。

「説明しやすくするための単純化」が動作を壊すことがある、というのが今回の実感です。
単純化そのものが悪いのではなく、単純化した状態を検証していなかったのが問題でした。

### 2. 事実は一次情報に当たる

「〜と決まっている」と書くときは、決めている文書を確認する。

今回は二次情報（まとめサイトや解説記事）しか見ていませんでした。
しかも探していた「9色の規定」は**存在しないもの**だったので、いくら探しても一次情報に辿り着かないのは当然でした。

出てこないときは「見つからない」ではなく「無いのかもしれない」と疑うべきでした。

### 3. 公開前に、記事と実装を並べて読む

コードブロックだけ抜き出して、対応する実装ファイルと1つずつ突き合わせます。手作業ですが、記事1本あたり5分くらいで終わります。

## 技術記事を書く側として

記事を書くことで理解が深まる、というのはよく言われます。実際そのとおりだと思います。

ただ今回は、**書くことで理解の粗さが露出した**という感じでした。書いている最中には気づかず、公開前に突き合わせて初めて出てきたので。

書けば分かる、ではなく、**書いたものを検証すると分かる**。順序としては後者でした。

## まとめ

- 記事用にコードを**書き起こすと壊れる**。実装からコピーする
- Tailwind v4 の `@theme` は `:root` に出力されるので、定義元と同名にすると自己参照になる
- 「説明しやすくするための単純化」は、単純化後の動作確認まで含めてやる
- 「〜と決まっている」は一次情報を確認する。**見つからないときは、無いことを疑う**
- 記事は自分の理解をそのまま出すので、粗い箇所は粗いまま公開される
