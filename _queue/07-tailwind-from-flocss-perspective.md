WordPressの受託でコーディングを2年やってきました。FLOCSSでクラスを分類して、SCSSでデザインカンプを1px単位で詰める。
そういう作り方が身体に入っています。

その状態で、個人開発のアプリに初めてTailwind CSSを使いました。

触ってみて最初に思ったのが「こんなにシンプルなのに、結構いい感じにできてしまうな」でした。ただ、その「いい感じ」が気持ち悪くもありました。
自分がこれまでやってきた、カンプの数値を拾って当てていく作業とは、明らかに別のことをしている感覚があったからです。

気になって仕組みから読み解いたら、**自分が持っていた前提のほうが間違っていた**ことが分かりました。

## 使う前に思っていたこと

恥ずかしいので先に出しておきます。使う前の理解はこうでした。

> - Tailwindは、なんとなくいい感じになるように作られている
> - ピクセルパーフェクトなカンプ再現は難しい
> - デザイン重視のサイトやLPには向かない
> - シンプルなアプリなら破綻しにくくて速いから向く

結論を先に書くと、上の4つは全部外していました。

同じようにWeb制作からフロントエンドに寄ろうとしている人は、たぶん似た前提を持っていると思うので、どこがどう違ったかを書きます。

## 誤解1: ピクセルパーフェクトは普通にできる

任意値記法というものがあります。角括弧に値を直接書く書き方です。

```jsx
<div className="p-[13px] top-[37.5%] w-[calc(100%-2rem)]">
```

これで何でも書けます。`calc()` も入ります。

というか、自分が書いたコードにも `gap-[3px]` が既にありました。
プレートの間隔を3pxにしたかったので、何も考えずにそう書いていた。**使えないと思い込みながら使っていた**ことになります。

素のCSSと併用してもいい、というのも後から知りました。`index.css` に `body {}` を普通に書いています。
全部ユーティリティクラスで書かないといけない、という決まりはありませんでした。

## 誤解2: 合わせる方向が逆だった

一番大きかったのがこれです。

カンプに合わせる作業を、自分は「Tailwindが持っている倍率に、カンプの数値をどう当てはめるか計算する」ことだと思っていました。
`p-4` が16pxなら、カンプの15pxはどう表現するんだ、と。

実際は逆でした。**カンプの規則のほうを、Tailwindに教える**んです。

```css
@theme {
  --spacing: 5px;
}
```

こう書けば、以後 `p-3` は15pxになります。カンプが5pxグリッドなら、その5pxを基準値として渡してしまえばいい。

自分が計算するのではなく、基準を教えて、あとは短い記法で書く。この方向が理解できていませんでした。

## 誤解3: 任意値だらけでも意味は残る

「結局 `p-[13px]` だらけになるならTailwindを使う意味がないのでは」とも思っていました。

Tailwindのメリットを4つに分けて考えると、任意値だらけになったとき失われるのは1つだけでした。

| メリット | 任意値だらけのとき |
|---|---|
| スケールが揃う | **失われる** |
| クラス名を考えなくていい | 残る |
| CSSとマークアップを往復しない | 残る |
| 未使用CSSが積もらない・削除が安全 | 残る |

そして、**SCSSの実務で自分の時間を食っていたのは2つ目と3つ目**でした。

クラス名を考える時間。`.p-service__card-inner` みたいな名前をひねり出して、命名規則から外れていないか確認する時間。
そしてHTMLとSCSSを行き来して、どのクラスがどこに効いているか追う時間。

これが丸ごと残るなら、ピクセルパーフェクトな受託案件でも使う理由は十分ありました。

### 「制約が強いフレームワーク」ではなかった

この3つを踏まえると、Tailwindの性格が違って見えてきます。

制約が強いのではなく、**初期値が良くて、そこから逸脱するとコストがかかる**設計でした。

`p-4` は3文字、`p-[13px]` は8文字。どちらも書けます。ただ外れる方が長くて目立つ。だから根拠のない値が自然に減っていく。
禁止しているわけではなく、面倒にしてある。

レビューで「この13pxの根拠は？」と聞く材料にもなります。
SCSSだと `padding: 13px;` は他の行と同じ見た目なので、そもそも目に留まりません。

## 思想の違い——「名前が設計」と「値が設計」

ここが今回いちばん面白かったところです。

FLOCSSとTailwindは、設計をどこに置くかが正反対でした。

| | FLOCSS | Tailwind |
|---|---|---|
| 何をするか | 意味で分類し、命名で構造を表現する | 分類も命名もしない |
| 設計の置き場所 | CSSファイル側 | トークン（`@theme`） |
| ひとことで言うと | **名前が設計** | **値の集合が設計** |
| 何がコストになるか | 命名規則の習得と遵守 | トークン設計 |

FLOCSSでは `.c-button` `.p-service` `.u-hidden` と接頭辞で層を分けます。
名前を見れば役割が分かるようにする書き方で、設計はCSSファイルの構造そのものに宿っています。

Tailwindは分類しません。`p-4` は「padding: 1rem です」以上の意味を持たない。
代わりに `@theme` に置いた値の集合が、そのプロダクトの設計になります。

**どちらが優れているという話ではなく、コストを置く場所が違う**だけでした。
FLOCSSは命名にコストを払い、Tailwindはトークン設計にコストを払う。
FLOCSSをやってきた身からすると、払う先が変わっただけで、払う量が減ったわけではないと思います。

ただ、命名のコストは「チーム全員が同じルールを覚えて守る」必要があるのに対して、トークン設計は1ファイルに集約されます。
人が増えたときの効き方が違うのかもしれません。ここはまだ実務で試していないので、想像です。

## 副産物: グリッドから外れた箇所が目に見える

これは使ってみるまで気づかなかったことです。

カンプの数値が `padding: 13px` `gap: 7px` とバラついているとき、SCSSではこう書きます。

```scss
.card {
  padding: 13px;
  gap: 7px;
}
```

**普通の見た目です。** 異常だと分からない。

Tailwindだとこうなります。

```jsx
<div className="p-[13px] gap-[7px]">
```

角括弧が並ぶので、視覚的に「外れている」ことが見えます。

自分は8pxグリッドが前提として身についています。
そのためグリッド意識のないカンプに当たったとき、これまでは「なんとなく気持ち悪い」としか言えませんでした。
これが「グリッドに乗っていない箇所が12個ある」と数えられる形になる。

デザイナーに指摘を返すときの説得力がまるで違います。感想ではなく数になるので。

## BootstrapとTailwindは同じカテゴリではない

「Bootstrapと似たような使い心地？」というのが、自分の最初の質問でした。クラスを並べてスタイルを当てる、という表面が似ているので。

抽象度がまったく違いました。

- **Bootstrapは完成品を配る**（`.btn` `.card` `.navbar`）。クラスの意味は「これはボタンです」
- **Tailwindは部品を配る**（`p-4` `flex`）。クラスの意味は「padding: 1rem です」

実務で効いてくる最大の違いは、**上書き地獄があるかどうか**でした。

Bootstrapが入ったテーマでカンプ通りに作ろうとすると、打ち消すCSSを書くことになります。
`.btn-primary` の背景・border・padding・hover状態。
詳細度で負けて `!important` を足す、あの作業です。
WordPressの案件で何度もやりました。

Tailwindには打ち消す相手が存在しません。最初から見た目を持っていないので。

CSS量も違います。
Bootstrapは全部入りを読み込むので、`bootstrap.min.css` が約190kB（gzip後 約30kB）。
Tailwindは使った分だけで、自分のアプリでは12.76kB（gzip後 3.54kB）でした。

そして、**「Bootstrapっぽいサイト」は一目で分かるのに、「Tailwindっぽいサイト」は原理的に存在しません。**
Tailwind自体が見た目を持っていないからです。

## 書いてみて残っている疑問

腑に落ちた部分が多かった一方で、まだ分かっていないこともあります。

- 大規模でトークンが増えたとき、`@theme` は本当に1ファイルで管理しきれるのか
- コンポーネント化されていない場所（WordPressのテーマの中など）で、同じクラス列を何度も書く問題をどう扱うのが定石なのか

このあたりは、次に実務のテーマ制作で使ってみるまで答えが出ないと思っています。
Tailwindはバンドラなしでも動いて `.php` もスキャンできるので、WordPressにそのまま持ち込めます。
その話は続編に書きました。

## まとめ

- ピクセルパーフェクトはできる。任意値記法で何でも書ける
- カンプに合わせるのは、こちらが計算するのではなく**カンプの規則をトークンで教える**
- 任意値だらけでも、命名と往復から解放されるメリットは残る
- FLOCSSは「名前が設計」、Tailwindは「値の集合が設計」。コストの置き場所が違う
- 外れた値が視覚的に目立つので、グリッド逸脱を数えられる

2年やってきた道具と違うものを触ると、まず違和感が来ます。
その違和感が「相手が変」なのか「自分の前提が古い」なのかは、仕組みまで降りないと判別できないんだなと思いました。今回は全部後者でした。
