## 間違った説明を、自分でテストして「確認済み」にした話です

フォームのバリデーションを Zod で書いていたときのことです。

`.refine()` の挙動について、AI からこう説明されました。

> フィールドの検証が落ちると `.refine()` は走らない

これは間違いでした。実際には毎回走ります。

ただ、この記事で書きたいのは「AIが間違えた」ではありません。
**その直後に自分で動かしたテストが、間違いを裏付けたように見えた**ほうです。

## 書いていたスキーマ

カードを1枚登録するためのスキーマです。
種類が3つあり、`link` のときだけURLが必須、`note` のときだけ説明が必須、という形にしたい。

```ts
export const itemSchema = z
  .object({
    title: z.string()
      .min(1, { error: 'タイトルを入力してください' })
      .max(60, { error: 'タイトルは60文字以内で入力してください' }),
    type: z.enum(['link', 'note', 'feed']),
    url: z.string().optional(),
    description: z.string().max(500).optional(),
    visible: z.boolean(),
  })
  .refine(
    (data) => (data.type === 'link' ? !!data.url : true),
    { error: 'URLを入力してください', path: ['url'] },
  )
  .refine(
    (data) => (data.type === 'note' ? !!data.description : true),
    { error: '説明を入力してください', path: ['description'] },
  )
```

`url` と `description` は `optional` です。
「常に必須」ではなく「種類によって必須」なので、フィールド単体では条件を書けません。
だから `.refine()` でオブジェクト全体を見る形にしています。

## 動かして、説明どおりだと思った

説明を受けたあと、そのまま動作確認をしました。
テスト入力もあわせて提示されたもので、`type` は `feed` でした。

結果はこうです。

- `url` を空にしても、エラーは出なかった
- 通った

**「フィールドの検証が落ちると走らないのだから、こうなるはずだ」という説明と、
目の前の結果が一致していました。** それで確認済みということにして、先へ進みました。

## 午後に矛盾が出た

別の作業をしていて、`type` を `link` にした瞬間に `url` のエラーが出ます。

同時に `title` を空にしたケースを試すと、**`title` と `url` の両方**が返ってきました。
フィールドの検証（`title`）が落ちているのに、`.refine()` のエラー（`url`）も出ている。

午前の説明が正しいなら、`title` で落ちた時点で `.refine()` は走らないはずです。

## 実際に数えてみた

推測で決めたくなかったので、`.refine()` の中にカウンタを置いて数えました。
zod は 4.4.3 です。

```ts
const ran = { url: 0, desc: 0 }

const itemSchema = z
  .object({ /* 上と同じ */ })
  .refine((d) => { ran.url += 1;  return d.type === 'link' ? !!d.url : true }, { path: ['url'] })
  .refine((d) => { ran.desc += 1; return d.type === 'note' ? !!d.description : true }, { path: ['description'] })
```

結果です。

| 入力 | `.refine()` の実行回数 | 出たエラー |
|---|---|---|
| `type: feed` / `url: ''` | **1回ずつ** | なし（通過） |
| `type: link` / `url: ''` | **1回ずつ** | `url` |
| `title` が61字 / `type: link` / `url: ''` | **1回ずつ** | **`title` と `url` の両方** |
| `title` が空 / `type: link` / `url: ''` | **1回ずつ** | **`title` と `url` の両方** |
| `type: note` / `description: ''` | **1回ずつ** | `description` |

3行目と4行目が答えでした。
**フィールドの検証が落ちている状態でも `.refine()` は走り、両方のエラーが返ってきます。**

説明は間違っていました。そして午前のテストは、その間違いを一度も踏んでいません。

## 通ったのに、通った理由が違った

午前に何が起きていたのかを並べるとこうなります。

| | 起きたこと |
|---|---|
| 入力した `type` | `feed` |
| `.refine()` | **走った** |
| 返り値 | `type` が `link` ではないので `true` |
| 結果 | `url` のエラーが出なかった |
| 自分の解釈 | 「走らなかったからエラーが出なかった」 |

エラーが出なかったのは事実です。
ただし理由は「走らなかったから」ではなく、**「走ったうえで `true` を返したから」**でした。

予測と結果が一致していて、一致した理由だけが違う。
テストは実行されたし、出力も読んだのに、間違いはそのまま残りました。

## いちばん困ったのは、疑う理由が消えたこと

未確認のままなら、次に触ったときに疑えます。
「そういえばあれ、ちゃんと見ていないな」と思い出せる。

一度「確認済み」にすると、そこは飛ばして先へ進みます。
**確認という行為が、間違いに寿命を与えた**という感覚がありました。

もう1つ、あとから気づいたことがあります。

説明したのも、テスト入力を出したのも、同じ相手でした。
自分は実行して結果を見ただけです。
**間違いと、間違いを裏付けるテストが、同じところから出ていました。**

二重チェックの形にはなっていたのに、独立していなければ意味がありません。

## どうすればよかったか

`type` は3種類しかないので、**全部試していれば午前のうちに矛盾が出ていました。**
`link` を1回入れれば、それで終わっていた話です。

いま意識しているのはこのあたりです。

- **入力を、説明した側とは別のところから取る。** 提示されたテストケースをそのまま使わない
- **列挙型は全部の値を通す。** 3つなら3つとも入れる。分岐を1本しか通さないテストは、通らなかった分岐について何も言っていない
- **「通った」ではなく「なぜ通ったか」まで一致しているかを見る。** ここが今回いちばん抜けていた部分でした

`.refine()` の挙動そのものは、ドキュメントを読むかカウンタを1行足せば分かることでした。
そこに10分使わなかったぶんを、午後に矛盾を追いかける形で払っています。
