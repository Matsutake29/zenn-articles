書いたブログやZennの記事を、公開のタイミングに合わせてXへ告知したい。ただ毎回手で投稿するのを忘れる。

というわけで、共用サーバーのcronからX APIを叩いて、キューに書いた投稿を自動で出す仕組みを作りました。

出しているのは**自分の記事の告知と、自分で書いた投稿だけ**です。他人の投稿を再送したり、大量投稿したりする用途ではありません。

作る過程で判断したことを書きます。

## なぜ純正の予約投稿を使わないのか

XのWeb版には予約投稿の機能があります。ただし**本人がブラウザで操作する必要があります。**

記事を書き終えたタイミングで、そのまま告知まで仕込みたかったので、スクリプトから完結させたいという要求がありました。

そしてX API v2 には、**予約投稿のエンドポイントが存在しません。**

だから「予約」は自前でやるしかありません。cronが定期的に起きて、キューの時刻に達したものを「いま」投稿する、という形になります。

## 設計で効いた判断

### 1. cronを固定時刻で撃たない

最初は「毎日20:00に実行」で書こうとしました。やめました。

```
*/10 18-22 * * *   # 10分おきにtick
```

10分おきに起きて、キューに書かれた時刻を過ぎているものだけを投稿します。

**毎日きっかり同じ分に投稿が出るのは、機械が出している信号そのもの**なので。人間は20:00ちょうどには投稿しません。

### 2. 告知のオフセットを乱数にする

記事の公開時刻に対して、**+5〜55分のランダム**で告知を出しています。

- 公開より前に出すと、リンクが404になる
- 固定オフセット（常に+30分など）だと、これも機械的

「公開したら、しばらくして告知する」という人間の行動を、幅で表現しています。

### 3. リンクは返信に分ける

本文（リンクなし）を主投稿にして、URLは返信でぶら下げています。

アカウント全体のリンク投稿比率を下げる意図です。効果を厳密に測ったわけではないので、ここは推測に基づく判断だと明示しておきます。

### 4. 依存パッケージゼロで書く

これが技術的には一番手応えがありました。

共用サーバーなので `pip` が使えません。**OAuth 1.0a の署名を、標準ライブラリだけで実装しました。**

ハマったのは署名対象です。

X API v2 は JSON body を取りますが、**bodyは署名対象に含めません。**

```python
# Content-Type: application/json のとき、
# 署名するのは oauth_* パラメータとクエリだけ
params = {
    "oauth_consumer_key": CONSUMER_KEY,
    "oauth_nonce": nonce,
    "oauth_signature_method": "HMAC-SHA1",
    "oauth_timestamp": str(int(time.time())),
    "oauth_token": ACCESS_TOKEN,
    "oauth_version": "1.0",
}

base = "&".join([
    "POST",
    quote(url, safe=""),
    quote("&".join(f"{k}={quote(v, safe='')}" for k, v in sorted(params.items())), safe=""),
])
key = f"{quote(CONSUMER_SECRET, safe='')}&{quote(TOKEN_SECRET, safe='')}"
sig = base64.b64encode(hmac.new(key.encode(), base.encode(), hashlib.sha1).digest())
```

OAuth 1.0a の仕様はこうです。
`application/x-www-form-urlencoded` のときだけ、bodyのパラメータを署名に含めます。
JSONを送る場合は含めません。ここを勘違いすると401が返り続けて、原因が分からなくなります。

### 5. 二重投稿を状態ファイルで防ぐ

cronが10分おきに起きるので、同じエントリを何度も投稿する事故が起こりえます。

投稿したものは、日付とキーをログファイルに追記して、次回以降スキップしています。

```
2026-07-25 20:20  git-flow-github-flow
```

シンプルですが、これがないと安心して回せません。

## 詰まった話: サーバーにUTF-8ロケールが無かった

ここは共用サーバーならではだったので、独立して書きます。

スクリプトを動かしたら、**日本語が全部 `?` になりました。**

原因を辿ると、`LANG=C.UTF-8` が**設定されているのに、そのロケールがインストールされていない**状態でした。

伏線はありました。sshでログインするたびに、perlがこう警告していたんです。

```
perl: warning: Please check that your locale settings:
    LANG = "C.UTF-8"
    are supported and installed on your system.
```

毎回出ていたのに、読み飛ばしていました。**エラーメッセージは出ていた。読んでいなかっただけでした。**

そのうえサーバーのPythonは 3.6 で、UTF-8 mode（3.7以降の `-X utf8`）がありません。
ロケールの設定がそのまま効いてしまいます。

症状は3つに分かれました。

| 経路 | 結果 | 対処 |
|---|---|---|
| `print` で日本語を出す | `UnicodeEncodeError` で落ちる | 起動時に stdout/stderr を `TextIOWrapper` で UTF-8 に張り替える |
| ファイルを読み書きする | locale依存で壊れる | `open(..., encoding="utf-8")` を全箇所に明示 |
| **コマンド引数で日本語を渡す** | `?????` に化ける | **回避不能** |

3つ目が厄介でした。`argv` のデコードはlocaleに依存するので、Python側でどうにかできません。
`LANG=C.UTF-8` を付けても直りません。**ロケール自体が無いのだから当然**でした。

### 結論: 引数で日本語を渡す設計にしない

**ファイル経由にすれば全部解決します。**

実際、本番の経路（キューファイルから読む）では一度も問題が起きていません。
困ったのは、手元から動作確認のために引数で文字列を渡していたときだけでした。

「回避できない制約」に見えたものが、**そもそもその経路を使わなければいい**だけだった、というオチです。
制約を突破しようとして時間を溶かす前に、迂回できないか考えるべきでした。

## まとめ

- X API v2 に**予約投稿のエンドポイントは無い**。cronで「いま」投稿するしかない
- 固定時刻で撃たない・オフセットに幅を持たせる。機械的なパターンを避ける
- OAuth 1.0a は標準ライブラリだけで書ける。**JSON bodyは署名に含めない**
- 共用サーバーでは `LANG` が設定されていてもロケールが存在しないことがある
- **引数で日本語を渡さない設計にすれば、ロケール問題の大半は回避できる**

pipが使えない環境は制約が多いですが、そのぶん標準ライブラリの中身を読むことになります。
OAuthの署名を手で書いたのは、今回いちばん勉強になりました。
