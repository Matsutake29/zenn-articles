## 「Vercelは簡単すぎるのでは」から始まった

ポートフォリオとして Next.js のアプリを作っていて、置き場所を考えていました。

自分は仕事で使っているレンタルサーバー（ConoHa WING）を契約しています。
WordPress のサイトはそこに置いています。

最初に考えたのは、**アプリもそこに置いたほうが評価されるのでは**ということでした。
Vercel に置くのは、ボタンを押すだけで終わってしまう。
自分でサーバーに載せたほうが、技術的にやっていることが多いように見えるのではないか。

いま書くと動機がズレているのが分かるのですが、当時は真面目にそう思っていました。

## 調べたら、置けなかった

理由は単純でした。

```
Next.js が動くのに必要なもの    → Node.js のプロセスが常時起動していること
レンタルサーバーが提供するもの  → PHP の実行環境（リクエストごとに起動して終わる）
```

図にするとこうなります。

```mermaid
flowchart TB
    subgraph A["レンタルサーバー（PHP）: リクエストごとに起動して終わる"]
        direction LR
        A1[リクエスト] --> A2[プロセス起動] --> A3[HTML を返す] --> A4[プロセス終了]
    end
    subgraph B["Next.js: プロセスが常駐して待っている"]
        direction LR
        B1[起動して待機] --> B2[リクエストを受ける] --> B3[HTML を返す] --> B1
    end
```

WordPress が動くのは、**PHP がこの「起動して終わる」形に合っているから**です。
リクエストが来るたびに PHP が立ち上がり、HTML を作って返し、消える。
1回ぶんの仕事が終われば、何も残りません。
だから共有サーバーでも成立します。

Next.js のサーバーは常駐している前提です。
置き場所として噛み合いません。
`next start` を打ち続ける場所が無い、というだけの話でした。

## `output: export` という逃げ道はある

静的なHTMLとして書き出す設定があります。

```ts
// next.config.ts
const nextConfig = { output: 'export' }
```

これならただのHTMLとCSSとJSになるので、レンタルサーバーに置けます。

ただし代償があります。同梱ドキュメントに、使えなくなるものが列挙されていました。

> Features that require a Node.js server, or dynamic logic that cannot be computed during the
> build process, are **not** supported

- Server Actions
- Cookies
- Route Handlers（`Request` に依存するもの）
- Proxy（旧 middleware）
- Rewrites / Redirects / Headers
- Incremental Static Regeneration
- 既定のローダーを使った画像最適化
- Draft Mode
- `generateStaticParams()` の無い動的ルート

Cookie も Server Actions も使えないので、**ログインのあるアプリは成立しません。**

ここで1つ勘違いしていたことがあります。
「Server Components も使えなくなる」と思っていたのですが、そうではありませんでした。
Server Components は**ビルドのときに実行されて結果がHTMLになる**ので、静的書き出しでも使えます。

使えなくなるのは「**リクエストが来た瞬間にサーバーで何かする**」ものでした。
Cookie を読む、フォームを受け取る、リクエストごとに出し分ける。
言われてみれば当然の線引きなのですが、名前が似ているので混ざっていました。

## VPS なら置ける。ただし

技術的には VPS を借りれば動きます。root 権限があるので Node.js を入れて常駐させられます。

そのかわり、こうなります。

| | レンタルサーバー | VPS | Vercel |
|---|---|---|---|
| root 権限 | なし | あり | ー（PaaS） |
| Node.js の常駐 | ❌ | ✅ | ✅ |
| OS の更新 | 事業者 | **自分** | プラットフォーム |
| プロセスの常駐管理 | ー | **自分**（PM2 など） | プラットフォーム |
| リバースプロキシ | ー | **自分**（Nginx など） | プラットフォーム |
| SSL の自動更新 | 事業者 | **自分** | プラットフォーム |
| 落ちたときの対応 | 事業者 | **自分** | プラットフォーム |

**運用が全部こちらに来ます。**

ポートフォリオのアプリを1本置くために、OS の更新とプロセスの監視を引き受けるのかというと、
それは自分がやりたいこととは違いました。

## 理解を訂正した

最初に考えていた「Vercel は簡単すぎてズルいのでは」は、前提が間違っていました。

**そこは自分の職責ではないから任せている**、というのが正しい理解です。
アプリを作る人がインフラも見るべきだ、という考え方はありますが、
少なくとも「難しいことをしているほうが偉い」ではありません。

WordPress の案件でレンタルサーバーを選ぶのも、同じ判断をしています。
サーバーの面倒を見ないで済むから選んでいるはずなのに、
自分のアプリになった瞬間に「自分で面倒を見たほうが立派だ」と考えていました。

置き場所は Vercel にしました。

## 持ち帰り

- Next.js は **Node.js のプロセスが常駐している前提**。PHP のリクエスト単位の実行環境とは噛み合わない
- `output: export` で静的化すれば置けるが、**Cookie も Server Actions も使えない**。ログインのあるアプリは無理
- **Server Components はビルド時に実行されるので静的書き出しでも使える。** 使えないのはリクエスト時の処理
- VPS なら動くが、OS 更新・プロセス常駐・SSL 更新まで自分で背負う
- 「簡単な方法を選ぶ＝手を抜いている」ではありませんでした
