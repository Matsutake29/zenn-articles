自作アプリでダークモード対応をしていて、**同じ構造のバグを2回踏みました。**

1回目は「まあ見落としだな」で済ませられます。
2回目が出た時点で、これは自分の注意力の問題ではなく、**ライトモードで決めた設計がダークで壊れる構造がある**のだと思いました。

その構造を言語化してみます。

## 1例目: 背景に溶ける色が、逆転していた

バーベルのプレート枚数を計算するアプリを作っています。
プレートは競技規格で色が決まっていて、25kgは赤、20kgは青、といった具合に9種類の色を画面に描いています。

実装したときに、こういう対処をしていました。

> 5kgの白と0.5kgの銀は背景に溶けやすいので、この2つにだけborderを持たせる

ライトモードで見れば正しい対処です。カード背景が `#ffffff` なので、白いプレートは輪郭がないと消えます。

ダークモードで開いたら、**2.5kgの黒が背景に溶けていました。**

### 感覚ではなく数値で確認した

「なんとなく見にくい」で終わらせず、コントラスト比を測りました。

- 黒プレート `#18181b`
- カード背景 `#212224`
- **コントラスト比 1.11 : 1**

WCAG 1.4.11（非テキストのUIコンポーネント）が求める最低基準は3:1です。大きく下回っていました。

数値にすると話が変わります。「見にくい気がする」は主観ですが、「1.11:1で基準を満たしていない」は欠陥です。
直すかどうかの議論が要らなくなりました。

### 最初に浮かんだ2案は、どちらも間違っていた

最初の問いは「borderをつけるか、背景を明るくするか」でした。

背景を明るくする案は、計算した時点で破綻しました。
黒プレート（`#18181b`）に対して3:1を確保するには、背景を `#6b6b6d` 相当——中間グレーまで明るくする必要があります。
ダークテーマの階層感が完全に壊れます。

borderをつける案も、よく考えると1例目とまったく同じ発想でした。「溶けそうな色を見つけて、その色にだけ対処する」という。
**この対処法そのものが、今回の穴の原因**です。

もうひとつ、設計として引っかかったことがあります。

- 背景トークン（`--surface`）は全画面に効く
- 溶けているのはプレート1種類

**全画面に効くトークンを、特定要素1つの視認性のために動かすのは影響範囲が不釣り合い**でした。
加えて「プレート実物の色（競技規格）」と「UIの背景色」は責務が別で、後者を前者に合わせるのは依存の向きが逆です。
プレートの色は規格で決まっていて動かせないほうなので。

### 採用した解: 輪郭を共通レイヤーに格上げする

やったのは、輪郭を「個別プレートの属性」から「全プレート共通のレイヤー」に格上げすることでした。

```css
:root {
  --plate-edge: rgba(0, 0, 0, 0.3);      /* ライト: 暗い輪郭 */
}

@media (prefers-color-scheme: dark) {
  :root {
    --plate-edge: rgba(255, 255, 255, 0.32);  /* ダーク: 明るい輪郭 */
  }
}
```

**輪郭色が常に背景の反対側にあるなら、9色すべて・両モードで自動的に成立します。** どの色が溶けるかを考える必要がなくなりました。

副産物として、コードが短くなりました。
プレートの色定義から「borderを持つかどうか」の情報が消えて純粋な色表になり、描画側の三項演算子も消えた。
差分は -6行 / +2行です。視認性バグを直したらコードが減る、というのは気持ちのいい体験でした。

### 1例目の教訓

**例外を列挙する設計は、想定していない方向で必ず漏れます。**

「溶けそうな色」を列挙した時点で、その列挙はライトモードという条件付きでした。条件が変われば列挙も変わる。
1つのルールで全ケースをカバーする形にすれば、漏れようがなくなります。

## 2例目: ホバー色でも同じことが起きた

後日、ホバーの実装をしていて、既存のトークンを流用しようとしました。

`--surface`（カードの背景）と `--surface-2`（一段違う背景）が既にありました。
ホバー時に `surface-2` を当てれば済むだろう、と。

当てる直前に気づきました。

| | `--surface` | `--surface-2` | 関係 |
|---|---|---|---|
| ライト | `#ffffff` | `#ececea` | surfaceのほうが**明るい** |
| ダーク | `#212224` | `#2a2b2e` | surfaceのほうが**暗い** |

同じクラスを当てると、**片方のテーマで明暗が逆転します。** ライトでは「ホバーすると暗くなる」、ダークでは「ホバーすると明るくなる」。

……と書くと正しそうに見えますが、実際には逆です。
`surface-2` を当てるとライトでは一段暗く（正しい）、ダークでも一段明るく（正しい）なるのは偶然です。
この2つのトークンは「ホバー用」として設計されていないので、次にどちらかの値を調整したときに関係が崩れます。

`--surface-hover` を独立させて、「**ライトは一段暗く、ダークは一段明るく＝どちらでも手前に浮く向き**」と決めました。

## 一般則: トークンに持たせるべきは「色」ではなく「関係」

2例に共通していたのは、これでした。

- ダメな持ち方: 「この要素は `#ececea`」（ライトでの見え方を固定している）
- 良い持ち方: 「この要素は**背景より一段手前に見える**」（両モードで意味が保たれる）

1例目の `--plate-edge` は背景の反対側、2例目の `--surface-hover` は手前に浮く向き。
やっていることは同じです。
**相対関係をトークン名に込めた**。

ダークモード対応というと「色を2セット用意する」作業だと思っていました。実際にやることは、**色ではなく関係を書き出す**作業でした。
関係さえ書けていれば、値は各モードで別々に決めていい。

## 気をつけていること

書いていて思ったのですが、これは「ダークモードの話」というより「**片方の条件でしか確認していないと起きること**」の一例です。

同じ時期に、モバイルでしか動作確認していなかったせいでホバーの実装が丸ごと抜けていた、というのもやりました。
片方でしか見ていない状態は、見ている側からは完璧に見えます。だから自分では気づけない。

いまのところ有効だったのは、条件を切り替えて両方見ることと、**主観ではなく数値で測ること**の2つでした。
1.11:1という数字が出た瞬間に、議論が終わったので。

## まとめ

- ライトモードで決めた「溶けやすい色」の列挙は、ダークで逆転する
- **例外を列挙する設計は、想定外の方向で必ず漏れる**。1つのルールで全ケースを覆う形にする
- 全画面に効くトークンを、特定要素1つのために動かさない
- トークンに持たせるのは**色ではなく関係**（「背景の反対側」「一段手前に浮く」）
- 「見にくい」はコントラスト比で測れる。数値にすると議論が終わる
