パワーリフティング向けのプレート計算アプリを作りました。

https://plate-calculator-zeta.vercel.app/

:::message
目標の重量に対して、バーの片側に何kgのプレートを何枚つければいいかを計算するWebアプリです。
公式大会では装着する構成が自動で表示されるのですが、これが普段の練習でもスマホで見られたら便利だなと思って作りはじめました。
Web制作のコーダーからフロントエンドエンジニアへの転向を目指していて、その1本目として作ったものです。

- リポジトリ: https://github.com/Matsutake29/plate-calculator
- Vite + React + TypeScript + Tailwind CSS + Vitest / Vercel
:::

作っている途中で、入力仕様を一度ひっくり返しました。
「0.25kg刻みで自由に入力できる」から「その場にあるプレートで組める値しか入力できない」へ。

きっかけは、**バーベルが左右対称であるという当たり前の事実**でした。
当たり前すぎて、コードに落とすまで自分でも気づいていませんでした。

## 最初の仕様は「0.25kg刻みの自由入力」だった

要件を書いた時点では、目標重量は0.25kg刻みで自由に入力できることにしていました。
一番軽いプレートが0.25kgなので、それに合わせた——という、それだけの理由です。

実装してしばらく使っていて、この仕様が破綻していることに気づきます。

`142.3` と入力すると、画面には `142.3kg` と表示されたまま、内部では142.5kg相当の構成が計算されて出てくる。
つまり**画面の数字と計算結果が食い違う**。

自分は競技をやっているので、この気持ち悪さがすぐ分かりました。
記録に挑戦する人はグラム単位で重量を見ています。
「142.3kgと入れたのに142.5kgの構成が出てくる」アプリは、その時点で信用できません。

対応していないなら、対応していないと明示する。そう考えて仕様を変えました。

## バーベルは左右対称なので、合計は片側の2倍でしか動かない

では正しい刻みは何kgなのか。
ここで詰まって、紙に書いて考えました。

バーベルは左右に同じものを着けます。
片側に0.25kgを1枚足せば、**合計は0.5kg増えます**。
片側に足せる最小の重さが0.25kgなら、合計として動かせる最小の幅は0.5kgです。

つまり、

> 実現できる最小の増分 = 使えるいちばん軽いプレート × 2

これ以外の刻みを許すと、**必ず組めない目標が生まれます**。
合計 +0.25kg は片側 +0.125kg を意味しますが、そんなプレートは存在しません。

書いてしまえば一行ですが、ここに辿り着くまでが長かった。
現実では当たり前に分かっていることが、ロジックに落とすと途端に見えなくなります。

そして重要なのは、**この「いちばん軽いプレート」がジムによって違う**ということです。

## 刻みを固定値にすると、ジムによって破綻する

対象を公式大会だけに絞るなら、刻みは2.5kg固定でも成立します。
でもこのアプリは、ローカル大会や個人練習、家庭用まで想定しています。

- 街のジムには1.25kgより軽いプレートが無いことが多い
- 25kgプレートが無いジムもある
- 規定のカラー（2.5kg×2）が無い場所もある

刻みを0.5kg固定にすると、1.25kgまでしかないジムで「組めない重量」を入力できてしまいます。
逆に2.5kg固定にすると、0.25kgプレートを持っている人が微調整できません。

**固定値にした時点で、どちらかの環境が必ず壊れます。**

そこで、使用可能なプレートの設定（アプリ内で on/off できます）から刻みを導くことにしました。

```ts
/**
 * その環境で実現できる目標重量の刻み幅を返す。
 *
 * バーベルは両側対称なので、合計重量は「片側に足した分の2倍」でしか動かない。
 * つまり使えるいちばん軽いディスクの2倍が、動かせる最小の単位になる。
 * 0.25kgディスクをonにすると合計0.5kg刻みになり、これはIPFの記録更新の
 * 最小幅（新記録は既存記録より最低0.5kg上）と一致する。
 */
export const getWeightStep = (availablePlates: PlateWeight[]): number => {
  if (availablePlates.length === 0) return FALLBACK_STEP
  return Math.min(...availablePlates) * 2
}
```

関数としては3行です。
けれどこの3行があることで、**どんなジムの設備でも自動的に正しくなります**。

25kgしか無い倉庫のような環境なら刻みは50kgになり、0.25kgまで揃った競技会場なら0.5kgになる。
場合分けを書かずに、在庫という事実から一意に決まります。

## 丸めの責務は「stateの持ち主」に置いた

刻みが決まったら、入力値をそこへ寄せる必要があります。

```ts
export const roundTargetWeight = (
  targetWeight: number,
  baseWeight: number,
  step: number,
): number => {
  const baseUnits = toUnits(baseWeight)
  const plateUnits = toUnits(targetWeight) - baseUnits
  if (plateUnits <= 0) return baseWeight

  const stepUnits = toUnits(step)
  return toKg(baseUnits + Math.round(plateUnits / stepUnits) * stepUnits)
}
```

ポイントは、**丸めるのはプレート分だけで、バーとカラーの重量には触っていない**ところです。

バー15kg・カラー無しの環境で刻みが2kgのとき、100kgと入力すると101kgになります。
一見おかしく見えますが、正しい。
15kgから2kgずつ積める値は 15, 17, 19… なので、100kgはそもそも組めません。

そして丸めをどこで呼ぶか。
これは入力欄（子コンポーネント）ではなく、**stateを持っている親**に置きました。

```tsx
// 目標重量を「その環境で実際に組める値」に揃える。下限・上限で挟んでから刻みに丸める。
// 入力欄の表示と計算結果がズレないよう、目標重量を変える経路はすべてここを通る
const normalizeTargetWeight = (
  weight: number,
  baseWeight: number,
  availablePlates: PlateWeight[],
) => {
  const clamped = Math.min(Math.max(weight, baseWeight), MAX_TARGET_WEIGHT)
  return roundTargetWeight(clamped, baseWeight, getWeightStep(availablePlates))
}
```

目標重量が変わる経路は3つあります。

1. 数値を直接入力する
2. ± ボタンを押す
3. 環境設定を変える（バーを軽くする、プレートを on/off する）

3つ目が見落としやすい。
**目標重量そのものを触っていなくても、刻みや下限が変わるので目標重量は無効になり得ます。**
20kgバーで100kgを入力した後にバーを10kgへ変えたら、下限も刻みも変わります。

この3経路が別々に丸めを実装していたら、いつか必ずどれかがズレます。
1つの関数に集約したことで、「画面の数字と計算結果が一致する」がアプリ全体の保証になりました。

## 副産物として、競技のルールと一致した

実装してから気づいたのですが、この設計には嬉しい偶然がありました。

0.25kgプレートを on にすると、刻みは自動的に **0.5kg** になります。
そしてこの0.5kgは、**IPF（国際パワーリフティング連盟）が定める記録更新の最小幅と一致します**。

つまり「記録挑戦モード」のような機能を別途作る必要がなかった。
在庫から導くという設計が、競技のルールを自然に再現していました。

なぜ一致するのかを考えると、これは偶然ではありません。
ルールが0.5kgを下限にしているのは、**バーベルが左右対称だから**です。
公認ディスクの最小が0.25kgである以上、合計を0.25kg刻みで動かすことは物理的にできません。

ルールの側が物理的な制約に従っているので、物理から導いた実装と一致するのは当然でした。

## ルールブックを直接読んだら、仕様の誤りが2件見つかった

刻みの根拠を書いていて、「記録更新の最小幅は0.25kg」と要件定義に書いていたことに気づきました。
参考記事から拾った数字です。

気になって、IPFのTechnical Rulebook（英語・PDF）を直接読みに行きました。
結果、**2件の誤り**が見つかりました。

1. **記録更新の最小幅は0.25kgではなく0.5kg**（9.1 2)(g)）。実際の大会でも0.5kg刻みで記録が更新されています
2. **1kgのディスクが実装から抜けていた**。重量許容誤差の表（2.3(b)1）に載っている公認ディスクでした

さらに、保留していた別の疑問も片づきました。
「小さいプレートの規定色が二次情報しか見つからない」と悩んでいました。
ルールブックには **10kg以下は "any color"** と明記されていました。

**見つからなかったのは、存在しないものを探していたからでした。**

IPFが色を規定しているのは25kg（赤）・20kg（青）・15kg（黄）の3つだけです。
それ以外は慣習色にすぎない。
これを知らずにREADMEへ「IPF規定の色です」と書いていたら、間違った説明を広めるところでした。

ソースコードのコメントにも、規定色と慣習色の区別を書き残しています。

```ts
// IPFが色を規定しているのは25kg(赤)・20kg(青)・15kg(黄)の3つだけで、
// 10kg以下は "any color"（IPF Technical Rulebook 2.3(b)6）。
// 10kg以下はEleiko等の製品で事実上の標準になっている色を採用し、
// 規定のない1kg以下は互いに識別できることを優先して選んでいる。
```

44ページの英語PDFを読むのは面倒でしたが、**一次情報を読まないと「無いことの確認」ができない**という当たり前を体験しました。
二次情報をいくら探しても、「規定が存在しない」という結論には辿り着けません。

## その設計を、自分で壊していた

ここまで書いておいて情けない話ですが、この設計を自分で踏み抜いていました。

目標重量の ± ボタンの増減幅を、**2.5kg固定**にしていたのです。
ウォームアップで2.5kgずつ刻むことが多いから、という理由でした。

刻みを在庫から導いておきながら、ボタンの移動量は固定値。
当然おかしなことが起きます。

| 刻み | ＋1回 | −1回 | 結果 |
|---|---|---|---|
| 1kg | 3kg | 2kg | 非対称 |
| 5kg | 5kg | 0kg | −だけ効かない |
| 10kg | 0kg | 0kg | 両方効かない |

ボタンが常に「+2.5kg」を要求し、親側の丸めが最寄りの刻みへ戻してしまう。
刻みが粗い環境では、**押しても数字が1ミリも動きません**。

原因は「ボタンが何kg動くべきか」を決める責任が、どのファイルにも置かれていなかったことでした。
丸めは「不正な入力を正す」仕組みであって、「ボタンの移動量を決める」仕組みではありません。
後者を暗黙に前者へ委ねていました。

直し方は単純で、増減幅を刻みの整数倍にすること。
整数倍なら丸めが手を出す余地がないので、押した分だけ確実に動き、＋と−が対称になります。
倍数のなかでも「1倍」がいちばん説明が短い——**±ボタンは1刻み動く**、で完結します。

固定値を持たせるのをやめ、親から受け取っている `step` をそのまま使うようにしました。
同じ轍を踏まないよう、なぜ固定値ではいけないのかを型定義のコメントに残しています。

```tsx
type WeightInputProps = {
  value: number
  onChange: (value: number) => void
  // その環境で実現できる刻み幅（使えるいちばん軽いプレートの2倍）。
  // ±ボタンはこの1つ分だけ動かす。固定値にすると親側の丸めと食い違い、
  // 刻みが粗い環境ではボタンを押しても元の位置に戻されてしまう
  step: number
  min: number // バー+カラーの合計。これ未満は組めない
  max: number
}
```

「刻みは在庫から導く」と決めたなら、**ボタンの移動量も同じ思想に揃えるべきでした**。
片方だけ慣習に基づく固定値を残していたのが敗因です。

なおこのバグは、**既存のテスト21本が全部通っている状態で存在していました**。
なぜ通ってしまったのかは、次の節に書きます。

## テストは「性質」で書く

刻みまわりは純粋関数に切り出してあるので、Vitestで固定しています。

面白かったのは、修正後に書き足したテストです。
「この入力ならこの出力」ではなく、**「どの在庫設定でも ± が対称に動く」という性質**を書きました。

```ts
for (const smallestPlate of PLATE_WEIGHTS) {
  const step = getWeightStep(
    PLATE_WEIGHTS.filter((weight) => weight >= smallestPlate),
  )

  it(`最小${smallestPlate}kg（${step}kg刻み）の環境で±が対称に動く`, () => {
    const current = roundTargetWeight(100, BAR_WEIGHT, step)

    expect(roundTargetWeight(current + step, BAR_WEIGHT, step)).toBe(
      current + step,
    )
    expect(roundTargetWeight(current - step, BAR_WEIGHT, step)).toBe(
      current - step,
    )
  })
}
```

在庫パターンをループで回して、全部の環境で性質が保たれることを確認しています。
個別の値を並べるより、**壊れたときに「何が保証されなくなったか」が分かりやすい**。

「固定値を使ってはいけない理由」自体もテストとして残しました。
将来の自分が2.5kg固定に戻そうとしたら、このテストが落ちます。

## おわりに

「入力の刻み」というごく地味な仕様ひとつに、これだけ考えることがありました。

学びとしては、

- **現実の制約（左右対称）を先に見つけると、実装は短くなる**。場合分けを書かずに済んだ
- **環境の違いは、設定項目ではなく事実から導く**。「在庫」という1つの入力から刻みも下限も決まる
- **一次情報を読むと「無いことの確認」ができる**。二次情報では辿り着けない結論がある
- **同じ思想を全体に貫かないと、片方だけ古い設計が残って壊れる**
