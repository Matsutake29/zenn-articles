AIとペアを組んで作ったアプリを、GitHubの公開リポジトリに置くことにしました。

:::message
この記事で「公開する前に整えた」対象がこのリポジトリです。

- リポジトリ: https://github.com/Matsutake29/plate-calculator
- パワーリフティング向けのプレート計算アプリ（Vite + React + TypeScript + Tailwind CSS）
- 公式大会では装着する構成が自動で表示されるので、普段の練習でもスマホで見られたら便利だなと思って作りはじめました
:::

そのとき「これ、このまま公開していいんだっけ」と引っかかった箇所がいくつかあって、順番に整えていったので記録します。
Gitの履歴書き換えを3回やることになりました。

なお、AIを使うこと自体を隠したいという話ではありません。
**何を自分の判断でやったかが見える状態にしたい**、という一人称の整理です。

## 1. コミットの `Co-Authored-By: Claude` を消した

Claude Codeは、デフォルトでコミットに共著者のトレーラー行を付けます。

```
Co-Authored-By: Claude <noreply@anthropic.com>
```

普段の作業では気にしていなかったのですが、Jr.レベルの転職用ポートフォリオという文脈だと、採用担当が履歴を見たときに「丸投げしたのかな」と受け取られるリスクがあると考えました。

判断として、今後は付けない設定にし、既にコミットしていた4件からは履歴を書き換えて除去しました。

```bash
git filter-branch --msg-filter 'sed "/^Co-Authored-By: Claude/d"' HEAD
git push --force-with-lease
```

繰り返しになりますが、AI活用を隠す意図ではありません。
AIを使ったこと自体はXでもZennでも書いています。
リポジトリという「製品」の側には、自分の判断の痕跡だけを残したかった、という切り分けです。

## 2. CLAUDE.md から内部情報を分離した

これがいちばん大きい整理でした。

`CLAUDE.md`(AIへの指示書)に、こういうものを書いていました。

- ローカルの作業ディレクトリのパス
- NotionのURL
- 自分の学習状況
- AIとの協働の進め方

**リポジトリを公開したら、これも全部公開される**わけです。気づいて青ざめました。

### 判断の基準

整理するにあたって置いた基準が、**「リポジトリに置くのは、製品と、開発に他人にも必要な規約だけ」**でした。

プロセスの内部情報は、別のチャネル(ローカル設定・自分の管理ディレクトリ・XやZennでの発信)に分ける。

自分ひとりのポートフォリオではあるのですが、**「誰かが使う製品になるかもしれないつもりで作る」**と考えると、線を引く場所が自然に決まりました。

### 実装

ファイルを2つに分けました。

| ファイル | 内容 | git |
|---|---|---|
| `CLAUDE.md` | 技術スタック・コマンド・Git規約のみ | 追跡する(公開) |
| `CLAUDE.local.md` | 内部運用・個人的な文脈 | 管理外 |

`CLAUDE.local.md` はClaude Codeが自動で読んでくれるので、AIに渡る情報は減りません。公開される情報だけが減ります。

整理後の公開側は [CLAUDE.md](https://github.com/Matsutake29/plate-calculator/blob/main/CLAUDE.md) で見られます。技術スタックとコマンド、Git規約だけが残っている状態です。

### 履歴からの除去

問題は、過去のコミットに残っていることです。ファイルを消すコミットを積んでも、履歴を遡れば読めてしまいます。

```bash
git filter-branch --index-filter \
  'git rm --cached --ignore-unmatch CLAUDE.md' \
  --prune-empty HEAD
```

- `--index-filter` … 各コミットのインデックスから対象ファイルを取り除く
- `--prune-empty` … そのファイルだけのコミットは、中身が空になるので自動で削除される

### 消えたことの確認方法

書き換えたつもりで残っていたら意味がないので、全履歴を横断して検索しました。

```bash
git grep <検索語> $(git rev-list main)
```

`git rev-list main` が全コミットのハッシュを吐き、それを `git grep` に渡すことで**全履歴を対象に検索できる**という書き方です。
これは知らなかったので収穫でした。

## 3. `.claude/settings.local.json` の扱いを確認した

AIコーディングツールの設定ファイルにも、個人情報的なものが入ります。

`.claude/settings.local.json` には、セッション中に許可したBashコマンドの履歴などが入っていました。

こちらは `.gitignore` に最初から登録されていて、`git ls-files` で確認しても未追跡だったので実害なしでした。

覚えておきたいのは、**ファイル名に `local` が付くかどうかで機械的に判断できる**ということです。

| ファイル | 用途 | git |
|---|---|---|
| `.claude/settings.json` | チーム共有 | 追跡する |
| `.claude/settings.local.json` | 個人設定 | 管理外 |

「AIツールのローカル設定は最初からgitignoreする」を、次のプロジェクトからは標準の初期設定にしようと思っています。

## 4. コミットメッセージの規約を決めた

Conventional Commitsの接頭語を使い、**subjectは英語・bodyは日本語**という折衷にしました。

```
feat: add plate calculation logic

貪欲法で大きいプレートから順に割り当てる方式を採用。
端数が埋まらない場合は不足分をshortfallとして返す。
```

### 「英語ができないからコミットメッセージが書けない」は思い込みだった

正直、英語のコミットメッセージには苦手意識がありました。書こうとすると手が止まる。

でも実際に見本を大量に読んで気づいたのは、subjectは**自由英作文ではない**ということです。

```
接頭語: 動詞の原形 + 対象
```

この超定型文しかない。しかも動詞は10個くらいで回ります。

`add` / `remove` / `update` / `fix` / `rename` / `move` / `extract` / `bump` / `prevent` / `simplify`

これに気づいてから、まったく怖くなくなりました。

### bodyに書くのは「なぜ」

bodyの本質は「何をしたか」ではありません。何をしたかはdiffを見れば分かります。

**diffから読み取れない「なぜ」を書く**のがbodyの役割だと整理しました。
だからここは日本語のほうが情報量が出せる。

### そもそも英語が標準とは限らない

調べていて分かったのですが、「コミットメッセージは英語が標準」というのはOSSや国際的なチームの話で、**日本企業の社内開発では日本語のコミットも普通**でした。

本当の標準は「チームの規約に従う」ことで、一人開発なら自分で決めていい。
当たり前のことなのですが、思い込みが1つ減りました。

## force pushが許されたのは、条件が揃っていたから

ここまでで履歴書き換えを3回やり、そのたびに `--force-with-lease` を打っています。

強調しておきたいのですが、**これは例外的に許される条件が揃っていたからです**。

- 公開した直後
- 一人で開発している
- PRもレビューも走っていない
- 他の誰もcloneしていない

このどれかが崩れたら、やってはいけない操作です。
GitHub Flowで運用を始めた後のmainブランチなら原則禁止だと理解しています。

なお `--force-with-lease` は `--force` の安全版で、**リモートが自分の想定より進んでいた場合には失敗してくれます**。
生の `--force` はその確認をせず上書きするので、使うならこちらを選ぶべきだと学びました。

## 副次的に分かったこと: コミットの粒度

作業しながら、コミットの粒度についても認識が変わりました。

「とにかく細かく刻むのが良い」と思っていたのですが、本質は細かさではなく**「1コミット = 1つの論理的な変更」**でした。

あと、`docs:` や `chore:` のコミットが履歴に混ざるのは実務でも普通だと知って、少し安心しました。機能追加だけがコミットではない。

## まとめ

| やったこと | 判断の軸 |
|---|---|
| AI共著表記の除去 | 製品側には自分の判断の痕跡を残す |
| CLAUDE.mdの分離 | リポジトリは製品と共有規約だけ |
| ローカル設定の確認 | ファイル名の `local` で機械的に判断 |
| コミット規約の決定 | subjectは定型文、bodyには「なぜ」 |

全体を貫いていたのは、**「誰かが使う製品になるかもしれないつもりで作る」**という前提でした。
一人のポートフォリオでも、その前提を置くと判断の基準ができます。

AI時代の公開リポジトリで、CLAUDE.mdをどこまで公開するかはまだ定石がない領域だと思います。
現時点での自分なりの線引きとして。
