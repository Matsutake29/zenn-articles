## developブランチ運用が当たり前だと思っていた

普段のWeb制作の仕事では、developブランチに変更を溜めてからmainにマージする運用に慣れていた。これがいわゆる「Git Flow」という名前がついた運用方法だと知ったのは、実はつい最近のことだった。

今回、個人開発するにあたって、「GitHub Flow」という別の運用方法を採用した。
調べてみると、developブランチを使わず、mainブランチと短命のfeatureブランチだけで完結する、思っていたよりシンプルな仕組みだった。

## 使い分けの本質は「規模」ではなく「リリースの形」

最初は「チームの規模や案件の大きさで使い分けるものなのかな」と思っていたが、実際に調べて腹落ちしたのは、使い分けの本質は規模ではなくリリースの形にあるという点だった。

- バージョン単位でまとめてリリースする(アプリストア審査・クライアントへの納品など)なら、developに変更を溜めておく意味がある
- マージしたらすぐ本番に出るWebサービスの場合、developを経由する分だけ手間が2倍になるだけで、あまり意味がない

自分の場合、Web制作の受託案件は「まとめて納品」に近い形が多く、個人開発のWebアプリは「マージ即デプロイ」向き。
同じ自分が扱っているプロジェクトなのに、案件側はGit Flow運用、個人開発側はGitHub Flow運用と、性質によって自然と使い分けている状態になっている。

## PRごとのプレビューが検証環境の役割を代替する

GitHub Flowでdevelopブランチを使わないと聞いたとき、最初は「動作確認する場所がなくなるのでは」と思った。
しかし実際は、PRを作るとVercelなどが自動でプレビュー環境を用意してくれるので、developブランチが担っていた「本番前に確認する場所」の役割はここで代替されていると気づいた。

## どちらが正しい、ではなく判断軸を持てたこと

Git FlowとGitHub Flowのどちらが優れているという話ではなく、「リリースの形に応じて使い分ける」という判断軸を持てたのが、今回の一番の収穫だった。
