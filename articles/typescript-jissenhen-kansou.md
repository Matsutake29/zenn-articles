## はじめに

「サバイバルTypeScript」（https://typescriptbook.jp/ ）というOSSの無料教材を使って、「作って学ぶTypeScript」という実践チュートリアル章を完走しました。

簡単な関数の作成から始まり、Reactのいいねボタン、Next.jsの猫画像ジェネレーター、Vercelへの本番デプロイ、Vitestでのテスト、Prettier・ESLint・huskyによる自動化まで、実務でTypeScriptを使うとどんな開発になるかを一通り体験する構成になっています。テキストベースの教材をAIと対話しながら読み進めるスタイルで、動画教材だとコピペできず質問もしづらかった、という以前の手詰まり感が解消されたのも良かった点でした。

Web制作を本業にしながらフロントエンドエンジニア転向を目指して学習していて、この数日間を振り返ると、共通して起きていたのは「動かしながら理解が後から追いついてくる」という順番でした。今回はその過程を、時系列でたどりながら書きます。

## 宣言的UIが、対比によって腑に落ちた

最初の山場は「Reactでいいねボタンを作ろう」の章でした。命令的なコード（`document.createElement`等で「どう表示するか」を逐一記述する）と、宣言的なコード（JSXで「こうなってほしい」だけを書く）の対比を読んだとき、以前ふわっとしか理解できていなかった「宣言的」の意味がスッと腹落ちしました。

以前バニラJS→Reactの順で別の講座を受けていたので、その積み上げが今回の理解を後押ししてくれた実感があります（この気づき自体は、当時Twitterにも書きました）。

一方で、TypeScriptの型注釈については「間違った型が入らないようになった」程度の実感にとどまっていました。シンプルな実装だと型推論に任せる場面が多く、恩恵を感じにくい、という構造に自分で気づいたのもこのタイミングです。

## 環境構築で足元をすくわれた話

いいねボタンの実装に入る前、開発環境を整える段階で最初のトラブルに遭遇しました。

`brew install node@26`を実行しても、`node -v`の結果がいつまで経ってもv24.14.0のまま変わりません。原因は、nvmとHomebrewを併用していたことでした。PATH上で先に見つかる方（今回はnvm管理下のnode）が、もう一方をシャドーイングしていたのです。

```bash
brew uninstall node@26
nvm install 26
nvm use 26
nvm alias default 26
```

Node.jsのバージョン管理を一本化して解決しましたが、「`brew install`したのに反映されない」という現象は、原因が分かるまで地味に混乱しました。ツールを併用するときは、どちらが優先されるかを意識しておく必要がある、という実体験からの学びです。

## Next.jsとVercelデプロイで、2つのエラーを解決した

次の山場は「Next.jsで猫画像ジェネレーターを作ろう」と「Vercelにデプロイしてみよう」でした。TheCatAPIと連携して画像を切り替えるだけのシンプルなアプリですが、実際に本番デプロイまで走らせてみると、チュートリアルだけでは踏まない実務的なつまずきが2つありました。

1つ目は、Vercelのデプロイが「環境変数が設定されていません」というエラーで失敗したことです。ローカルの`.env`は`.gitignore`対象なので、Vercel側に環境変数を別途設定する必要がある、という基本を身をもって学びました。

2つ目は、GitHub上でPull Requestを作成したときのプレビューデプロイ失敗です。「コミット作者のチームアクセスを確認できない」というVercel側のエラーで、最初はGitHubのメール認証が原因かと疑いましたが、確認すると既に認証済みでした。自分の場合は、これはプレビューデプロイだけをブロックする挙動で、マージ自体は妨げられていなかったため、そのままマージして解決しています。

`git push`するだけで本番環境に自動反映される体験を通して、「CI/CD」という言葉の「CD（継続的デプロイ）」の部分を初めて実感として理解できました。「CI（継続的インテグレーション、自動テスト）」の方は、この後に控えていたVitestの章につながる、というのもこのとき言語化しています。

## 「知ってるつもりだった」ものが、実は分かっていなかった

Vitestの章に入って早々、名前の勘違いに気づきました。「Vitest」を最上級を表す英語の接尾辞「-est」（fast→fastestのような）だと思い込んで、「Viteの上位互換なんだろう」と勝手に解釈していたのです。実際は単に Vite + test の組み合わせで、「Viteのエンジンを再利用して作られたテストランナー」というのが正体でした。

似たようなことがnpmとnpxでも起きました。普段からコピペで打っていたコマンドだったので、違いを聞かれて初めて「実はちゃんと分かっていなかった」と気づきました。

- npm: パッケージを**入れる**係（インストール・依存関係の管理）
- npx: パッケージを**動かす**係（一時実行、またはローカルインストール済みの実行ファイル呼び出し）

`npx create-next-app`は「一時的にダウンロードして実行し、終わったら消す」使い方で、`npx vitest`は「プロジェクトに入ってる実行ファイルを呼ぶ」使い方。同じnpxでも中身の動きが違う、というのも今回初めて理解しました。

動かしながらコマンドを打って、後から「これは何だったのか」を知る。この順番で学ぶのが、自分には合っているようです。

## テストを書いた後に残った「実務でどう活かすか」という違和感

Vitestの章、Reactコンポーネントのテストの章と進めて、テストの書き方自体は理解できました。ただ完走した直後、正直に言うと「これを実務でどう活かすかまでは、まだイメージがつかない」という感覚が残りました。

説明はされているのに、腹落ちしない。この感覚自体が今回の一番の気づきかもしれません。

テストの価値は、「テストがなくて壊れた」を実際に経験して初めて実感が湧くものだと思います。今の自分にはまだその経験がありません。代わりに持てた考え方は、「全部にテストを書く」のではなく「壊れたら困る部分に書く」という優先順位です。静的なコーポレートサイトのコーディングでは正直優先度は低いけれど、計算ロジックが絡む部分――たとえば自分が構想しているパワーリフティングのプレート重量計算アプリのようなもの――には、テストがあると安心感が全然違うはずです。

## エラーメッセージを自分で切り分けて直した話

一番手強かったのはESLintの章でした。

`npm init @eslint/config@latest`を実行したら、依存関係の解決エラー（ERESOLVE）が出ました。typescript-eslintというパッケージが要求するTypeScriptのバージョン（`>=4.8.4 <6.1.0`）と、プロジェクトに入っていたTypeScript（7系）が噛み合わなかったのが原因です。

`--legacy-peer-deps`オプションを付けて再インストールすると、一見成功したように見えました。ただ、`package.json`の中身を実際に開いて確認したら、肝心のESLint関連パッケージが1つも追加されていませんでした。

```json
"devDependencies": {
    "jiti": "^2.7.0",
    "typescript": "^7.0.2"
}
```

ターミナルの出力だけを信じて次に進んでいたら、気づかずに素通りしていたと思います。手を動かして、明示的にインストールし直して解決しました。

その後、今度は実行時エラーとして本題が出てきました。

```
typescript-eslint does not support TS 7.0.
```

TypeScript 7がリリースされたばかりで、typescript-eslint側の対応がまだ追いついていない、というエコシステム側の時差でした（GitHubのissueで追跡中と分かりました）。プロジェクトのTypeScriptを対応バージョンまで一時的に下げて解決しています。最新版を追いかけることが偉いわけじゃなく、「ツール同士が対応してるバージョンで揃える」のも実務的な判断なんだと、体験を通して分かりました。

## これから

「作って学ぶTypeScript」の章はこれで完走です。次に控える「読んで学ぶTypeScript」――型システムを体系的に扱う章――は、頭から読み切るのではなく、この先ポートフォリオを作る中で必要になった箇所をリファレンス的に読む、という進め方に決めました。チュートリアルをなぞる段階は一区切りにして、実際に手を動かす段階に進みます。

動かしながら分かった気になって、後から「実はちゃんと分かってなかった」に気づく。今回の5日間は、その繰り返しでした。次はポートフォリオ制作に進んでいきます。
