個人開発でアプリを作るとき、配色をどう決めていますか。

自分はWeb制作でコーダーをやっているので、渡されたデザインを実装するのは日常です。
でも**ゼロから配色を決める**となると話が別で、いつも手が止まります。

:::message
パワーリフティング向けのプレート計算アプリを作っています。
目標の重量に対して、バーの片側に何kgのプレートを何枚つければいいかを計算するWebアプリです。

公式大会では装着する構成が自動で表示されるのですが、これが普段の練習でもスマホで見られたら便利だなと思って作りはじめました。

- リポジトリ: https://github.com/Matsutake29/plate-calculator
- Vite + React + TypeScript + Tailwind CSS
:::

このアプリを作るにあたって、条件はこうでした。

- デザインに時間はかけたくない
- でも第一印象は良くしたい

この2つを両立させるためにやったことと、決めた後の「置き場所」の判断をまとめます。

## 勘で決めるのをやめた

まず、好みで選ばないことにしました。「なんとなく青が落ち着くから」で決めると、後から理由を説明できません。
ポートフォリオである以上、聞かれたときに答えられる状態にしておきたい。

代わりに、2ステップ踏みました。

### 1. トレンドと競合を調べる

調べたのは2つです。

- **2026年のフィットネス系UIのトレンド** … ソフトなニュートラル + ミニマルな配色が主流
- **競合アプリ「Bar Is Loaded」の方向性** … クリーンでボタン少なめ

いきなり色を選ぶのではなく、「このジャンルでは今どういう見え方が普通か」を先に把握する。
ここを飛ばすと、独りよがりな配色になります。

### 2. 3案作って、実際の画面で見比べる

調査を踏まえて、方向性の違う3案を設計しました。

| 案 | 方向性 |
|---|---|
| A | クリーン・ミニマル |
| B | 硬派・ジム系 |
| C | 明るめ・親しみやすい |

そして重要なのがここで、**カラーパレットだけを並べても判断できない**ということです。
色見本で良く見えても、実際の画面に乗せると印象が変わる。

なので、実際のアプリ画面に近いミニモックアップを作りました。
目標重量の入力欄・環境設定のチップ・プレートの装着イメージまで含めた、動く見本です。
ライト/ダークの切り替えボタンも付けて、その場で見比べられるようにしました。

見比べた結果、選んだのは**案A(クリーン・ミニマル)**でした。

### 選定理由が、設計判断とも噛み合った

面白かったのが、選んだ理由が機能側の制約と一致したことです。

このアプリは25kgから0.25kgまで、9種類のプレートを色分けして画面に出します(25kg赤 / 20kg青 / 15kg黄 / 10kg緑 / 5kg白 / 2.5kg黒 / 1.25kg橙 / 0.5kg銀 / 0.25kg金)。

ちなみに記事を書くにあたって規定を確認し直したのですが、IPFのTechnical Rulebookで色が定められているのは**25kg(赤)・20kg(青)・15kg(黄)の3つだけ**でした。

> Discs must conform to the following color code: 10 kg and under - any color, 15 kg - yellow, 20 kg - blue, 25 kg - red.
> — IPF Technical Rulebook 2026, 2.3 Bars and Discs

10kg以下は「any color」、つまり競技上は自由です。
それ以下の色は、実際のジムで見慣れた配色に合わせている、というのが正確なところでした。

いずれにせよ、**情報量として色がすでに多い**ことは変わりません。

だから背景側は控えめにするべきで、それはクリーン・ミニマル路線と自然に整合しました。

好みで選んだのではなく、「表示する情報の性質から逆算するとこうなる」と説明できる状態になった。
これが勘で決めなかった一番の収穫でした。

## 決めた後、どこに置くか

配色が決まったので、次は管理の話です。

「`design.md` を作って配色を記録しておくべきか」を検討して、**作らないことにしました。**

### 理由: 二重管理になるから

別ファイルに「メインカラーは `#xxxxxx`」と書くと、その瞬間から**コード(実体)とドキュメント(説明)の2箇所に同じ値が存在する**ことになります。

そして必ず、片方だけ直してもう片方を忘れます。ドリフトが起きる。

ドキュメントが実体とズレると、ないほうがマシな状態になります。読んだ人が古い値を信じてしまうので。

### 代わりに: デザイントークン

やったのは、**値の定義元を1箇所に固定する**ことでした。

`src/index.css` のCSS変数を唯一の定義元にして、Tailwind v4の `@theme` ブロックからはそれを間接参照させる構造にしています。

```css
:root {
  --bg: #f7f7f5;
  --surface: #ffffff;
  --text: #1c1c1e;
  --accent: #0f766e;
}

@media (prefers-color-scheme: dark) {
  :root {
    --bg: #17181a;
    --surface: #212224;
    --text: #f2f2f0;
    --accent: #2dd4bf;
  }
}

@theme {
  --color-bg: var(--bg);
  --color-surface: var(--surface);
  --color-text: var(--text);
  --color-accent: var(--accent);
}
```

実物は [src/index.css](https://github.com/Matsutake29/plate-calculator/blob/main/src/index.css) にあります。プレート9色の定義は [src/lib/plateColors.ts](https://github.com/Matsutake29/plate-calculator/blob/main/src/lib/plateColors.ts) です。

ポイントは、**定義元の変数名を `--bg` にして、`@theme` 側の `--color-bg` とは別名にしている**ところです。

`@theme` は最終的に `:root` へ変数を出力するので、両方を同じ `--color-bg` にすると `--color-bg: var(--color-bg)` という自己参照になり、値が解決できません。
ここは名前を分けておく必要がありました。

こうしておくと、色を変えたいときに触る場所が1箇所しかありません。
Tailwindのクラス側も、コンポーネント側も、全部そこを見ている。ダークモードも `:root` の値を差し替えるだけで、`@theme` 側は触らずに追従します。

いわゆるSSOT(Single Source of Truth)を、デザインの値についても適用したかたちです。

### ただし「なぜ」だけは別に残す

値の実体はコードにのみ置く。ただ、**「なぜこの配色にしたか」という判断の記録は別途残しました**(`設計思想.md`)。

役割分担はこうです。

| 置き場所 | 何を書くか |
|---|---|
| コード(CSS変数) | 値の実体 |
| 設計思想のドキュメント | なぜそう決めたかの記録 |

**値はズレるが、判断の記録はズレません。** 「情報量が多いので背景を控えめにした」という理由は、色を微調整しても変わらない。

だから前者はコードに一本化し、後者だけをドキュメントに残す。この切り分けなら二重管理になりません。

## 実務と比べると

チーム開発なら、この領域はもっと重装備です。

- Figmaでデザインを管理
- デザイントークン管理ツールでコードと同期
- Storybookでコンポーネントカタログを作る

ただ今回は、**個人開発で1画面完結の規模**です。
ここにその仕組みを持ち込むのは明らかにオーバースペックだと判断しました。

規模に対して仕組みが重すぎると、メンテナンス自体が目的化します。
「本来やるべき正しい構成」ではなく、「この規模で妥当な構成」を選ぶ。ここも一つの判断でした。

## まとめ

- 配色は勘で決めず、トレンド + 競合調査 → 3案 → 実画面のモックで比較
- カラーパレット単体では判断できない。実際の画面に乗せて見る
- 選定理由が機能側の制約(色数が多い)と噛み合うと、説明できる配色になる
- `design.md` は作らない。値はコード(CSS変数)に一本化してドリフトを防ぐ
- Tailwind v4の `@theme` に渡す変数は、定義元と**別名**にする(同名だと自己参照になる)
- ただし「なぜそう決めたか」は別に残す。値と違ってズレないから
- 仕組みは規模に合わせる。チーム前提の重装備を個人開発に持ち込まない

デザインが専門ではないので、ここは今後も試行錯誤すると思います。現時点での整理として。
