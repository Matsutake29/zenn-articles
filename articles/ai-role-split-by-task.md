個人開発でAIとペアを組むとき、「どこまで自分で書いて、どこからAIに任せるか」で毎回悩みます。

:::message
パワーリフティング向けのプレート計算アプリを作っています。
目標の重量に対して、バーの片側に何kgのプレートを何枚つければいいかを計算するWebアプリです。

公式大会では装着する構成が自動で表示されるのですが、これが普段の練習でもスマホで見られたら便利だなと思って作りはじめました。

- リポジトリ: https://github.com/Matsutake29/plate-calculator
- Vite + React + TypeScript + Tailwind CSS
:::

このアプリを作っている途中、**隣り合う2つの工程で、AIとの役割分担が真逆になった**ことがありました。

- 工程4(テスト実装) … 自分で書いて、AIにレビューしてもらう
- 工程5(UI実装) … AIに実装してもらって、自分がレビューに回る

続けて踏んだ工程で正反対の体制を選んだので、なぜそうなったのかを整理しておきます。

## テストは自分で書いた

Vitestでのテスト実装は、AIにたたき台を作ってもらうのではなく、自分で書いてAIにレビューしてもらう体制にしました。

理由は単純で、TypeScriptの型システムやVitestの記法がまだ自分の中で定着していなかったからです。
実際、判別可能Unionの絞り込みが1段階では足りないことに気づけたのは、自分で書いて型エラーを踏んだからでした。
読んでいるだけなら、最初から正しく絞り込まれた完成形しか見ていません。

このあたりの詳細は別記事に書いたので、ここでは省きます。

https://zenn.dev/matsutake_prgrm/articles/test-how-much-to-write

## UIはAIに任せた

一方、UI実装(コンポーネント・デザイントークン・CSS)は、AIに実装してもらって自分はレビューに回る体制にしました。

Web制作の実務でCSSを長年触ってきているので、ここは**ゼロから書いても学びの伸びしろが薄い**という判断です。
Tailwindは実務での経験が浅いぶん多少の慣れは必要ですが、それも「CSSを知っている人がクラス名の対応を覚える」話であって、新しい概念を獲得するわけではありません。

自分で書けば時間はかかる。
かかった時間のわりに、得られるものが少ない。
それなら実装スピードとクオリティを優先しよう、と考えました。

## 使い分けの軸

振り返って言語化すると、判断していたのは**「新しい概念を学ぶ工程か、それとも既に実務スキルを持っている領域か」**でした。

| 工程 | 領域 | 体制 |
|---|---|---|
| テスト実装 | 新しい概念(型・テスト記法) | 自分で書く → AIレビュー |
| UI実装 | 既存スキルの延長(CSS) | AI実装 → 自分がレビュー |

「AIとペアで進める＝常に自分で書くべき」でも、「常に任せるべき」でもない。
**領域ごとに使い分けるという判断自体**が、実務の感覚に近いのかもしれません。
実務でも、自分の専門外は巻き取ってもらい、専門領域は自分でやる、という判断は日常的に発生します。

## ただし「任せる」は丸投げではなかった

やってみて分かったのは、実装を任せても**決めなければいけないことは残る**ということでした。

実際、UI実装では手を動かす前に3つ決める必要がありました。

### 1. 計算結果の4状態を、画面でどう描き分けるか

計算ロジックは判別可能Unionで4パターンを返します。
これをそのまま4分岐で描き分けるのがUIの本質でした。

```ts
type Result =
  | { ok: true; breakdown: Plate[]; shortfall: number }
  | { ok: false; reason: "targetBelowMinimum"; minimum: number }
  | { ok: false; reason: "invalidInput" }
```

実物は [src/lib/calculatePlates.ts](https://github.com/Matsutake29/plate-calculator/blob/main/src/lib/calculatePlates.ts) にあります。

ここで引っかかったのが、要件定義に書いていた「構成不能なときは下に丸めた近似値と不足分を出す」という仕様です。
これを独立したエラー状態だと思い込んでいたのですが、**型の上では `ok: true` かつ `shortfall > 0` として表現されている**。
エラーではなく、成功の一種でした。

型を先に決めておくと、画面に必要な状態も自動的に決まります。
逆に言えば、型と画面の数がズレていたら、どちらかの理解が間違っているということです。

### 2. 色が背景に溶ける問題

このアプリはプレート9種を色分けして表示します。
比較用に作ったモックアップでは4色しか使っていなかったので気づかなかったのですが、実装に入ると**5kg(白)と0.5kg(銀)が背景に溶けて見えなくなる**ことが分かりました。

対処として、プレートの輪郭線を背景と反対側の色で1本持たせることにしました。

```css
--plate-edge: rgba(0, 0, 0, 0.3);          /* ライト時 */
--plate-edge: rgba(255, 255, 255, 0.32);   /* ダーク時 */
```

こうすると、白でも黒でも同じ1本の輪郭で成立します。
色ごとに個別対応する必要がありません。

実物は [src/index.css](https://github.com/Matsutake29/plate-calculator/blob/main/src/index.css) にあります。

### 3. ダークモードをv1に含めるか

要件定義に書いていなかったので、含めるかどうかを決める必要がありました。

結論としては含めました。
デザイントークンをCSS変数で持つ構造にしてあったので、`:root` の値を差し替えるだけで済み、追加コストがほぼゼロだったからです。
構造を先に決めておくと、後からの判断が軽くなる例だと思います。

---

3つとも、**手を動かす部分ではなく決める部分**でした。
実装を任せるかどうかと、設計を握るかどうかは別の話なんだと分かりました。

## まとめ

- 隣り合う工程で、AIとの役割分担を真逆にした
- 軸は「新しい概念を学ぶ工程か、既に実務スキルがある領域か」
- 新しい概念は自分で書く。手を動かさないと定着しない
- 既存スキルの延長は任せる。ゼロから書く練習の意義が薄い
- ただし任せても設計判断は残る。**実装を任せることと、判断を明け渡すことは別**

役割分担を工程ごとに固定せず、そのつど問い直す。
それ自体がAIとペアで開発するときのスキルなのかもしれない、と感じた出来事でした。
