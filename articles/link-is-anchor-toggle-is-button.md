2作目のポートフォリオとして「Hubpin」（分散した発信を1か所に集めるハブサイト）を作りながら書いています。

- リポジトリ: https://github.com/Matsutake29/hubpin

自分の発信をカードで並べるサイトを作っています。
カードを押したらその場で展開して、中に記事一覧や説明文を出す。そういうUIにしました。

設計の途中で、全部のカードを展開させるのはやめました。
種類によって `<a>` と `<button>` を出し分けています。

a11yのために手間をかけた、という話ではありません。
**分けたほうが実装が減って、結果としてa11yも正しくなった**という順序でした。

## 発端は機能の要望だった

もともとは見た目の話ではなく、出したい情報の違いから始まっています。

- SNSのカードは、アイコンを見れば何のリンクか分かる。押したら飛べばいい
- ブログや作品のカードは、展開して情報量を増やしたい（記事一覧や説明文を出したい）

ここで自分が心配したのは「**設定が一律じゃなくなると管理が大変になるのでは**」でした。
カードごとに挙動が違うと、登録画面でその都度選ばせることになる。項目が増えるのは避けたい。

## 実際には設定が増えなかった

結論から書くと、増えませんでした。

カードの種類（`type`）は、レイアウトの都合とは無関係に**もともと必要な情報**だったからです。
外部からフィードを取りに行くカードと、そうでないカードを区別しないと実装できません。

つまり既に2値で持つ予定だったものが、3値になるだけでした。

| type | 挙動 | 使う要素 |
|---|---|---|
| `link` | 展開せず直リンク | `<a href>` |
| `note` | 展開して説明文を出す | `<button aria-expanded>` |
| `feed` | 展開して外部記事一覧を出す | `<button aria-expanded>` |

自分のサイトの7枚を分類すると `link` が3枚、`note` が1枚、`feed` が3枚でした。

ユーザーが選ぶ項目は1つも増えていません。実装の分岐も1つだけです。
`type` を見て返す要素を変える、それだけで済みました。

## むしろa11yのほうが正しくなった

要素を分けた結果、こうなりました。

- **リンクはリンクとして振る舞う** — 中クリックで新しいタブ、右クリックでURLコピー、カーソルを乗せればステータスバーに遷移先が出る
- **開閉はボタンとして振る舞う** — スクリーンリーダーに「折りたたみが開いている / 閉じている」が伝わる

もし全部を `<a>` にしてJavaScriptで展開していたら、**どちらの利点も失っていました**。
リンクなのに新しいタブで開けない。開閉なのに開いているかどうかが読み上げられない。

「a11yに配慮して要素を分けた」と書くと丁寧なことをしたように見えますが、
実際には**役割に合う要素を選んだだけ**です。合わないものを選んで、JavaScriptで振る舞いを足し直すほうが手間でした。

## `<button>` の中に `<a>` は置けない

要素を分けると決めたあとで、構造上の制約にぶつかりました。

HTML仕様で、`<button>` の中に置けるものはこう決まっています。

> Phrasing content, but there must be no interactive content descendant and no descendant with the tabindex attribute specified.
> （[HTML Standard - The button element](https://html.spec.whatwg.org/multipage/form-elements.html#the-button-element)）

インタラクティブな要素を子孫に持てません。`<a>` はインタラクティブ要素なので、
**`<button>` の中に `<a>` は置けない**ことになります。

なので展開型のカードは、こういう形になります。

```
<button aria-expanded="true">カードのタイトル</button>
<ul>
  <li><a href="...">記事1</a></li>
  <li><a href="...">記事2</a></li>
</ul>
```

ボタンとリンクのリストが**兄弟**になります。
カード全体を `<button>` で囲んで、中に記事リンクを並べる書き方は、そもそも成立しません。

制約に気づいたのが実装前だったので助かりました。
カード全体をボタンにする前提でスタイルを組んでいたら、途中で組み直すことになっていたと思います。

## 却下した案: 自動判定

「展開するかどうか」を、説明文やフィードURLが入っているかどうかから自動で決める案も考えました。
カラムが増えないぶん、安く見えます。

やめた理由が2つあります。

- **「説明は書きたいが展開はさせたくない」ができない** — 入力した内容がそのまま挙動を決めてしまう
- **ユーザーから見て、なぜこのカードは開かないのかが分からない** — 挙動の理由が別の項目に隠れている

`type` という項目を1つ見せておくほうが、結果として説明しやすいと判断しました。
自動判定は入力の手間を減らしますが、**何が起きるか予測できなくなる**ぶんを別のところで払うことになります。

## 残っている課題: 押す前に区別がつくか

要素を分けただけでは足りません。

`<a>` と `<button>` の違いは、スクリーンリーダーや中クリックでは伝わりますが、
**画面を見て操作している人には見た目でしか伝わりません。**

飛ぶカードと開くカードが同じ見た目で並んでいたら、押すまで何が起きるか分からない。
ここは次の工程で詰めます。矢印のアイコンを付けるのか、余白で差をつけるのか、まだ決めていません。

要素の選び方を先に決めておくと、この検討が**見た目だけの問題**として残ってくれます。
そこは楽になりました。
