公開したページを Lighthouse で測ったら、モバイルだけ壊れていました。

原因は日本語Webフォントで、直したのは1行です。ただ「1行で直った」より、**なぜ気づかなかったか**と**直ったと判定してよかったのか**のほうが自分には収穫だったので、その順で書きます。

## モバイルだけ LCP が 9.6 秒だった

| | 📱 モバイル | 🖥 デスクトップ |
|---|---|---|
| Performance | **74** | 94 |
| **LCP** | **9.6 s** | 1.7 s |
| Accessibility / Best Practices / SEO | 100 / 100 / 100 | 100 / 100 / 100 |

落としているのは LCP ただ1項目でした。Performance の重みは25で、他に 0.9 を下回る項目がありません。

## 142リクエスト中130本がフォントだった

ネットワークを見たら、内訳がはっきりしていました。

```text
全142リクエスト中、130本がフォント。合計 1,539 KB。
<link rel="preload"> が 122本（うちフォントが121本）。
```

該当のコードはこれだけです。

```ts:src/app/layout.tsx
const zenKakuGothicNew = Zen_Kaku_Gothic_New({
  variable: '--f-jp',
  subsets: ['latin'],
  weight: ['400', '700'],
  display: 'swap',
})
```

## 日本語フォントは unicode-range で分割されて配信される

Google Fonts は日本語フォントを1ファイルで配らず、`unicode-range` で細かく分割して配信します。1ファイルに全グリフを入れると巨大になるためです。

`next/font` がビルド時に取りに行くのと同じ CSS を取得すると、Zen Kaku Gothic New は**1ウェイトあたり121ファイル**でした。日本語の分割が118、残りの3つが `cyrillic` / `latin-ext` / `latin` です。

## preload されたのは、2つ目のウェイトの日本語だけだった

`next/font` は、この CSS を上から読みながら `/* latin */` のようなコメントでサブセットを判定し、`subsets` に指定したものだけを preload の対象にします（`find-font-files-in-css.js`）。コメントの無いブロックは、**直前のコメントのサブセットを引き継ぐ**作りでした。

ところが、日本語の分割118ファイルにはサブセット名のコメントが付いていません。CSS の並びはこうなっていました。

```text
400 の日本語 118ファイル（コメント無し）
/* cyrillic */ /* latin-ext */ /* latin */   ← 400 の欧文
700 の日本語 118ファイル（コメント無し）     ← 直前の latin を引き継ぐ
/* cyrillic */ /* latin-ext */ /* latin */   ← 700 の欧文
```

400 の日本語は CSS の先頭にあり、まだ何のサブセットでもないので対象外です。**700 の日本語118ファイルは、直前の `/* latin */` を引き継いで、latin として preload されていました。**

数えると、latin が2本と 700 の日本語が118本で120本です。欧文フォント（JetBrains Mono）の latin 1本を足すと、フォントの preload 121本と一致しました。

ウェイトを400の1つだけにして同じように数えると、preload は1本でした。**ウェイトを2つ以上指定したときにだけ起きる**ことになります。

## `subsets: ['latin']` は効いていた

ここが自分の誤解していたところです。

以前、`next/font/google` の日本語フォントに `subsets: ["japanese"]` が指定できない話を書きました。そのときは `subsets: ["latin"]` を指定する形で解決しています。

https://zenn.dev/matsutake_prgrm/articles/japanese-webfont-subsets-latin

その記事に書いたとおり、`subsets: ["latin"]` を指定すれば日本語は問題なく表示されます。preload の対象も、ちゃんと latin に絞られていました。

ただ、日本語の分割ファイルには「自分は何のサブセットか」という印が無いので、2つ目のウェイトの分は latin に紛れ込みます。**`subsets` で絞ったつもりでも、ウェイトが2つ以上あると絞りきれません。**

前の記事では `subsets: ["latin"]` と `preload: false` を「どちらを選ぶか」の二択として書いたのですが、ウェイトを2つ以上使うなら**両方必要**でした。

## 直したのは1行

```ts:src/app/layout.tsx
  preload: false,
```

これは「フォントを読まない」設定ではありません。「全部先読みしろ」という指示を外すだけで、ブラウザが `unicode-range` を見て**実際に使う範囲のファイルだけ**を取りに行くようになります。

`display: 'swap'` は残しました。フォント待ちで文字が消えることはありません。

## 結果

同条件で測り直しました。

| | 📱 モバイル | 🖥 デスクトップ |
|---|---|---|
| **Performance** | 74 → **100** | 94 → **100** |
| **LCP** | **9.6 s → 1.7 s** | 1.7 s → 0.5 s |
| **CLS** | **0 → 0** | **0 → 0** |
| A11y / Best Practices / SEO | 100 / 100 / 100（維持） | 100 / 100 / 100（維持） |
| フォント | **130本 1,539 KB → 16本 187 KB** | 同左 |
| 総リクエスト | **142 → 28** | 同左 |

測定条件は Before の JSON から読み出して揃えました（Lighthouse 13.4.1・`simulate`・モバイルは既定 / デスクトップは `--preset=desktop`）。モバイルとデスクトップは**並列実行していません**。CPU が競合して数値が歪むためです。

## LCP だけ見て「直った」と判定しない

この表で自分が一番見たかったのは LCP ではなく **CLS** でした。

フォントの読み込み方を変えると、フォールバックフォントとのメトリクス差でレイアウトシフトが出ることがあります。`next/font` には `adjustFontFallback` があって自動で調整してくれるのですが、効いているかは測らないと分かりません。

結果は 0 → 0 で、悪化はゼロでした。`adjustFontFallback` が働いていたようです。

Before の CLS が 0 だったので、悪化していれば一目で分かる比較対象になっていました。**LCP だけ見ていたら、別の指標を犠牲にしていないかを確かめる手段がなかった**ことになります。

## デプロイする前に、ビルド出力で判定できる

スコアは本番でしか測れませんが、**原因が消えたかどうかはその手前で分かります**。

```bash
npm run build
grep -o 'rel="preload"' .next/server/app/<route>.html | wc -l
# 122本 → 2本（残るのは欧文フォントの1本と、スクリプトの1本）
```

減っていなければデプロイする意味がないので、ここで切れます。

### Preview デプロイでは測れませんでした

Vercel の Preview URL は Deployment Protection で **302**（ログイン画面）が返ります。preload を数えたら **0本**でしたが、これは改善ではなく**ログイン画面を数えていた**だけでした。

122 → 2 は期待どおりです。0 は**期待より良すぎました**。期待より良い数字が出たときは、測った対象が正しいかを先に疑ったほうがよさそうです。

保護を切れば測れますが、未公開の変更が誰でも見える状態になるので切りませんでした。`preload: false` を独立したコミットにしておけば、悪化していても1コミット revert できるので、本番マージ後に1回測る形にしています。

## デスクトップでは見えなかった

デスクトップは 94 で、合格に見えていました。開発中に見ていたのもそちらです。

回線とCPUがスロットリングされる環境では、1.5 MB のフォントが帯域を占有します。デスクトップの高速回線では、同じ130本を読んでも体感に出ません。

「速い」は環境に依存するので、**どの環境で速いのかを言わない限り意味がない**、というのが今回いちばん残ったことでした。モバイルとデスクトップは両方測るようにしています。

※ CSS の並びと `next/font` の判定は、2026年10月時点（Next.js 16.3.0）で確かめたものです。どちらも今後変わる可能性があります。
