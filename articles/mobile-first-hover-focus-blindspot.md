自作アプリのUI実装が終わって、マージした直後のことです。

PCのブラウザで触ってみて「あれ、ボタンのホバーアクションなくない？」と気づきました。

プロジェクト全体を検索したら、`hover:` の指定が **0件**でした。1つも書いていない。

## 見落としではなく、構造的に気づけない

最初は自分の注意不足かと思ったのですが、経緯を振り返ると違いました。

タップ時の押し込み（`active:scale-95`）は入れてあります。つまり**スマホでは何も問題なく動いていた**。
開発中の確認は390×844のシミュレータでやっていたので、そこでは完璧に見えていました。

問題はここです。

> **マウスにしかない「押す前」という状態を、スマホで確認している限り、永久に思い出せない**

ホバーは指では発生しません。存在しない状態のことは、確認していても気づけない。
「実装を忘れた」のではなく「**確認手段の中に存在しなかった**」のだと思います。

だからチェックリストに「hoverを確認する」と書いても弱いです。
原因は忘れっぽさではなく**入力デバイスが片方しかなかった**ことなので、「PCで触る」を工程そのものに入れないと再発します。

## ホバーを調べたら、もっと重い問題が出てきた

ホバーを実装するついでにフォーカスまわりも見たら、入力欄にこれが付いていました。

```css
outline: none;
```

**キーボードでフォーカスしても、いま自分がどこにいるか分からない状態**でした。
WCAG 2.4.7（フォーカスの可視化）に引っかかります。

これが出てきたのは、正直こたえました。
UI実装の工程で `aria-pressed` を付けたり、コントラスト比を測ったり。
アクセシビリティ対応は一通りやったつもりでいたからです。

抜けていた理由は、いま振り返ると明確でした。

- やったこと: **支援技術に情報を渡す**（`aria-*`、`fieldset` + `legend`、コントラスト比）
- やっていなかったこと: **キーボードだけで操作してみる**

情報を渡す設計はしたけれど、操作は一度も試していなかった。

優先度で言えば、ホバーは「あると気持ちいい」ものですが、フォーカスリングは**無いと操作できない人がいる**ものです。後者のほうが重い。
ホバーがないと気づいたことで、より重い問題に当たれたのは運が良かったです。

### `outline-none` はそもそも要らなかった

調べていて、これが一番の発見でした。

自分が `outline: none` を書く癖を持っていたのは、Web制作を始めた頃の慣習です。
当時は**クリックのたびにフォーカスリングが出るのが邪魔**だったので、消すのが普通でした。

いまは `:focus-visible` があります。
ブラウザが「キーボードで到達した」と判断したときだけ効くので、**マウスのクリックではもう出ません。**

つまり、消す理由になっていた問題は、ブラウザ側で解決済みでした。

**古い慣習が、目的を失ったまま手に残っていた**ケースです。WordPressを長くやっている人ほど、この手のものを持っていると思います。
自分にもまだあるはずですが、自覚がないから探しようがないのが厄介なところです。

## Tailwind v4 が黙って防いでいたもの

ホバーを実装するにあたって、生成CSSを確認しました。

```css
@media (hover: hover) {
  .hover\:bg-surface-hover:hover { ... }
}
```

**`hover:` は `@media (hover: hover)` に自動で包まれていました。**

これがないと、定番のバグを踏みます。スマホでタップした後にホバー状態が残って、指を離しても色が変わったまま、というやつです。
タッチデバイスには「ホバーを解除する操作」がないので。

自分で書いていたら、たぶん忘れていました。

ただ、**知らずに恩恵を受けるのと、確認して知っているのは別**だと思っています。
知らないままだと、フレームワークを変えたときに同じバグを踏むので。生成CSSを見る習慣は、この工程でだいぶ身につきました。

もうひとつ使ったのが `enabled:` です。
下限に達して `disabled` になったマイナスボタンがホバーに反応すると、「押せないのに反応する」という嘘のフィードバックになります。

```jsx
className="enabled:hover:bg-surface-hover"
```

これで抑止しました。ホバーは「反応してほしい」だけでなく「反応してほしくない場面」もある、というのは実装するまで考えていませんでした。

## 記録ルールを機械的に適用しなかった判断

余談ですが、運用まわりでも1つ判断がありました。

自分は「バグを見つけたら直す前にスクリーンショットを撮る」というルールを決めています。
ポートフォリオの掲載ページでBefore/Afterを見せたいので、直した後では復元できない画像を先に確保しておく、という趣旨です。

今回はこのルールを適用しませんでした。理由は2つあります。

1. **ホバー不在は静止画に写らない**（何も起きていない画面が撮れるだけ）
2. Beforeの状態はgitで完全に再現できる

ルールの目的は「**後から復元できないものを守る**」ことです。gitに残っているものは復元できるので、急いで撮る理由がない。

ルールを機械的に適用すると、目的を果たさない作業が増えます。
書いた本人が守らない、という話ではなく、**書いた目的に照らして判断する**ということだと思っています。

## まとめ

- モバイルファーストで作ると、**hoverは構造的に抜ける**。忘れるのではなく、確認手段に存在しない
- 対策はチェックリストではなく「**PCで触る**」を工程に入れること
- 「支援技術に情報を渡す」と「キーボードで操作してみる」は別の作業。前者だけやっても後者は埋まらない
- `outline: none` を消す慣習は、`:focus-visible` の登場で目的を失っている
- Tailwind v4 の `hover:` は `@media (hover:hover)` に自動で包まれる。生成CSSで確認できる

モバイルファーストという手法が悪いわけではないです。悪かったのは、**確認するデバイスが片方だけだった**ことでした。
