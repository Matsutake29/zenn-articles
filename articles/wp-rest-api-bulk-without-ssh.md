自分のブログに、消しても消しても謎の自動コメントが増えていく現象が起きました。

犯人は自分でした。正確には、WordPressの標準機能でした。

調べて対処するまでに、WordPressの仕様で2つ、サーバー環境で1つハマったので記録します。
ちょうどSSHが使えない時期に重なったのですが、REST APIだけでも一括処理はできました。

## 発端: スパムコメントとコメント欄クローズ

もともとはスパムコメントが2件来ていて、その対応でした。

コメント機能自体を使う予定がなかったので、ついでに全記事のコメント欄をクローズすることにしました。
これで終わるはずでした。

## ハマり1: コメントを閉じたのに自動コメントが止まらない

クローズしたあとも、コメントらしきものが増えていきます。

正体は**セルフピンバック**でした。

### セルフピンバックとは

自分の記事から自分の別の記事にリンクを貼ると、WordPressが「リンクされましたよ」という通知(ピンバック)を自分自身に送る機能です。

内部リンクを貼るたびに発生します。SEOのために記事同士をつないでいたので、その分だけ律儀に通知が積み上がっていました。

**悪意ある第三者ではなく、WordPress自身の仕組み**だったわけです。

### なぜコメントを閉じても止まらなかったのか

ここが2つ目のハマりどころで、WordPressの投稿には**別々のフィールドが2つ**あります。

| フィールド | 制御するもの |
|---|---|
| `comment_status` | 通常のコメント |
| `ping_status` | ピンバック・トラックバック |

自分が閉じたのは `comment_status` だけでした。ピンバックは `ping_status` の管轄なので、素通りしていたわけです。

管理画面の「ディスカッション設定」で新規投稿のデフォルトは変えられますが、**既存の記事には適用されません**。51本すべてを個別に開いて変更する必要がありました。

## SSHが止まっていた

普通ならWP-CLIで一撃です。

```bash
wp post update $(wp post list --format=ids) --ping_status=closed
```

ところが、このときはSSHが使えませんでした。

自分で契約しているレンタルサーバーなのですが、脆弱性への対応としてホスティング側がSSH接続を一時的に停止していた期間だったんです。
自分の設定ミスではないので、こちらで直せるものではありません。復旧を待つか、別の手段を探すかの二択でした。

セキュリティ対応としては妥当な判断だと思います。
ただ、**自分で契約しているサーバーでも、事業者側の都合で急に使えなくなる経路がある**というのは、このとき初めて実感しました。

管理画面から51本を手作業で開くのは現実的ではない。
一括編集機能にも `ping_status` の項目はありません。

### REST APIで代用する

そこで、WordPress REST APIを使いました。アプリケーションパスワードで認証して、記事一覧を取得し、1本ずつ `ping_status` を更新していきます。

```
GET  /wp-json/wp/v2/posts?per_page=100&status=publish
POST /wp-json/wp/v2/posts/<id>   { "ping_status": "closed" }
```

これで51本を一括処理できました。

**WP-CLIが使えない状況でも、REST APIがあれば一括管理はできる。**
恥ずかしながらこれを知らず、今まで「SSHが通らないなら手作業」だと思い込んでいました。

SSHはHTTPとは別の経路なので、片方が止まってももう片方は生きています。
経路を1つしか持っていないと、そこが塞がった時点で作業が止まる。そういう話でもありました。

## ハマり2: DELETEがWAFに403で弾かれる

ついでにスパムコメントも削除しようとして、もう1つ引っかかりました。

REST APIでコメントを削除しようと `DELETE` メソッドを投げたところ、**403で弾かれます**。認証は通っているのに、リクエスト自体が届いていない挙動でした。

原因はサーバー側のWAF(SiteGuard)でした。DELETEメソッドそのものがブロック対象になっていたようです。

### 回避策: POSTでステータスを変える

WordPressのREST APIは、削除を「ゴミ箱に入れる」形でも表現できます。

```
POST /wp-json/wp/v2/comments/<id>   { "status": "trash" }
```

DELETEを使わず、POSTでステータスを `trash` に変える。これなら通りました。

WAFの設定を緩めることもできましたが、**セキュリティ設定を下げるより、通る書き方に寄せるほうが筋がいい**と判断しました。
一度きりの作業のために防御を外すのは、割に合いません。

## まとめ

- 消えない自動コメントの正体は、内部リンクによる**セルフピンバック**(WordPress標準機能)
- `comment_status` と `ping_status` は**別フィールド**。片方だけ閉じても止まらない
- 管理画面のディスカッション設定は**既存記事には適用されない**
- SSHが止まっていても**REST APIで一括処理できる**。WP-CLIの代わりになる
- WAFで `DELETE` が403になるなら、POSTで `status: trash` に寄せる
- 自分の契約サーバーでも、事業者側の都合で経路が塞がることがある

WordPressを長く触っていても、ピンバックまわりは意識する機会がほとんどありませんでした。
コメント欄を閉じるだけの作業のつもりが、仕様を2つ知ることになった回でした。

SSHが止まっていなければ、WP-CLIで一撃で終わって何も学ばずに済んでいたはずです。
塞がったから別の道を探したわけで、そういう回り道のほうが手札は増えるのかもしれません。
