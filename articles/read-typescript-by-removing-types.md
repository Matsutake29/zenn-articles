Next.jsのApp Routerで動的ルートのページを書いていて、30行ほどのファイルが読めませんでした。

自分で書いたはずのファイルです。それでも、どこからどこまでが何なのかが分からない。
TypeScriptがまだ身についていないからだと思っていました。

分解してみたら、原因は型ではありませんでした。
**`{}` という同じ記号が、1つのファイルの中で6種類の意味で使われていた**からでした。

## 読めなかったコード

```tsx
export default async function UserPage({
  params,
}: {
  params: Promise<{ username: string }>
}) {
  const { username } = await params
```

関数の引数のところです。`{` と `}` と `:` が入り混じっていて、
どこまでが引数の宣言でどこからが型なのかが目で追えませんでした。

## 3手で素のJavaScriptまで戻す

読めないものは分解する、ということで3手戻しました。

1. 型注釈を消す
2. 改行を戻して1行にする
3. 分割代入をほどく

結果がこれです。

```tsx
async function UserPage(props) {
  const params = props.params
  const resolved = await params
  const username = resolved.username
```

読めました。**やっていることは、オブジェクトを1個受け取って、中から値を取り出しているだけ**でした。

Next.jsは引数を1個しか渡してきません。その1個のオブジェクトの中に `params` や `searchParams` が入っている。
元のコードは、それを受け取ると同時に中身を取り出して、さらに型を書いていたので、
3つのことが同じ場所に重なって見えていました。

戻した形と元の形は同じ意味です。戻した形が読めるなら、元の形も読めます。同じものなので。

## `{}` が6種類あった

分解して気づいたのが、記号の使い回しでした。

| 場所 | `{}` の意味 |
|---|---|
| `function UserPage({ params })` | 分割代入（値） |
| `: { params: ... }` | 型の宣言 |
| `{ username: string }` | 型の宣言（入れ子） |
| `const { username } = ...` | 分割代入（値） |
| `<h1>@{username}</h1>` | JSXの式埋め込み |
| `function ... { ... }` | ただのブロック |

6種類が1ファイルに同居していました。

読めなかったのは、型が難しかったからではなく、
**同じ記号を見るたびに「これはどっちだ」と判定させられていた**からでした。

見分け方は1つで済みました。

**`:` の右側にあるなら型、それ以外は値。** JSXの中の `{}` だけ別枠で、JavaScriptに戻るスイッチ。

これだけ決めてから読み直したら、同じコードが普通に読めるようになりました。

## 型は消しても動く

分解の過程で気づいたのが、型を全部消しても動くことでした。

```tsx
const cards = [{ title: "...", url: "..." }]   // 型注釈なし
const cards: Card[] = [{ title: "...", url: "..." }]   // 書いた場合
```

**今の時点では挙動が1ミリも変わりません。** 推論してくれるので、書かなくても同じように動きます。

では何のために書くのか。自分の場合、実際に効いた場面がまだ少ないので、
分かっているぶんだけ書いておきます。

**エラーが出る場所が「入口」になる**

DBと繋いだとき、型があると値が入ってきた時点でエラーになります。
型が無いと、壊れた値がそのまま流れて、画面に出す直前まで気づけません。
壊れたものが遠くまで運ばれるほど、原因を探す距離が長くなります。

**エラーメッセージに型名が出る**

`Property 'username' does not exist on type 'Promise<{ username: string; }>'`
のように、何が来るはずだったかがメッセージに書かれます。
これは実際に助かりました。

## ついでに調べた: 空配列の `never[]`

「型注釈なしだと空配列から始められない」と聞いたことがあって、
`never[]` になるから何も入れられない、という理解でいました。

気になったので `tsc --strict` で実際に試したら、思っていたのと違いました。

```ts
const a = []
a.push({ title: "x" })   // ← エラーにならない
```

通ります。型注釈なしの空配列は、**その後の代入で型が育つ**ようになっていました。

エラーになったのは、pushせずにそのまま使ったときです。

```ts
const b = []
const t = b.map((x) => x)
// error TS7005: Variable 'b' implicitly has an 'any[]' type.
```

`never[]` ではなく `any[]` と言われました。

`never` が出てきたのは、ジェネリックな関数に空配列を渡したときでした。

```ts
const [c] = useState([])
c.push({ title: "x" })
// error TS2345: Argument of type '{ title: string; }'
//   is not assignable to parameter of type 'never'
```

`useState([])` のような書き方をしたときに、初期値から型を決めようとして
`never[]` になる、という話だったようです。

聞きかじりの理解のまま「空配列は `never[]` になる」と覚えていたのですが、
どこで起きるかを取り違えていました。3行書いて実行すれば分かることでした。

## 難しかったのは型ではなく、記号の多義性だった

「TypeScriptが難しい」と感じていた中身は、型そのものではありませんでした。
**同じ記号が複数の役割を持っている**ことに慣れていなかっただけでした。

分解して素のJavaScriptに戻せば、やっているのは
「オブジェクトを1個受け取って、中から値を取り出す」だけです。

読めないファイルに当たったら、まず型を消して改行を戻す。
これは今後もやると思います。想定読者は、`page.tsx` の1行目で止まっていた少し前の自分です。
