書き溜めたZenn記事が4本たまったので、公開日を1日ずつずらして予約投稿しました。

`published_at` を07-26〜07-29に散らして、1回のpushで送りました。

**受理されたのは1本だけでした。**

## 何が起きたか

pushは成功しています。GitHubのコミット履歴にも4本ちゃんと乗っています。
なのにZennのダッシュボードには1本しか出てきません。

デプロイ履歴を開いたら、こう書いてありました。

> 次の記事は投稿数の上限に達したためデプロイされませんでした: （slug3つ）

Zennには投稿数の上限（レートリミット）があります。これ自体は知っていて、
だからこそ**公開日を分散させれば大丈夫だろう**と思っていました。

そこが間違いでした。

## 予約投稿では回避できない

公式FAQに書いてありました。

> 記事は直近24時間以内の投稿数（**投稿予約中を含む**）、本は直近1週間以内の投稿数に基づいて判定されます

https://zenn.dev/faq/rate-limit

`published_at` は「公開を遅らせる」だけで、**投稿そのものはpushした瞬間に行われています**。
予約中の記事も投稿数に含まれるので、公開日をどれだけ散らしても意味がありませんでした。

言われてみればそのとおりで、Zenn側には「予約中の記事」というデータが既に存在しています。
公開されていないだけで、投稿は済んでいる。そう考えると自然な仕様でした。

あわせて分かったことを並べます。

- **上限のロジックは非公開**です（不正防止のため、と明記されています）。何本までOKかを事前に知る方法はありません
- **記事・本・スクラップはそれぞれ独立した枠**を持っています。スクラップは意図的に緩めに設定されているそうです
- 上限緩和の申請窓口はありますが、想定されている用途は**他ブログサービスからの移行**です

## 「3本目から拒否される」ではなかった

以前に3本連続で投稿して3本目が弾かれたことがあり、「24時間で3本まで」という固定の閾値だと
思い込んでいました。

今回は**4本中1本しか通っていません**。3本目どころか2本目で弾かれています。

直前の数日を振り返ると、4日前に1本、2日前に2本を投稿していました。
おそらくその分だけ枠が削れていたのだと思います。**残枠は直近の投稿ペースで変動する**、
というのが実測から言えることでした。

固定の本数で覚えていたので、今回は読み違えました。

## 弾かれても何も起きないのが怖い

一番厄介だったのはここでした。

- GitHubへのpushは**成功します**
- ワークフローもエラーになりません
- 記事URLにアクセスしても、予約中なら公開前は404なので、失敗と区別がつきません

**ダッシュボードのデプロイ履歴を自分で開かない限り、弾かれたことに気づけません。**

このとき私は3本ぶんの公開予定が消えたことに、たまたまデプロイ履歴を見て気づきました。
見ていなければ、07-27の18時になっても記事が出ないことに当日まで気づかなかったはずです。

なお、拒否された記事は**Zennに登録されていない**ので、`published_at` を書き換えられます。
「一度設定した公開日時は変更できない」という制約は、登録が通った記事の話でした。
ここは救いでした。

ちなみに拒否された直後に日時を付け替えて再pushしてみましたが、受理はゼロでした。
拒否そのものは枠を消費しないようですが、直後の再試行は無意味でした。

## 対策：articles/ の外に待機所を作る

Zennが記事として読むのは **`articles/` 直下だけ**です。それ以外のディレクトリは無視されます。

なので、記事を置く場所をひとつ増やしました。

```
zenn-articles/
├── articles/     ← Zennが見る。ここに入った瞬間カウントされる
├── _queue/       ← 待機所。Zennからは見えないのでカウントされない
└── .github/workflows/drip.yml
```

`_queue/` に何本入れておいてもカウントされません。そこからGitHub Actionsで
**毎日1本ずつ `articles/` へ移す**ようにしました。

```
_queue/NN-{slug}.md   →   articles/{slug}.md   （毎日09:00・当日18:00公開で予約）
```

これで「まとめて書いて、出すのは毎日1本」が成立します。
上限を破っているわけではなく、Zennが許容しているペースに自動で合わせているだけです。

キューに入れる記事の `published_at` は書きません。昇格したときに日付が決まります。

## 実装で工夫した2点

### その日に公開予定があればスキップする

手動で予約した記事が1本残っていたので、そこにドリップが重なると同じ日に2本公開されてしまいます。

昇格の前に `articles/` を走査して、公開予定日が当日と一致する記事があれば見送るようにしました。

```python
for path in sorted(ARTICLES.glob("*.md")):
    if scheduled_date(path) == today:
        log(f"[skip] {today} は {path.stem} が公開予定です。今日は昇格させません。")
        return True
```

これで手動予約とドリップが混在していても、1日1本が保たれます。

### 公開されたかをフィードで照合する

前述のとおり、弾かれてもGitHub側は成功したまま無反応です。
自動化するとここが致命傷になると気づきました。**気づかないまま毎日1本ずつ捨て続ける**ことになるからです。

実行のたびに、公開予定日を過ぎた記事がZennのフィードに載っているかを確認して、
載っていなければジョブを失敗させるようにしました。

```python
# 当日公開分はまだ時刻前のことがあるので、前日〜4日前を見る
window = [today - datetime.timedelta(days=n) for n in range(1, 5)]
targets = []
for path in sorted(ARTICLES.glob("*.md")):
    d = scheduled_date(path)
    if d in window:
        targets.append((path.stem, d))

published = fetch_published_slugs()   # https://zenn.dev/{user}/feed をパース
if published is None:                # 取得できなければ照合を諦めて素通しする
    return True

missing = [(slug, d) for slug, d in targets if slug not in published]
```

`missing` が空でなければ終了コードを1にして、ワークフローを失敗させています。
失敗すればGitHubから通知が飛ぶので、翌日には気づけます。

フィードの取得に失敗したときは（ネットワーク断など）ジョブを落とさず素通しにしました。
検知の仕組み自体が原因で公開が止まると本末転倒なので、昇格の処理は続行させています。

## まとめ

- Zennのレートリミットは**直近24時間の投稿数**で判定され、**投稿予約中のものも含まれる**
- なので `published_at` で公開日を散らしても回避できない。**pushした時点でカウントされる**
- 上限は固定値ではなく、直近の投稿ペースで変動する（4本push → 受理1本を実測）
- 弾かれてもpushは成功する。**デプロイ履歴を見る習慣がないと気づけない**
- Zennが読むのは `articles/` 直下だけなので、外に待機所を作れば「まとめて仕込んで毎日1本」ができる

「書けたときにまとめて出す」ではなく「まとめて書いて、出すのは毎日1本」に切り替える。
仕組みで縛ってしまえば、投稿ペースを毎回考えなくて済むようになりました。
