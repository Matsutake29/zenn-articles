自作アプリをVercelにデプロイしました。ブラウザで開いたら普通に表示されて、これで工程完了……のつもりでした。

念のため `curl -I` でヘッダを見たら、そこそこ大きい問題が出てきました。

**ブラウザで開いて「表示された」で終わらせると、ヘッダの問題は永久に見つかりません。** 画面には何も出ないので。

見つかったものを5つ書きます。

## 1. アセットのキャッシュが実質無効だった

今回いちばんの発見です。

```bash
curl -I https://plate-calculator-zeta.vercel.app/assets/index-DHql7efF.js
```

```
cache-control: public, max-age=0, must-revalidate
```

`max-age=0, must-revalidate` が、**`/assets/` 配下にも付いていました。**

VercelのViteプリセットの既定です。つまり2回目以降の訪問でも、毎回サーバーへ問い合わせが発生していました。
304が返るので転送量は小さいものの、往復のレイテンシは毎回かかります。

`vercel.json` で上書きしました。

```json
{
  "headers": [
    {
      "source": "/assets/(.*)",
      "headers": [
        { "key": "Cache-Control", "value": "public, max-age=31536000, immutable" }
      ]
    }
  ]
}
```

1年（31536000秒）です。

### なぜ1年キャッシュしても安全なのか

ここが理解の要点でした。

Viteが出力するファイル名は `index-DHql7efF.js` のようになっています。
この `DHql7efF` は**中身から計算されたハッシュ**です。

内容が1バイトでも変われば、名前も変わります。つまり**同じ名前で中身が違うことが起こりえない。** だから永久にキャッシュして構いません。

### HTMLは `must-revalidate` のままが正しい

一緒に変えたくなりますが、変えてはいけない側でした。

HTMLの中に「どのハッシュのアセットを読むか」が書いてあります。
ここを1年キャッシュすると、**新しいデプロイが永久に届かなくなります。**

- **アセット: 1年キャッシュ**（名前が変わるので安全）
- **HTML: 毎回確認**（更新の入口なので）

この組み合わせで、キャッシュを効かせつつ更新も即座に届きます。

WordPressの案件でも `.htaccess` にキャッシュヘッダを書くことはありました。
ただ正直「よく見る設定をコピーしている」感覚でした。
**なぜその値なのかを説明できるようになったのは、今回が初めて**です。

## 2. メタ情報が3つしかなかった

```bash
curl -s https://plate-calculator-zeta.vercel.app/ | grep '<meta'
```

`charset` `viewport` と `title` `favicon` だけでした。Viteの雛形のままです。

公開URLを人に見せる工程だったので、`description`・OGP・`theme-color` を足しました。

`theme-color` は少し面白い挙動をします。

```html
<meta name="theme-color" content="#f7f7f5" media="(prefers-color-scheme: light)">
<meta name="theme-color" content="#212224" media="(prefers-color-scheme: dark)">
```

値はCSSのトークンと同じものを使いました。これを入れると、**スマホのアドレスバーがアプリの背景と地続きに見えます。**

PCのブラウザでは確認できない類の効果で、実機で開いて初めて「あ、効いてる」と分かりました。

## 3. ドメインが「取れたもの」であって「選んだもの」ではなかった

公開URLが `plate-calculator-zeta.vercel.app` になっていました。`-zeta` が付いている。

`plate-calculator.vercel.app` を誰かが既に使っていました。
Vercelが衝突を避けて、自動でサフィックスを付けていたんです。

確認方法は単純で、候補ドメインに `curl` して `<title>` を見ただけです。
英語の "Plate Calculator" が返ってきたので、**別のプロジェクトだと判別できました。**

デプロイ先のURLは、自分が選んだものとは限らない。当たり前ですが、意識していませんでした。

## 4. デプロイ固有URLは外から見えない

Vercelは、デプロイごとに固有のURL（`plate-calculator-7hfd6xcv1-...`）も発行します。

これに `curl` すると302で `vercel.com/sso-api` へ飛びました。
Deployment Protection の既定動作で、SSOで保護されています。正常な挙動です。

人に見せるのは本番ドメインのほう、という区別を知りました。SNSで共有するときに固有URLを貼ると、他人は開けません。

## 5. 実転送量とリージョンを数字で押さえた

```
x-vercel-id: hnd1::...
```

配信リージョンは `hnd1`（東京）でした。

初回ロードの実転送量は**約68.5kB**（brotli圧縮後）。
内訳はJS 63.2 + CSS 3.9 + HTML 0.5 + favicon 1.4 です。

**Reactを含めてこのサイズ**、というのは自分にとって意外でした。
WordPressのサイトだと、jQueryとプラグインのCSSだけで軽く超えます。

## おまけ: Lighthouseの数字は「体験の話」に翻訳する

ついでに測ったLighthouseは4項目すべて100点でした（パフォーマンス / ユーザー補助 / おすすめの方法 / SEO）。

- FCP 1.2秒
- LCP 1.2秒
- **TBT 0ミリ秒**
- **CLS 0**

ポートフォリオの掲載ページに書くにあたって、少し考えました。

**「4項目100点」より、TBT 0ms と CLS 0 を推したい**と思っています。100点は運の要素もありますが、

- TBT 0ms → **タップした瞬間に反応する**
- CLS 0 → **読み込み中にボタンが動かない**

と、体験の話に翻訳できるからです。採用担当がエンジニアとは限らないので、数値をそのまま出すより意味に訳したほうが伝わります。

CLS 0 が出た理由も説明できるようにしました。
プレートの描画は目標重量が確定してから行われるので、画像の後読みでレイアウトが動くことがない。
フォントもシステムフォント（`system-ui`）なので、Webフォントの差し替えによるズレが起きない。

「たまたま0だった」と「0になる理由がある」は、聞かれたときに差が出るところだと思います。

## まとめ

- **ブラウザで開くだけでは、ヘッダの問題は画面に出ない**
- Vercel + Vite の既定では、`/assets/` にもキャッシュが効いていない場合がある
- **アセットは1年・HTMLは毎回**。ファイル名にハッシュが入っているから1年で安全
- `theme-color` は実機でしか効果を確認できない
- Lighthouseの数値は、体験の言葉に翻訳してから見せる

デプロイは「動いたら終わり」に見える工程ですが、`curl -I` を1回打つだけで拾えるものがありました。5分の作業です。
