ただ、**うまくいった理由よりも、走りながら足りないと分かったものの方が多かった**です。
2本目に入る前に、その両方を整理しておきます。

## 実際にはこう進んだ

最初に10工程の計画を立てましたが、そのとおりには進みませんでした。
**★が計画に無かったもの**です。

```
0. 準備 ★                     記録ルールの制定・工程計画
1. 詳細設計                     要件定義・画面ラフ・競技ルールの確認
2. 環境構築                     Vite+React+TS+Tailwind / ESLint / CI
     └ 棚卸しレビュー ★         "終わったつもり"の後にもう一度点検
3. コアロジック実装              純粋関数として実装（UIから分離）
4. テスト                       エッジケースを固定
5. UI実装
     └ 読み解きフェーズ ★       自分が実装を理解する時間
     └ 差し込み修正 ★           読み解き中に見つけたバグ
6. 仕上げ                       レスポンシブ・バリデーション
     └ 一次情報の確認 ★         公式ルールブックを直接読む
7. デプロイ                     Vercel・Lighthouse計測
8. README整備                   設計判断・スクショ・ライセンス
9. 作品ページ ★                 非エンジニア向けの説明ページ
10. 記事・書類への反映
11. 振り返り ★                  この記事のもとになったもの
```

**★が5つ。計画の半分近くが、走りながら足されました。**

1本目なので当然ではあります。ただ、この5つは**2本目では最初から工程に入れられる**ものでした。

## 7日で終わった一番の理由

**記録を先に取っていたので、書く工程で考える時間がゼロだった**ことです。

数字で出ました。

| 工程 | 見積 | 実績 |
|---|---|---|
| README整備 | 3h | **1h** |
| 作品ページ制作 | （計画外） | **40分** |

READMEを書くときに「何を書こうか」と考える時間が発生しませんでした。
設計判断の理由も、スクリーンショットも、測定値も、開発中に別ファイルへ書き出してあったからです。

**書く工程のコストは、書く前にどれだけ材料が揃っているかで決まる。** これが一番の発見でした。

ただしこの記録ルールを作ったのは**工程5の途中**で、それより前の実績時間とスクリーンショットは
永久に失われました。詳しくは後述します。

## やってよかったこと

### 最初に工程表を作った

10工程に分けて、それぞれに見積時間と完了条件を書きました。効いたのは3つです。

- どこまで来たかが常に見えるので、**モチベーションが切れなかった**
- 見積があるから**差が測れる**
- 1工程ずつ完結させて進められた

見積と実績の差は、そのまま面接で話せる材料になります。
「3時間で見積もって1時間で終わり、理由はこうでした」と説明できる状態は、実務経験者としての武器になると思っています。

### 実装後に「読み解きフェーズ」を挟んだ

UIの実装が終わっても次の工程に進まず、**自分でコードを理解する時間**を取りました。

ここで設計の穴が2つ見つかりました。うち1つは、±ボタンを押しても目標重量が1ミリも動かなくなるバグです。

面白かったのは、**そのとき書いていたテストでは見つからない類のバグ**だったことです。
ボタン側の「2.5kg動かす」という要求も、値を丸める側の処理も、それぞれ単体では正しい。
組み合わせたときだけ壊れていました。

後から考えると、テストの書き方の問題でもありました。
「この関数がこの入力でこの値を返すか」ではなく「**押したら必ず値が動く**」という性質で書いていれば、
組み合わせの壊れも捕まえられたはずです。ここはまだ自分の中で整理しきれていません。

理解のための時間が、結果的に品質検査になっていました。

### 分からないところで止まらなかった

理解できない箇所は「未理解メモ」に送って、工程は進める運用にしました。区切りで回収する時間を取ります。

**止まらなかったから7日で終わった**というのは、たぶん間違いないです。
理解が浅いまま進む不安はありますが、後で回収する仕組みがあれば成立しました。

### 一次情報を読んだ

仕様を決めるとき、参考記事ではなく国際連盟が出している英語の公式ルールブック（44ページ）を直接読みました。

その結果、**参考記事をもとに書いていた仕様の誤りが2件**見つかりました。
想定外で1時間かかりましたが、この話はREADMEにも作品ページにも記事にも使えました。
**調べた時間は、素材の時間でもあった**わけです。

### AIとの役割分担を工程ごとに変えた

- テスト実装は**自分で書いた**（新しい概念を学ぶ工程だから）
- UI実装は**AIに任せた**（CSSは実務スキルがある領域だから）

「全部任せる」でも「全部自分で書く」でもなく、工程ごとに決めました。
判断の軸と、実際にどう分けたかは[同じプロジェクトで、テストは自分で書きUIはAIに任せた話](https://zenn.dev/matsutake_prgrm/articles/ai-role-split-by-task)に書いています。

## 次に直すこと

ここからが本題です。**9つ出ました。**

### 1. 記録ルールを最初に決める

記録ルールを作ったのが工程5の途中だったので、**工程2〜5の実績時間とスクリーンショットが永久に失われました**。

文章のログは後から書けます。でも**この2つだけは後から復元できません**。

次は工程0（着手前）で決めます。

### 2. 「作品ページ」を工程表に入れる

これが一番効きました。

記録ルールの目的は「**作品ページを書くための素材を確保すること**」なのに、
**その作品ページを書く工程が計画に存在しませんでした**。

素材を集めるだけ集めて終わる構造だったわけです。**目的地の無い計画**でした。

作ったものが人に届く経路は、コードではなく作品ページです。次は工程表の末尾を必ずこうします。

```
n-2. README整備
n-1. 作品ページ制作・公開      ← 必ず入れる
n.   記事＋書類への反映
n+1. 振り返り                  ← 必ず入れる
```

### 3. バグ修正は独立したコミットにする

ダークモードで黒いプレートが背景に溶けるバグを直したとき、**他の変更と一緒にコミットしてしまいました**。

結果、**Beforeの状態が履歴から再現できなくなりました**。
3週間後、作品ページで「一番伝わる画像」として使う予定だったのに、画像が存在しませんでした。

ルール自体は最初から書いてありました。守れなかったのは、**バグを見つけると反射的に直しにいく**からです。
知識としてのルールでは止まりません。手順に組み込みました。

1. バグを見つける → **その場でスクリーンショット**（修正を考えるより先）
2. 撮ってから直す
3. 修正後、**同じ画角で**もう1枚
4. **修正だけを1コミットにする**

### 4. 着手前チェックを最初から使う

工程5で、**Issueを立てるのとブランチを切るのを両方忘れました**。mainブランチ上で実装が完了していました。

コミット前だったので `git checkout -b` で助かりましたが、これも「知っている」では防げませんでした。

### 5. まだ決まっていないものを工程表に入れない

「v1公開後に着手を判断する」という工程を計画に入れていましたが、判断の結果は**取り下げ**でした。

v1のスコープを決めた時点で分かったはずのことを、工程として最後まで抱えていたことになります。
**未確定のものを工程表に置くと、完了率が実態より低く見えます。**

### 6. 公開直前に数値を測り直す

作品ページに載せるテスト件数が、**21のまま**でした。実際は32件です。
途中でテストを追加したのに、素材ファイルを更新していませんでした。

しかも測り直すとき、ソースコードを `it(` でgrepして「23件」と数えてしまいました。
Prettierの整形で改行されていて拾えていなかったんです。

**数えるな、コマンドの出力を使え**、という話でした。

### 7. ドキュメントを実装と突き合わせる

READMEを書いた後で1文ずつコードと照合したら、**挙動の説明に4件の誤り**がありました。

**READMEは最も多くの人が読むのに、テストもCIも通りません。** 誤りが最も長く残る場所です。

記事に載せるコードも同じで、「読みやすく」コメントを書き換えていた箇所が3つありました。
実装からそのまま引用して、説明を足したいときはコメントではなく本文に書くべきでした。

### 8. 撮影手段を先に確認する

デモGIFを撮ろうとしたのが工程8です。そこで初めて「ブラウザの自動操作では撮れない」と分かりました。
**最後まで未達のまま公開しています。**

### 9. 公開手段を先に確認する

8とまったく同じ構造の失敗を、作品ページの公開でも踏みました。

- 本番が追従しているブランチが、想定と違った
- サーバー上に過去の直接編集が残っていて、`git pull` が中断した

**公開はフローの最後にしか来ないので、問題が見つかるのも最後**です。しかも「あと一歩」の場所で止まります。

## 2本目で使うチェックリスト

上の9つを、実際に手を動かすタイミングごとに並べ直したものです。
**まだ検証していません。** 2本目で使ってみて、機能しなかった項目は書き換えます。

### 着手前（工程0）

- [ ] 記録ルールを決めた（何を・どこに・いつ残すか）
- [ ] 素材ファイルと `screenshots/` を作った
- [ ] 工程表に**作品ページと振り返りが入っている**
- [ ] 工程表に**まだ決まっていないもの（v1.1候補）が入っていない**
- [ ] GIF・動画の撮影手段を決めた
- [ ] **公開手段を確認した**（手順・追従ブランチ・最終操作を誰が実行するか）

### 各工程の着手時

- [ ] Issueを立てた
- [ ] featureブランチを切った（`git branch --show-current`）
- [ ] ワーキングツリーがクリーン（`git status`）

### 各工程の完了時

- [ ] 完成画面のスクリーンショットを撮り、素材ファイルに1行書いた
- [ ] 着手（Issue作成）と完了（PR作成）の時刻を記録した
- [ ] 見積との差の理由を1行書いた
- [ ] 測定した数値を素材ファイルに転記した

### バグを見つけたとき

- [ ] **直す前に**スクリーンショットを撮った
- [ ] 修正後、同じ画角でもう1枚撮った
- [ ] **修正だけを独立したコミットにした**

### 公開前

- [ ] 数値を測り直した（テスト数・バンドルサイズ・依存数・Lighthouse）
- [ ] ドキュメントを実装と1文ずつ照合した
- [ ] ライセンスを明示した
- [ ] 作品ページから実物とリポジトリに導線がある
- [ ] **本番の追従ブランチにマージした**（`main` とは限らない）
- [ ] 公開後にURLを開いて、表示まで確認した

「バグを見つけたとき」の3つは、**知識としてのルールでは守れませんでした**。
見つけた瞬間に手が直しにいくので、チェックリストという形にしないと機能しないと思っています。

## まとめ

9つのうち **1・2・3が効きました**。共通しているのは「**後から取り返せないもの**」だという点です。

- 実績時間とスクリーンショット（1）
- 素材の行き先（2）
- バグのBefore（3）

コードは後から直せます。ドキュメントも後から書けます。でもこの3つだけは、その瞬間に取らないと消えます。

もう一つ、意外だった発見があります。

**止まった箇所はすべて「判断」でした。** 手が止まったのではなく、決めるために止まっていた。
掲載先をどこにするか、URLに階層を挟むか、設計ドキュメントの矛盾をどう整理するか。

7日のうち何度か立ち止まりましたが、**面接で話せるのはたぶんその部分**だと思っています。
