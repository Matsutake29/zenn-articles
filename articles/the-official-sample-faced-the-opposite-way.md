## 認証は公式ガイドのサンプルから始めた

Supabase で認証を入れるとき、公式ガイドのコードをベースにしました。
自前で書ける部分ではないですし、Cookie の扱いを間違えると
「ユーザーがランダムにログアウトされる」類の事故になります。

実際、いまも手元のコードには公式から持ってきた注意書きが残っています。

```ts
// Do not run code between createServerClient and
// supabase.auth.getClaims(). A simple mistake could make it very hard to debug
// issues with users being randomly logged out.
```

この判断自体は変えていません。**変えたのは条件文の向きだけです。**

## そのサンプルは「原則保護」だった

自分が参照した時点（2026年8月）のサンプルは、こういう形の条件になっていました。

```ts
// 構造だけ書き出したもの
if (!user && ログインページ以外) {
  → /login へリダイレクト
}
```

読み下すと **「ログインページ以外は全部ログイン必須」** です。

社内ツールやダッシュボード型のアプリを想定すれば、これが自然だと思います。
認証を入れるアプリの多くは「ログインした人のためのアプリ」なので、
**既定を保護にしておくほうが安全側に倒れます。**

## 作っているアプリは、その逆だった

Hubpin は `/[username]` が**誰でも見られる公開ページ**です。
自分の発信をまとめたページを人に見てもらうためのサイトなので、
ここが見られないと存在意義がありません。

| | 公式サンプルの想定 | Hubpin |
|---|---|---|
| 既定 | **保護**（ログイン必須） | **公開** |
| 例外 | ログインページだけ通す | **`/dashboard` だけ保護する** |

そのまま繋いでいたら、**ハブサイト本体が未ログインで見られなくなっていました。**
「これだけは死守する」と決めていた要件に、真っ向から抵触します。

反転させて、いまはこう書いています。

```ts
const { data } = await supabase.auth.getClaims()
const user = data?.claims

if (!user && request.nextUrl.pathname.startsWith('/dashboard')) {
  const url = request.nextUrl.clone()
  url.pathname = '/login'
  return NextResponse.redirect(url)
}
```

条件が「ログインページ以外」から「`/dashboard` のとき」に変わっただけです。
コードとしては数語の違いですが、**既定の向きが逆になっています。**

## 怖いのは、エラーが出ないこと

コピーしたコードは**正しく動きます。**
ビルドは通るし、ログインもできるし、リダイレクトも仕様どおりに実行される。

「未ログインだと公開ページにも入れない」という挙動が、**書いたとおりに実現されるだけ**です。
警告も型エラーも出ません。

気づく手がかりは、**自分でブラウザを開いてみること以外にありませんでした。**
しかもログインした状態で開発していると、公開ページも普通に見えます。
シークレットウィンドウで開いて初めて分かる種類の間違いです。

テストも、そのケースを書いていなければ通ります。

## 公式は多数派の要件を書いている

当たり前の話なのですが、書き終えてから改めて思いました。

公式ガイドが載せているのは**よくあるユースケース**です。
認証を入れる人の多くが「ログインした人のためのアプリ」を作るなら、
原則保護のサンプルを置くのが親切な設計だと思います。

Supabase のガイドにも「ページを保護するときは気をつけて」という趣旨の警告セクションがあって、
**そのまま使うことを前提にしていないことは示されています。**

問題は自分の要件が少数派だったことのほうです。
**自分の要件が多数派と逆を向いているとき、コピーは「動くけど間違っている」状態になります。**

## 気づけたのは、先に自分の要件を文章にしていたから

このプロジェクトでは、実装の前に手順書を書く運用にしています。
そこに **「保護したいのは `/dashboard` だけ」** と、自分の要件を先に書いてありました。

公式のコードと並べたときに向きが逆であることに気づけたのは、そのおかげです。
**比較する相手が文章の形で手元にあった**、という順序でした。

もし手順書なしでコードから入っていたら、
「公式のとおりに書いた」で終わっていた可能性が高いです。
動いてしまうので、疑うきっかけがありません。

ただし手順書も万能ではありませんでした。
同じ日に `matcher` の設定で、手順書に警告を書いておきながら同じ間違いを踏んでいます
（→ [matcher に「保護したいパス」を書いたら、1時間後にログアウトされた](https://zenn.dev/matsutake_prgrm/articles/matcher-is-scope-not-protection)）。
**書いてあることと、その瞬間に思い出せることは別**でした。

## 持ち帰り

- 公式サンプルは**多数派の要件**で書かれている。自分の要件が逆を向いていると、コピーは動くまま間違う
- **エラーが出ない間違いは、自分で開いて見るまで見つからない。** ログイン状態で開発していると気づけない
- 実装の前に**自分の要件を文章で持っておく**と、サンプルとの差分が見える
- なお、`proxy` だけに保護を任せないこと。Server Function は `matcher` の除外に巻き込まれるので、
  関数の中でも認証と認可を確かめる必要があります
